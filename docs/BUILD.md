# Сборки и временные файлы Проекта

`target/` — игнорируемый Git рабочий каталог, не место постоянных доказательств. Структура принадлежит этому документу; после `cargo clean` её восстанавливают инструменты. В корне допустимы только нативные выходы Cargo (`debug/`, `release/`, `tmp/`, `CACHEDIR.TAG`, `.rustc_info.json`), `nextest/` и один проектный каталог `highgrade/`. Проектные пробы, JSON и скрипты прямо в корень не клади.

```text
target/
  debug/                         Cargo: разработка и тесты
  release/                       Cargo: обычная release-сборка
  tmp/                           Cargo: временный каталог тестов
  nextest/                       штатный тестовый раннер
  highgrade/
    build-cache/                 Cargo-кэш кандидатов из точного SHA
    candidate/                   последний кандидат: CLI, kit, candidate.json
    candidate.previous/          только аварийное восстановление
    reports/                     журнал последней сборки кандидата
    tools/                       локальные инструменты
    work/                        lock и временные исходники; после сборки пуст
    tmp/<запуск>/                кратковременные пробы; убираются после задачи
```

Кандидат активации готовит `python scripts/build-release.py <точный-SHA-коммита>`. Это единственная обязательная release-сборка кандидата; предварительную `cargo build --release --locked` не выполняй без отдельного риска. Скрипт экспортирует именно этот Git SHA, собирает с `--release --locked` и использует общий `target/highgrade/build-cache` отдельно от обычного `target/release`: параллельная разработческая сборка не может подменить кандидат. Бинарник берётся из `compiler-artifact` текущего запуска Cargo, в том числе при `CARGO_BUILD_TARGET`. Временные исходники удаляются после штатного успеха и ошибки. Сбой сохраняет прежний кандидат. Скрипт не активирует Поставку и не публикует Git. На Windows до сборки проверь, что контекст применения сможет прочитать будущий `target/highgrade/candidate`; если песочница и активация работают от разных пользователей, собирай и применяй в одном разрешённом контексте вместо ручного расширения ACL готового кандидата.

Если меняется исполняемая CLI или Поставка `kit/` либо автор явно просит активацию, проверь активный ID через `global-status` и **перед коммитом, который будет активирован**, повысь patch-версию в `Cargo.toml`, `Cargo.lock` и полях `release`/`cli_version` манифеста `kit/manifest.json`. Согласуй ожидаемые ID в тестах и проверь манифест. Затем создай коммит и собирай кандидат из его SHA. В зависимой цепочке промежуточные коммиты без нужды в активной CLI не получают нового release ID; подробное условие — в [проектной инструкции](../.highgrade/project/INSTRUCTIONS.md). ID выпуска нельзя использовать повторно: одинаковый ID с другим бинарником остановит обновление. Для остальных проектных правок без запроса на активацию сборка и новая версия не нужны.

`candidate.previous` появляется только при двойной ошибке замены и отката. При его наличии новый выпуск отказывается работать до ручной проверки. Изменённые или чужие файлы кандидата и ссылки/junction скрипт не удаляет. Одновременный запуск отвергается блокировкой; после аварийного выключения сначала проверь, что сборка не идёт, затем разбирай остаток в `work/`.

## Обслуживание

```powershell
python scripts/target-maintenance.py
python scripts/target-maintenance.py --apply --scratch run-20260925
python scripts/target-maintenance.py --apply --cache release
python scripts/target-maintenance.py --check
```

Первая команда только показывает размер и найденные пути; удаление не планируется без выбора. `--scratch` удаляет только названного непосредственного ребёнка `highgrade/tmp/`; остальные файлы сохраняются. `--cache release` вызывает штатный `cargo clean --release`, а `--cache debug` — `cargo clean --profile test`. Перед удалением инструмент отказывает при работающем Cargo/rustc/nextest, непустом `work/`, аварийном кандидате, ссылке или junction внутри `target/`. Неизвестные пути он сообщает, но не удаляет. `--check` возвращает ошибку при неизвестном пути, оставшейся пробе или превышении мягкого бюджета **600 МиБ после обслуживания**. Это контроль на контрольных точках, а не жёсткий предел во время сборки. Не запускай полный `cargo clean` ради обычной уборки: он удалит и кандидат с инструментами.

Долговременные доказательства сохраняй в `specs/changes/<ID>/evidence` либо `docs/evidence`; приватную историю — в игнорируемом `.highgrade/local/archive`. Нужный отчёт копируй до удаления временной пробы. Старые неизвестные файлы разбирай по ссылкам и владельцу; автоматическая очистка их не захватывает. Кэш `build-cache/` можно пересоздать, но штатное обслуживание его сохраняет, чтобы не повторять сборку зависимостей каждого выпуска.

Маршрут preview → apply с одним `candidate_sha256` — в [проектной инструкции](../.highgrade/project/INSTRUCTIONS.md). Используй CLI и kit одного кандидата. Сам SHA не гарантирует одинаковые байты бинарника разных сборок; для apply сохраняется отпечаток конкретного кандидата. Проверка сборочного маршрута: `python -m unittest discover -s scripts/tests -v` (реальные Git/Cargo, отказ компиляции, чужие файлы и junction). Python 3.12 и Cargo обязательны; дополнительных Python-пакетов нет.
