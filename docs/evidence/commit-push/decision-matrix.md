## Состояния и общие предпосылки

- Pre-submit — обязательные для данного проекта проверки и ревью до фиксации/передачи кандидата. Их ошибка не превращается в допустимый поздний пробел
- Финальная готовность — полный набор обязательных local/remote критериев проекта. CI, возможный только после push/PR, может оставаться незавершённым при разрешённом кандидате
- Work, локальный SHA/build ID, commit, push, PR, CI, техническая готовность, human acceptance, merge/release, локальная активация и эксплуатационный deploy имеют отдельные основания и наблюдения
- Разрешённый кандидат не получает фиктивные ready, spec-integrate, result attention или accepted. Завершение Work и Goal остаётся зависимым от настоящих финальных барьеров
- Известные состав, цель, последствия и полномочия используются без повторного вопроса; существенное неизвестное ограничивает только зависимое действие

## HG-0063-S1: solo Git без выпуска и локальной активации

Вход: Git есть; конкретная задача и разрешение на commit известны; проект не назначает release ID и активацию. Remote/PR могут ещё отсутствовать.

| Условие | Предписанное действие и состояние | Что не выводится |
|---|---|---|
| Pre-submit выполнен; staged diff соответствует задаче | Сверить весь staged diff, лицензии/секреты, обязательные доказательства; создать точный локальный commit и сообщить SHA | Не нужны выпуск, повышение версии, build-release, global-update, push, PR или приёмка |
| Проверки Work актуальны; состав и значимые входы прежние | Переиспользовать результаты; повторять только затронутую проверку либо обязательный барьер проекта | Полный повтор тестов не нужен только из-за перехода этапа |
| Локальный обязательный pre-submit упал либо состав неизвестен | Вернуться в Work/уточнить зависимый состав до commit | Ошибку нельзя объявить поздним remote-пробелом |
| Финальные local gates выполнены | Готовность определяется проектом; отдельно сообщить состояние commit и acceptance | Сам SHA не доказывает готовность или принятие |
| Remote неизвестен, но локальный состав ясен | Локальный commit разрешён; будущую отправку оставить незавершённой | Отсутствие маршрута push не блокирует локальную фиксацию |

Наблюдение: правила действительно разделяют local fixation и release. `commit.md`, «Состав и барьер коммита» и «Проектная активация», не подставляет механизм установки High Grade в другой проект; шаблон «Сопровождение» хранит назначение активации и допускает её неприменимость. Вывод: нормативный исход S1 подтверждён.

## HG-0063-S2: feature → PR → обязательный remote CI

Вход: местный маршрут назначает feature-ветку, конкретную PR base, отдельный pre-submit и remote final gates; push и PR разрешены, merge не разрешён.

| Наблюдение / переход | Предписанное действие | Остаток и запрет |
|---|---|---|
| Remote CI ещё не может существовать до отправки | После pre-submit создать Commit-кандидат; по поручению отправить диапазон и создать/обновить PR с правильными base/head | Work/final readiness ещё не завершены; не нужен fictitious accepted |
| CI pending | Проверить удалённый SHA и вернуть ожидание конкретного CI в Work | Не интегрировать спеку, не передавать готовый result |
| CI unavailable / нет достоверного результата | Назвать недоступное наблюдение и следующий шаг; не подменять локальным успехом | Unknown остаётся финальным пробелом |
| CI failed | Вернуться в Work, устранить разрешённую причину; изменённый состав заново проходит затронутые проверки и разрешённые Commit/Push | Не обходить упавший pre-submit; не переиспользовать старый CI для нового SHA |
| CI success, но для другого SHA | Считать нужный exact-SHA CI незакрытым | Зелёный статус ветки не подтверждает проверяемый кандидат |
| CI success для точного SHA | Использовать это доказательство; завершить остальные финальные барьеры перед Work/spec-integrate/result | Не возникают acceptance, merge, release/deploy или локальная активация |

Наблюдение: `commit.md` явно допускает candidate при позднем CI; `push.md`, «Отправка кандидата и возврат в Work», предписывает отправку до CI и обратный переход. `work.md`, «Передача и продолжение», и «Работа с JSON-спецификацией» не требуют ready ради получения remote-наблюдения и не снимают финальные барьеры. Шаблон хранит pre-submit, final gates, remote/ветку, base/head и права. Вывод: нормативный исход S2 подтверждён; круговой зависимости ready → push → CI → ready нет.

## HG-0063-S3: отправка запускает autodeploy

Вход: runbook указывает автоматическое развёртывание от push в выбранную ветку. Это существенный внешний эффект с конкретной средой.

| Полномочия / наблюдение | Предписанный исход |
|---|---|
| Разрешён только Commit | Разрешённая локальная фиксация не разрешает push или deploy |
| Разрешён push, но deploy не раскрыт/не разрешён | До отправки раскрыть эффект и среду; остановить зависимый push до разрешения. Не обходить запрет новой веткой по догадке |
| Явно разрешён этот deploy в этой среде | Допустим обычный push выбранного диапазона после pre-submit; затем прочитать фактическое состояние среды и связь deployed result с отправленным SHA проектным способом |
| Deploy pending / unknown / failed | Сохранить этот отдельный статус и конкретный остаток; успешные push/CI его не заменяют |
| Проверка deploy | Не запускать развёртывание повторно ради наблюдения |
| Deploy успешен | Сообщить фактическую эксплуатационную активацию отдельно; acceptance не возникает |

Наблюдение: `push.md` прямо содержит все эти условия, включая проверку назначенной среды/отправленного SHA и запрет повторного развёртывания ради проверки. Шаблон сохраняет последствия отправки и необходимые разрешения. При первом чтении явное наблюдение deploy отсутствовало; вход исправлен и повторно прочитан до закрепления настоящего отчёта. Вывод: нормативный исход S3 подтверждён для хеша Push выше.

## HG-0063-S4: noGit и неизменяемый результат

Вход: Git не используется. Work и доступные проверки определены. Нативная приёмка при необходимости должна иметь неизменяемый проектный build/artifact ID.

| Вариант | Предписанное действие | Состояние решения |
|---|---|---|
| Проект назначил ID и способ хранения; проверки завершены | Завершить Work; передавать проверенный пакет по отдельно разрешённому проектному способу | Native result/accepted возможны только с точным ID, актуальными readiness/CAS/fingerprint и явным решением |
| ID ещё нет | Назвать пробел идентификации; честно сообщить выполненный Work и ограничения | Не записывать acceptance, не выдавать результат за опубликованный |
| Нет задачи создавать Git | Commit и Git-push неприменимы; не выполнять git init, не изобретать remote/release ID | Неприменимость Git не означает технический провал проверенной локальной работы |

Наблюдение: `commit.md` задаёт noGit-ветку до отбора Git-состава; `work.md`, «Передача человеку и фиксация решения», допускает Work без Git; `push.md` направляет пакет только в отдельный проектный маршрут. Шаблон хранит noGit ID/проверку/хранение и условия Work без commit. `specifications.md` допускает exact Git SHA **или build ID** и не снимает технический барьер. Формулировка Work «до коммита» при отсутствии ID не превращает Git в обязательный механизм: непосредственно перед ней задан noGit-маршрут. Вывод: нормативный исход S4 подтверждён.

## HG-0063-S5: native кандидат SHA1 и записи в SHA2

Вход: локальный кандидат разрешён; принятия человеком ещё нет; обязательные поздние проверки ожидаются.

| Этап | Предписанный переход | Источником доказанного результата остаётся |
|---|---|---|
| Pre-submit пройден, final CI pending | Создать выбранный commit SHA1, показать остаток; Work не завершён | Точный состав SHA1, без accepted/result/spec-integrate |
| Обязательные проверки закрыты | Сверить SHA1 с предъявленным составом и актуальность влияющих входов; передать result при readiness | Проверенная реализация SHA1 и её актуальные отпечатки |
| Пользователь явно принял показанный результат | Записать решение по действующим CAS/readiness/fingerprint с verified_revision=SHA1 | SHA1; решение не доказывает human observation сценария |
| Добавлены только записи result/acceptance | Включить их в следующий **разрешённый** metadata-only commit SHA2, не меняя реализацию | SHA1 не заменяется SHA2 задним числом |
| Metadata готовы до выбранного commit | Допустим один commit при совпадающем результате | Второй пустой commit не обязателен |
| В SHA2 изменились влияющие inputs/реализация | Повторить затронутую проверку; при существенном дрейфе новое решение | Нельзя выдать новую реализацию за прежнюю принятую |
| Пользователь говорит только «активируй» | Выполнять лишь разрешённую активацию с её барьерами | Acceptance не появляется |

Наблюдение: `commit.md`, «Решение пользователя», прямо фиксирует SHA1/SHA2, explicit acceptance, сохранение исторического verified_revision и текущих отпечатков. `work.md` требует ready+immutable ID для result и записи решения только по явному ответу. `specifications.md`, «Номера, версии и приёмка» и «Явные обращения к человеку», сохраняет CAS, текущий spec-check, change/inputs hashes и атомарное отклонение устаревшего пакета. Вывод: нормативный исход S5 подтверждён. Это вывод о норме, не утверждение о фактическом вызове spec-decide.

## HG-0063-S6: squash / rebase / merge меняют SHA

Вход: проверенный кандидат и итоговый SHA различаются; проект назначает способ сравнения деревьев/артефактов и значимых входов.

| Соответствие | Разрешённое использование доказательств | Граница решения человека |
|---|---|---|
| Эквивалентность установлена; inputs и проверки актуальны | Сохранить связь старой и новой редакций; переиспользовать эквивалентные доказательства и выполнить назначенный final CI нового SHA | Прежний verified_revision остаётся историческим; accepted подтверждается текущим spec-list |
| Значимый состав/inputs изменены | Новые затронутые проверки и явный остаток; существенное изменение требует нового решения | Старое принятие не копируется на новый результат |
| Соответствие неизвестно | Оставить пробел; не заявлять новый SHA проверенным | Номер PR, имя ветки или сообщение commit не являются доказательством |

Наблюдение: `commit.md` требует фактического сравнения и запрещает ручную замену verified_revision; `push.md` применяет это правило и местные final checks нового SHA. Шаблон хранит способ связи проверенного состава с результатом преобразования истории. Вывод: нормативный исход S6 подтверждён; неизменность ссылки/названия не подменяет идентичность.

## HG-0063-S7: Init → сохранённая адаптация → последующие этапы

Вход: новый либо ранее подключённый проект; документы/CI уже содержат часть ответов. Известные ответы не требуется подтверждать заново.

| Сведения | Где сохраняются / используются |
|---|---|
| Git или noGit, immutable result и хранение | Шаблон «Git и идентичность результата»; Commit выбирает соответствующую ветку, Work завершает noGit-результат |
| Remote, целевая ветка, PR base/head и обязательность PR | «Публикация через highgrade-push»; Push читает проектный маршрут до отправки |
| Pre-submit и final local/remote checks, ревью и ответственный | Отдельные поля «Pre-submit» / «Финальная готовность»; Commit не ждёт недоступного CI, Push возвращает pending/failed в Work |
| Назначение локальной активации, preview, проверка, восстановление | «Локальная фиксация… / Локальная активация»; Commit применяет только назначенный механизм из точного ID |
| Autodeploy/другие последствия и среда | «Последствия отправки»; Push проверяет разрешение эффекта и наблюдает результат |
| Кто принимает, разрешает merge/release/deploy | «Решения и полномочия»; успех commit/CI/активации не выдаётся за согласие |
| Squash/rebase/merge и идентичность | «Git и идентичность результата»; Commit/Push сохраняют историческую редакцию и сравнивают значимые входы |
| Поля известны из документа/CI/решения | Init переиспользует с источником; найденная команда не превращается в полномочие её выполнить |
| В старой адаптации поле неизвестно | Назвать конкретный upgrade gap и зависимый шаг, предложить минимальное согласованное дополнение; не переписывать местные правила молча |
| Неизвестен будущий remote | Ограничить будущий Push; не блокировать независимую локальную работу |

Наблюдение: `init.md`, «Подготовка репозитория», прямо ссылается на шаблон и перечисляет источники/поля/upgrade gap. Шаблон требует статус «определено» с источником, «неприменимо» с причиной либо «неизвестно» с зависимым действием. Commit читает местную инструкцию, Push — проектный маршрут. Ни шаблон, ни общие процедуры не назначают main, High Grade release ID или build-release всем проектам. Вывод: нормативный исход S7 подтверждён; schema-only совместимость сама по себе не доказывает полноту адаптации.

## HG-0031-S1: явная приёмка отдельно от активации

Общее исходное условие: выбранная область и точный готовый результат показаны вместе с проверками и существенным остатком. Варианты с дрейфом ниже меняют только актуальность снимка.

| Ответ / обстоятельство | Acceptance | Активация и human evidence |
|---|---|---|
| «Принимаю и активируй», точная текущая готовая редакция | Допустима запись без повторного вопроса, с действующими readiness/CAS/fingerprint | Отдельно разрешена названная активация; решение не является human observation |
| «Активируй», даже после показа готового результата | Не записывается | Разрешена только активация; успех проверяется отдельно |
| «Выполняй», согласование требований, вызов Commit/Push | Не записывается | Только соответствующая разрешённая работа; будущий результат ещё не принят |
| Обычная установка или пробная активация | Не записывается | Наблюдение установки не заменяет приёмку спеки |
| Явное принятие, но снимок/inputs устарели | Старое решение не переносится; stale сохраняет историю, требуется актуальный результат и решение при существенном изменении | Активация не исправляет несовпадение доказательств |
| Приёмка записана, затем активация упала | Прежнее решение не отменяется одним сбоем активации, если сама принятая редакция не изменилась | Commit сохраняется; фактический сбой/состояние/восстановление сообщаются отдельно |

Наблюдение: `commit.md`, «Решение пользователя» и «Проектная активация», содержит эти различия; `work.md` запрещает вывод приёмки из молчания, тестов, ревью или плана. Шаблон повторяет узкую границу «активируй» без acceptance. Справочник CLI сохраняет требование текущего spec-check и отпечатков. Вывод: нормативный исход HG-0031-S1 подтверждён.

Исходный контракт берётся из операции HG-0048-R2 нового HG-0063; исторические результаты прежнего изменения не используются как новое подтверждение. Сценарий сопоставляет локальную работу без передачи с явно согласованной передачей и требует проверять фактический состав лишь для последней. Переименованный этап рассматривается как canonical Commit, без восстановления отдельного Approve-маршрута.

Влияющие входы этого дополнения: `kit/procedures/init.md`, `kit/procedures/work.md`, `kit/procedures/commit.md`, `kit/procedures/push.md` с уже закреплёнными выше хешами, а также:

| Исходные условия | Наблюдаемое нормативное правило | Предписанный итог |
|---|---|---|
| Локальная проверенная работа; передачи/commit/push не поручены | Work, «Сохранность результата при передаче», прямо запрещает создавать новый delivery-барьер без поручения; diagnostics называет проверку состава необязательной для локальной работы без передачи | Локальный результат можно завершить/показать при его собственных критериях; нет навязанных commit, upload, remote, сборника всех логов или проверки ещё не существующего внешнего пакета |
| Init готовит адаптацию будущего проекта | Init, «Обследование», выясняет владельца, место, срок хранения и способ передачи обязательных доказательств у существующего подходящего владельца | Нужные условия известны заранее; новый обязательный реестр не навязывается, обследование не разрешает upload |
| Поручена конкретная передача | Work согласует минимальные обязательные отчёты/невосстановимые входы и сверяет выбранный состав, включая untracked/ignored материалы, по diagnostics | Наличие локального файла не выдаётся за включение в выбранный пакет; проверяется реальный состав |
| Выбран Git commit | Commit, «Состав и барьер коммита», сверяет обязательные spec/results/отчёты/невосстановимые inputs с выбранным индексом; diagnostics проверяет реальные index blobs и хеши | Только нужные доказательства включаются с выбранным составом, посторонние файлы сохраняются; одна запись пути не подтверждает передачу правильных байтов |
| Поручен Push диапазона | Push проверяет обязательные доказательства в отправляемых SHA и сверяет остаток рабочего дерева | Нельзя считать отправленным доказательство, оставшееся только в рабочем каталоге |
| Передаётся noGit-пакет | diagnostics принимает явный files.json, проверяет выбранные текущие файлы/хеши; одного списка недостаточно для immutable ID | Не возникает фиктивный Git; состав пакета и неизменяемая идентичность проверяются отдельно |
| Обязательный файл отсутствует либо хеш отличается | diagnostics задаёт failed; исключённый файл/неизвестный состав дают unknown | Передача не подтверждается; неизвестное не становится passed |
| Доказательство находится по внешней ссылке | Work/diagnostics требуют местной проверки доступности и хранения; URL сам по себе недостаточен | Автоматическая загрузка не назначается; существование будущей копии не утверждается |
| Delivery check успешен | Work/diagnostics отделяют проверку состава от spec-check и человеческого решения | Не возникает technical ready или acceptance только из успешной проверки доставки |

Нормативная цепочка замкнута: Init сохраняет существующий способ хранения → Work готовит минимальные доказательства и проверяет только порученную передачу → Commit сверяет индекс → Push сверяет отправляемые SHA. Общие процедуры ссылаются на один диагностический владелец, не копируют его контракт в новый реестр.

Вывод: нормативный HG-0048-S2 подтверждён на перечисленных входах; обязательность проверки фактического состава не распространена на локальную работу без порученной передачи. Это содержательная проверка правил. Реальный Git index/bundle/remote здесь не проверялся; runtime-доказательство исполняемого delivery-check принадлежит отдельным контрактным тестам. Новая пользовательская приёмка не записывалась.
