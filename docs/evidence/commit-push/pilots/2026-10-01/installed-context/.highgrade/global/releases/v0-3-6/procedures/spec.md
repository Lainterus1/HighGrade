# Подготовка спецификации

Когда требуется решение по подготовленному содержанию, создай явное обращение `requirements` через [spec-attention](../references/tools/specifications.md#явные-обращения-к-человеку). Не превращай каждый черновик или stale в запрос человеку. Согласование сохраняет снимок содержания и не является разрешением реализации. При уже данном разрешении отдельное согласование не навязывается.

Применяй общие правила языка и контекста из rules.md.

Возьми согласованное описание результата или эквивалентное явное поручение. Прочитай AGENTS, проектную инструкцию и относящиеся к задаче требования. Найди затронутые компоненты целевым поиском. Сначала проверь основание по [task](task.md#выбор-достаточного-маршрута): новый или изменённый контракт либо явно порученная формализация. Для технической работы и восстановления описанного поведения новый change не нужен. Для нового изменения используй установленный CLI High Grade и нативный JSON; команды и форматы — в [справочнике](../references/tools/specifications.md#структурированные-спецификации). Если проект явно сохраняет старый маршрут OpenSpec, следуй ему до согласованного перехода. Наличие старых файлов само по себе не назначает новый маршрут.

Начни с выборочного `spec-list` и относящихся требований, затем создай `spec-new --title TITLE` с полученным store_sha256. Номер назначает CLI. Получи `spec-read --view editable`, заполни цель, основание, границы, вопросы, конкретные задачи и операции; передай только изменённые поля через `spec-edit` с CAS прочитанного снимка. Для modify/remove сначала прочитай текущее требование: CLI сам фиксирует его базу. При конфликте перечитай и сопоставь чужие правки. Полный вывод и spec-save нужны при соответствующей необходимости, не для каждого сохранения. Каталог напрямую не редактируй; сохраняй ID при редактуре. Миграция старого формата выполняется явно по согласованному переходу.

Выбери теги из spec-tags по предметной области задачи, обычно 1–3 без обязательной квоты. Не добавляй verification или documentation лишь потому, что у реализации есть тесты и документы. При недостающей устойчивой области дополни словарь с понятным описанием; не создавай теги статусов, дат и отдельных задач. Для старых интегрированных спек используй отдельный preview/apply метаданных. Причины depends_on/related_to указывай по реальной зависимости, без наследования текста.

Каждая задача описывает конкретный результат, например «Отклонять весь пакет при неизвестном теге», а не универсальный этап «реализовать и проверить». Не переписывай завершённые исторические задачи ради нового оформления.

## Контракт сценария

Требование объясняет нужное поведение, сценарий показывает конкретный пример. Запиши исходные условия, одно значимое действие, наблюдаемый результат и существенные ограничения или запрещённые последствия. Ожидание выводится из согласованного правила до реализации; оно должно отличать правильную реализацию от нарушения. Детали тестового раннера не становятся продуктовым требованием. Проверка наличия файла не доказывает поведение его содержимого.

Выделяй отдельный сценарий для отличающегося наблюдаемого исхода или существенного риска, а не для повторения того же ожидания другими словами. Фиксированной квоты нет: все обязательные исходы должны иметь доказательство. Один фактический прогон может покрывать несколько сценариев, если результат каждого наблюдается и записывается отдельно; проверка текста инструкции не подтверждает действия агента.

Примеры формы, не готовые требования подключаемого проекта:

- Обычное приложение: сохранён валидный каталог; пользователь передаёт запись без обязательного названия; операция возвращает ошибку, прежний каталог не меняется. Проверка вызывает настоящую операцию сохранения и наблюдает состояние.
- Событийный процесс: получены факты о запасе и резерве; поступает запрос резервирования; проверяются ответ и новые факты. Повтор запроса проверяется на отсутствие двойного резерва только если идемпотентность входит в контракт.
- Процедура агента: задача и область записи разрешены, рядом есть чужой файл; агент выполняет задачу; результат достигнут, чужой файл сохранён, непроведённая проверка не объявлена успешной. Наблюдаются реальные действия и файлы, а не совпадение текста ответа.

Для каждого нового или изменённого сценария выбери способ доказательства по [матрице work](work.md#содержательные-проверки): штатный тест, непосредственное наблюдение либо смысловая сверка нормативного содержания. Смысловая сверка подтверждает только содержание правила; утверждение о фактическом исполнении требует наблюдения. При выборе проверки определи, как воспроизводимо подготовить исходное состояние, выполнить действие и наблюдать результат. Укажи команду/тест или наблюдение и проверяемый исход. Поддержка отчёта в trace — свойство инструмента, не критерий допустимости теста. Выбор проверки ещё не доказывает выполнение.

Выполни `spec-validate`: он проверяет наполненность контракта, но не выполнение задач или тестов. Пустой шаблон остаётся черновиком. Проверь смысл: ожидание выводится из согласованного правила, а не из текущей реализации; не подгоняй требование под ошибку. При готовом контракте и имеющемся разрешении переходи в work без нового формального согласования.

Исторические Markdown/OpenSpec доступны по сохранённым в проекте путям. Выборочный перенос требует явного поручения: `spec-import` создаёт черновик, сохраняет исходный текст и сверяет сценарные ID. Агент и независимое ревью проверяют эквивалентность. Если поведение подтверждено сценарными доказательствами, `spec-integrate` переводит владение в JSON. Если задача состоит только в переносе прежнего контракта, `spec-transfer` после завершённой сверки и свежего GO закрепляет требование и происхождение без ложного PASS: техническая готовность остаётся открытой до проверок. Исходный файл сохраняется как история, другие требования в нём остаются действующими. Не поддерживай две редактируемые версии одного требования.

Для проверки заполни checks, если проект использует их: сценарии, файл теста, точный selector и настроенный runner либо ручной способ, подготовку, действие, наблюдение и значимые входы. shared_inputs сокращает повторы общих входов. Форматы — в [справочнике проверок](../references/tools/verification.md). Повтор неизменённой интегрированной спеки обновляет results; новый change нужен для изменения требований или нормативных сценариев.

## Начальная проработка при init

Полный init нового проекта сохраняет начальные спеки ближайших результатов по [маршруту init](init.md#начальные-спецификации). Укажи цель, границы, известные требования и конкретные tasks в логичном порядке; открытые вопросы храни в questions. Не записывай предположение как согласованное правило. Для последующих результатов достаточно меньшей глубины, но пустой шаблон без предметного содержания не является подготовкой.

Черновик сохраняется через spec-edit с CAS; необязательный --validate true используй для заполненного контракта. Выполни spec-validate и объясни относящиеся к незавершённой проработке пробелы, не объявляя успех. Различай неполноту требований и повреждение данных: неверный формат/путь нужно исправить. Успех spec-validate подтверждает структуру, а не достаточность требований; вопросы и смысл сверяются отдельно. Spec-check оценивает выполнение, поэтому его ready не является барьером завершения init.

При следующем запросе task/spec перечитывают и уточняют тот же неинтегрированный ID; выполненный контракт меняется новым change по общим правилам. До work должны быть определены требования и проверки выбранной работы и разрешены её существенные вопросы. Рекомендуемый порядок спек не равен depends_on; связи отражают необходимые результаты. Источник задач — сами спеки, без второго backlog в survey.
