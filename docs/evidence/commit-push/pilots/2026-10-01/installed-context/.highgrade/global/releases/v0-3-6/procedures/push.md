# Отправка выбранных коммитов

Запускай по явному поручению `highgrade-push`. Прочитай проектный маршрут: remote, целевая ветка отправки, base-ветка/обязательность PR, pre-submit и финальные барьеры. Установи непрерывный диапазон локальных коммитов; он может содержать несколько задач. Если диапазон, цель и последствия уже однозначно разрешены, не переспрашивай. Иначе покажи конкретный пакет, цель и существенные последствия до отправки. Без Git этот маршрут неприменим; передачу неизменяемого пакета выполняй только по отдельному проектному способу и поручению.

Сверь каждый коммит с источником задачи, локальной фиксацией, происхождением, лицензией и отсутствием закрытых данных. Сообщение коммита само по себе не доказывает принадлежность. Проверь файлы и обязательные spec/results/доказательства именно в отправляемых SHA по [правилам передачи](../references/tools/diagnostics.md#состав-передачи-доказательств). Сверь git status с порученным составом: нужные файлы не должны оставаться только в рабочем дереве; посторонние сохраняй и называй в итоге. Неизвестный коммит останавливает диапазон.

## Отправка кандидата и возврат в Work

После выполненных pre-submit-проверок разрешён отдельно порученный push кандидата для удалённого CI/PR до финальной технической готовности. Для нативной спеки переиспользуй `spec-check --brief true`; pending/failed из-за ещё недоступного финального наблюдения остаётся явным пробелом. Не объявляй требования интегрированными или результат принятым ради отправки. Не повторяй успешные локальные проверки без изменения входов или нового риска; упавшие обязательные pre-submit-проверки сначала верни в Work.

Проверь актуальное состояние удалённой ветки и правила проекта. Push не разрешает PR, merge, тег, release или deployment автоматически: выполни только явно включённые в поручение действия. Если отправка сама запускает автодеплой или другое существенное внешнее действие, до push раскрой его и проверь разрешение на этот эффект, включая среду; без него останови зависимую отправку, не обходи правило новой веткой по догадке. После разрешённого автодеплоя проверь фактическое состояние назначенной среды и связь развёрнутого результата с отправленным SHA по проектному механизму; pending/unknown/failed назови явно. Не запускай развёртывание повторно ради проверки. Для PR сверь base/head и применимый проектный маршрут; push в ветку не доказывает наличие PR или его принятие.

Выполни обычный push без force по умолчанию. Проверь удалённый SHA выбранной ветки и результаты CI для этого точного коммита, когда они доступны. Если CI ожидается, падает, относится к другому SHA либо требует доработки, верни задачу в Work с конкретным остатком и следующим шагом. Исправления требуют новых актуальных проверок и разрешённых Commit/Push в пределах поручения. Ни публикация, ни зелёный CI сами по себе не завершают остальные финальные критерии. Завершай Work и вызывай spec-integrate/передачу result лишь после их настоящих барьеров.

При squash/rebase/merge применяй [правило идентичности результата](commit.md#решение-пользователя) и местные финальные проверки нового SHA. Push не меняет `verified_revision` и не переносит человеческое решение на изменённый состав. Merge и выпуск остаются отдельными разрешёнными действиями.

Сообщи диапазон/задачи, цель и удалённый SHA, статус PR/CI и существенный остаток; отдельно — локальную/удалённую активацию и приёмку. Push не делает новый коммит, в том числе ради закрытия Planner. При сбое коммиты остаются локальными; успешная публикация не означает локальной активации или человеческой приёмки.
