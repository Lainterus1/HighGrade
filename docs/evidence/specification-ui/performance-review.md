# Быстродействие интерфейса

Проверена текущая локальная сборка, проект MyCodex. Изменены только frontend и документирование; API/CLI-схемы и механизм CAS сохранены.

## Результаты ревью

1. Общая очередь API удерживала новый выбор за уже ненужным чтением. Теперь смена выбора и размонтирование отменяют прежнее чтение, а очередь и задержка StoreBusy учитывают отмену. Записи не отменяются и не повторяются автоматически. Проверка serial продолжает исключать устаревшие результаты.
2. Редактор глубоко копировал поля базы на каждый render и сериализовал неизменённые структуры. Теперь поля разделяют неизменяемые ссылки, базовый набор и patch мемоизированы, идентичные поля пропускают сериализацию. Обновления редактора остаются immutable; сравнение содержимого сохраняет возможность вернуть поле к прежнему значению.
3. Фильтры, сортировка и темы мемоизированы. Поисковая строка нормализуется один раз за пересчёт.

## Измерения и границы

- Живой GET списка:1042–1295ms,42110bytes. Чтение HG0051:668ms,334078bytes; HG0052:674ms,891330bytes. Это разовые локальные измерения, неp95.
- Контролируемый браузерный сценарий: B задержан на3000ms; пользователь выбирает C. До5769ms, после1389ms (~76% меньше). Тот же проект и скрипт; новая сборка замерялась параллельно с тестами.
- Первое открытие3566→4599ms: улучшение запуска не доказано, условия нагрузки различались. Нельзя приписывать ускорение всего приложения результату переключения.
- JS340.97→341.50kB, gzip107.11→107.30kB. Размер практически прежний, новых зависимостей нет. Отмена сетевого ожидания не гарантирует остановку уже начатой серверной работы.

## Следующие направления

- Основная нагрузка ответа HG0052 — история:~392kB из~456kB change при повторной JSON-сериализации. Карточка её не показывает. Отдельная компактная read-модель может уменьшить передачу/разбор/память, но должна сохранить hashes, конфликты и полный путь редактирования; вырезать поля общего контракта без отдельной проверки нельзя.
- Сервер повторно читает каталог и хеширует доказательства. Межзапросный cache может пропустить внешнее изменение файла; не введён. Следующий шаг — профилировать повторы внутри одного чтения с сохранением проверки свежести.
- Poll раз в10s при видимой странице и на focus остаётся. Отдельный дешёвый endpoint актуальности требует контрактной проверки изменений evidence, а не только каталога.
- Разделение JS на чанки пока не введено: общий runtime React/Radix необходим и чтению, редактор мал; дополнительный запрос может ухудшить первое действие.
