# Оптимизация редактора UI

Область: техническая оптимизация существующего контракта HG-0058 и оформления Editorial HG-0067. Новые поля, действия, требования или временные SLA не вводятся. Выполнение поручено пользователем 2026-10-02.

Изменение: SpecEditor пропускает рендер неизменённых требований через React.memo, сохраняет стабильный callback с functional state update и сравнивает только изменённые элементы массива. Разметка, CSS, API, CAS, очередь записей и фоновые проверки сохранены.

## Методика

`ui/benchmarks/playwright.config.ts`, `performance.ts`: Chromium, 1440×900, production Vite bundle внутри debug CLI; Linux, один worker. Обычный каталог — 7 спецификаций / 3 требования; большой — 250 / 3; длинный документ — 7 / 160. Подготовка меняет только временный fixture. Хеш каталога до/после и отсутствие POST проверяются автоматически.

На сценарий: 7 чтений API и первых открытий с очищенным browser cache; 20 переключений и поисков; 25 вводов; один интервал покоя 11 с. API включает localhost транспорт, действия — Playwright и ожидания кадров. inputTask — разность CDP TaskDuration на нажатие End+x и два RAF, а не чистое время React. Историческое имя inputToPaint означает input → callback следующего RAF, не доказанное отображение пикселей. Idle — единичное наблюдение, не надёжный percentile. Замеры не являются SLA и не доказывают ускорение всего приложения.

Команда из ui: `HIGHGRADE_PERF_OUTPUT=../docs/evidence/ui-performance/<attempt> HIGHGRADE_TEST_EXE=<binary> npx playwright test --config benchmarks/playwright.config.ts`. Исходная копия бинарника — target/highgrade/tmp/ui-performance/before-highgrade; финальная — target/debug/highgrade. before и before-repeat — исходный код, after — промежуточная memo-оптимизация, final — итоговая реализация. Первоначальная попытка большого каталога остановилась на отсутствующем optional results.json в fixture; исправлена подготовка, исходные успешные замеры сохранены. Запуск браузера требует разрешения sandbox.

## Результат замеров

В длинном документе inputTask: исходные медианы 11,869 и 10,562 мс, итог 8,202 мс (снижение 22–31%). p95: 22,750 / 14,343 → 14,147 мс; разброс исходных прогонов не позволяет заявить устойчивое крупное улучшение p95. Обычная форма: 4,245 / 4,314 → 4,055 мс. Большой каталог: 4,606 / 4,313 → 5,082 мс, p95 6,211 / 6,126 → 6,089 мс; ускорение для этого случая не заявляется.

| Медиана, мс | Обычный до/после | 250 спецификаций до/после | 160 требований до/после |
|---|---|---|---|
| Первое открытие | 89,4 / 90,1 | 845,4 / 847,2 | 138,6 / 138,6 |
| Переключение | 100,0 / 99,9 | 300,0 / 300,0 | 177,7 / 182,9 |
| Поиск | 33,3 / 33,3 | 33,9 / 33,4 | 33,3 / 33,3 |

Таблица использует before-repeat/final. Запуск, навигация и поиск практически не изменились; оптимизация адресована работе с длинным черновиком. На 250 спецификациях чтение списка API занимает около 244/241 мс, документа — 185/184 мс: дальнейшее ускорение загрузки потребует отдельной работы с чтением каталога. Backend в этой задаче сохранён. Интервалы покоя 11 секунд не показали фоновых записей; отсутствие изменений каталога проверено хешами.

Снимок обычной формы до/после совпал побайтно (`visual-comparison.json`), итоговый CSS совпал (`identity.json`). Это узкое визуальное доказательство, дополненное общими проверками интерфейса; оно не доказывает совпадение всех возможных состояний.
