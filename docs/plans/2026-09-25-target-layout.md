# План: управляемый каталог `target/`

Версия: 4. Публикация и локальная активация включены по поручению автора; release ID назначается до сборки кандидата.

Цель: оставить в корне `target/` только штатные файлы и каталоги Cargo/nextest и один каталог `highgrade/` для файлов Проекта; очистить прежний временный мусор и ограничить повторный рост без потери кандидата выпуска и доказательств.

Область: этот Проект, его инструкции и локальные скрипты. Правила и файлы Поставки `kit/` не меняются, кроме release ID/версии манифеста, необходимых для локальной активации нового бинарника; подключённые проекты не меняются. `target/` остаётся игнорируемым и воспроизводимым; постоянное описание структуры принадлежит `docs/BUILD.md`. После проверки разрешены локальное утверждение задачи с активацией Поставки из её точного SHA и отправка выбранного диапазона в `origin/main` штатным маршрутом.

## Этапы

1. **T1 — Контракт и инвентаризация.** Зафиксировать исходный размер, владельцев путей, ссылки на результаты и исключения. Создать одно нативное изменение требований для устойчивого правила структуры и безопасной очистки.
2. **T2 — Новая раскладка.** Перенести проектные результаты в `target/highgrade/{build-cache,candidate,reports,tools,work,tmp}`; оставить нативные `debug/`, `release/`, `nextest/` и файлы Cargo на верхнем уровне. Обновить скрипт выпуска, тесты, команды и документацию. Временные пробы создавать только в `target/highgrade/tmp/<запуск>` и убирать после завершения.
3. **T3 — Обслуживание и разовая очистка.** Добавить небольшую команду просмотра/применения с явным списком путей, защитой от reparse points, работающих сборок, неизвестных файлов и кандидата. Проверить ссылки на текущие доказательства и убрать старые временные результаты. Штатно очистить устаревший `debug` и обычный `release`; кэш кандидатов очищать только отдельным осознанным действием. Ориентир после обслуживания — не более 600 МиБ, превышение без безопасной очистки сообщать явно.
4. **T4 — Проверка и ревью.** Проверить негативные сценарии очистки на временной фикстуре, жизненный цикл сборки кандидата из точного SHA, согласованность команд и документов, отсутствие лишних файлов в корне, итоговый размер и независимое ревью изменений.
5. **T5 — Утверждение, активация и публикация.** До коммита с порученной активацией назначить новый release ID и согласовать версии Cargo/манифеста/тестов. После положительных проверок выполнить `highgrade-approve`: зафиксировать только относящиеся к задаче файлы и собрать кандидат из созданного коммита. Проверить `global-status`, выполнить preview/apply новым ID с одним `candidate_sha256`, затем `highgrade-push` для выбранного диапазона без force и сверить удалённый SHA и CI. При уже активном ID не перезаписывать выпуск: сравнить состав по процедуре Update и устранить конфликт новым ID. Человеческое решение по точной версии спеки не выдумывать.

## Критерии готовности

- **A1:** один документированный владелец каждого допустимого пути; корень `target/` не содержит пользовательских проб и неизвестных файлов.
- **A2:** кандидат, его аварийная копия и активная сборка не удаляются обслуживанием; ссылка/junction за пределы корня отвергается.
- **A3:** значимые доказательства сохранены вне `target/`, старый мусор очищен без изменения посторонних данных.
- **A4:** сценарий точного SHA и штатные проверки после переноса работают; размер после обслуживания измерен и находится в бюджете либо обоснованно обозначен как исключение.
- **A5:** локальный коммит задачи, активация из его SHA, обычный push и удалённый SHA подтверждены отдельно; состояние CI сообщено по факту.

Разрешена локальная очистка только подтверждённых временных файлов внутри `target/`. Не затрагивать чужие изменения, другие проекты и плагины.
