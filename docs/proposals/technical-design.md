# High Grade: техническая схема первого выпуска

Дата: 2026-09-23. Статус: проектная схема и ранее обсуждавшиеся гипотезы, не нормативное описание текущего кода. Реализованные форматы и пределы заданы [контрактами P0–P2](../implementation/p0-p2-contract.md) и [P3–P5](../implementation/p3-p5-contract.md); локальная проверка — в [отчёте кандидата](../reviews/p3-p6-candidate-review.md). [SPECIFICATION](../workflow/SPECIFICATION.md) и [CONTEXT](../workflow/CONTEXT.md) задают поведение; [TOOLING](TOOLING.md) — обязанности; [план](../plans/first-release.md) — последовательность P0–P6. Пилоты P6b ещё не проведены.

## 1. Архитектура и источники

```text
Автор -> запрос и проектные решения -> агент Codex
          |                            |
          v                            +-> init / work / refresh / update
  адаптация целевого проекта           |       |
          |                            |       +-> Rust CLI: doctor / inspect / trace / install-update
          +-> документы и OpenSpec <----+       |         |
          |                            |       |         +-> структурные отчёты и ошибки
          +-> ID сценариев <-> отметки тестов   |
                                       +-> штатные тестовые команды -> исходные отчёты

High Grade (исходники) -- явное получение/локальная сборка --> выбранная основа в проекте
                                                          + отдельная адаптация
```

Нет серверной платформы, собственного LLM API, фонового мониторинга, управления соседями или обязательного gstack. Сам Codex и сетевые команды могут требовать сеть; локальная основа High Grade не требует связи с авторским репозиторием при повседневной работе. Общий Rust CLI не меняет языки целевых проектов. OpenSpec остаётся внешней зависимостью; Rust сам по себе не устраняет его runtime.

Механизмы проектных навыков Codex и OpenSpec 1.13.1 проверены в границах отчёта кандидата. `.agents/skills` и имена highgrade-* обнаружены backend Codex app/CLI; полный GUI-прогон остаётся частью пилотов. Глобальные инструменты пользователя не менялись.

## 2. Владение файлами и контрактами

```text
project/
  README.md, AGENTS.md
  docs/ARCHITECTURE.md, ENGINEERING.md, DEVELOPMENT.md
  openspec/                         поведение и задачи изменений
  .agents/skills/highgrade-*/        четыре проектных навыка
  .highgrade/                       фактический состав в контрактах реализации
    releases/<id>/                  выбранная общая основа, без проектных правок
    active.json                     выбор проверенной основы
    project/                        настройки, роли документов, бюджеты, пробелы
    state/                          только ссылка на основной план и точка продолжения
    feedback/                       ошибки workflow, без автоматического экспорта
    local/                          тяжёлая диагностика, вне Git
    transactions/                   восстановление незавершённых изменений установки
```

Схема — карта ответственности, не обязанность создать каждую папку. Пути адаптируются к режиму WF-INIT-02. Доказательства значимых задач находятся рядом с их материалами по WF-EVIDENCE-02; отдельного параллельного хранилища evidence не вводим. ADR создаётся при долговременном решении, а не ради пустого каталога. Реальный реестр разработки пока `.mycodex/project/documents.json`; это не выполненная миграция в `.highgrade`.

| Запись | Минимальный смысл | Что не дублирует |
|---|---|---|
| Настройки проекта | Корень, области, пути, выбранные режимы, ссылки на команды/источники | Тексты всех инженерных правил |
| Реестр документов | ID, роль, область, режим чтения, связи, бюджет/база/потолок, основание и пересмотр | Содержимое документов |
| Пробелы | ID сценария, согласование, причина, исходное состояние | Разрешение игнорировать будущие падения |
| Состояние задачи | Ссылка на источник задач, стадия, один Next, блокер и доказательства | Второй список задач OpenSpec |
| Запуск проверки | Команда, область, фактическое состояние кода, время, инструмент, ссылка на исходный отчёт | Подробный универсальный отчёт всех тестов |
| Результат trace | Производные связи, статусы и ограничения | Ручной реестр связей или новая спецификация |
| Обратная связь | Процедура/поставка, ожидание, факт, доказательство, причина либо гипотеза, исправление | Телеметрия, автоматический GitHub issue |

JSON — рабочий кандидат для машинных записей, Markdown — для человеческих документов. Точные схемы, ограничения размера и правила ошибок выбираются в P0. Неизвестный бюджет остаётся not-agreed; отсутствующая область не становится успешно проверенной. Временный обход хранится у исходной задачи с причиной, проверкой и условием удаления; архивирование задачи не должно скрыть незавершённое обязательство.

## 3. Инициализация, подключение и приёмка

```text
готовый проект -> полный аудит применимой области -> интервью / выборы A-B и Git
               -> согласованное устройство и один план
               -> [поручение выполнять] -> подключение / адаптация / проверки / ревью
               -> готово к приёмке -> [явное принятие] -> обычная продуктовая работа

новый проект -> интервью -> устройство и план -> [поручение] -> выполнение и проверки
```

Средство проведения аудита/интервью может быть предоставлено до подключения, но это не активация полного workflow в проекте. Полный аудит по WF-INIT-01 предшествует подключению существующего проекта; неполнота чтения/проверок явно видна. Нет автоматического сканирования соседних репозиториев. Сохранение промежуточных ответов и одного Next позволяет продолжить интервью; новые изменения в проекте требуют актуализировать затронутые наблюдения.

Выбор документации A/B и политики Git фиксируется в адаптации, не навязывается. В обоих режимах нужны пять ролей, отсутствие противоречий и сохранение полезного содержания. Сначала завершается адаптация; разрешены необходимые срочные исправления. Техническая готовность не равна приёмке пользователя. Молчание, самопроверка вместо обязательного ревью и общий exit 0 не переводят состояние в принятое. Правило приёмки первоначальной адаптации не добавляется к каждой обычной задаче.

Установка изменяет только заранее выбранные файлы. Существующий AGENTS не перезаписывается шаблоном; конфликт рассматривается по смыслу. Совпадение имени чужого навыка не даёт права его заменить. Для прерывания нужны сохранённые исходники и запись операции; неполное подключение выдаёт конкретный статус. Повтор операции не плодит копии. Восстановление касается только собственных изменений с проверкой последующих чужих правок.

## 4. Данные и ошибки чтения

```text
корень + область + источники -> валидация -> измерение/извлечение -> производный отчёт
  нет входа ----------------> unknown: указать недостающий источник
  пустой вход --------------> отличить допустимую пустоту от отсутствия тестов/требований
  плохой формат/ссылка ------> конкретная ошибка с путём; не частичный PASS
  чтение/процесс прерван ----> неполная область и ограничения; старые данные не выдавать за новые
  входы изменились ---------> отчёт относится к старому состоянию; повтор затронутой проверки
```

Doctor/inspect/trace — чтение. Штатные команды тестирования запускает агент напрямую, никакой общий verify не возвращается. Отчёт операции должен различать измерения, проверенные условия, предупреждения, ошибки и неизвестное, указывать область и входы. Машинный отчёт и его краткое человеческое представление не являются двумя источниками истины. Смысловую согласованность оценивает агент с указанием области; CLI её не гарантирует.

| Путь / класс сбоя (логическое имя, не готовый Rust тип) | Восстановление | Пользователь видит |
|---|---|---|
| DependencyMissing / ConfigInvalid | Остановить зависимую операцию; не устанавливать молча | Компонент/путь, причина, что нужно для повторения |
| InputUnreadable / EmptyRequiredInput | Отчёт partial/unknown либо нарушение условия | Что не прочитано или отсутствует; нет общего PASS |
| TraceReferenceInvalid / ReportMalformed | Исправить источник в разрешённых границах; повторить trace | ID/тест/отчёт и отсутствие подтверждения |
| EvidenceStale / ImpactUnknown | Повтор подходящих проверок; не подменять старый успех падением | Исторический результат и неподтверждённое новое состояние |
| BudgetExceeded | Пересмотр по диапазону, без автоматического повышения потолка | Размер, метод, диапазон и причина предупреждения |
| SemanticConflict / ReviewUnavailable | Только зависимая работа ожидает решения/ревью | Конкретные положения и ограничения, не «всё готово» |
| ArchiveInterrupted / DestinationConflict | Проверить факт переноса; восстановить своё без перезаписи чужого | Незавершённость, сохранённые файлы, конфликт |
| CandidateIncompatible / PostcheckFailed | Не активировать либо вернуть прежнюю основу | Кандидат не принят, прежняя работоспособность проверяется |
| ConcurrentChange / PathOutsideRoot / FileBusy | Отказ от опасной записи; проверить состояние перед продолжением | Затронутые пути и восстановимая точка остановки |

Никаких молчаливых fallback на другую установку, общих catch-and-pass или бесконечных повторов. Повтор изменяющей операции начинается с проверки фактического состояния. Контекст диагностики достаточен для воспроизведения, но секреты и транскрипты пользователя не копируются в логи.

## 5. Тесты, контекст и штатный цикл

```text
порученная задача -> применимые требования/контекст -> работа и native проверки
 -> документы + размеры/ссылки + временные обходы + архив
 -> ревью по риску -> повтор затронутого -> доказательства / Next
```

Связи: OpenSpec-ID → отметка рядом с тестом → идентичность конкретного теста в инвентаре/отчёте → фактический результат. Дубликаты/удаление ID, параметризация, пропуски и повторные попытки входят в P4. Исходный отчёт не подменяется пересказом агента; ссылка не доказывает выполнение. Изменённый сценарий теряет автоматическое применение старого исключения. Covers и полный единый отчёт не нужны для первого выпуска.

Подтверждение относится к проверенному коду, тестам и существенным зависимостям, включая незакоммиченные изменения. Один commit SHA без учёта рабочего дерева недостаточен. Неизвестное влияние требует перепроверки; точный способ снимка/отпечатка — P0/P4. Семантическая правильность проверки отдельно оценивается при ревью.

Inspect измеряет байты/строки и токены либо явно помеченную оценку, связи и маршруты. Точный алгоритм оценки выбирается технически; он не притворяется полным окном Codex. Контролируются отдельные документы и совокупность читаемого контекста, накопленный рост, новая область, устаревшее свидетельство обзора. Начальный бюджет согласуется автором, затем проверяется на задачах. Размер сам по себе не доказывает опасность или безопасность.

Refresh повторно использует аудит; analysis-only действительно не пишет. Штатная актуализация документов, архив и обходы не ждут refresh. Тяжёлые файлы локальные, видео выключено; история значимых проверок сохраняется с задачей. Обратная связь извлекается вручную, без автоматической отправки в High Grade.

## 6. Архив и добровольное обновление

Архивирует агент; CLI проверяет структуру/ссылки. Завершённое OpenSpec-изменение обрабатывается штатным механизмом выбранной версии, который нужно проверить до применения; отвергнутая гипотеза не идёт по пути применения дельты. ADR при замене может сохранить путь со статусом и ссылкой. Удаление функциональности не разрешается переносом документа.

```text
старая рабочая основа
 -> явно выбранный кандидат -> проверка форматов, целостности и смысла
 -> проверки кандидата без изменения повседневного выбора
 -> повторная проверка исходного состояния -> переключение -> постпроверка
       | конфликт/сбой до переключения                 | сбой после
       +-> старая основа остаётся                      +-> восстановить старую
```

Потенциальный механизм: неизменяемые локальные поставки, небольшой указатель выбора, журнал и сохранённые исходники. Это кандидат реализации требований D16/D20/D21, а не разрешение гарантировать атомарность по одному переименованию файла. Кандидат не активируется при несовместимости смысла, даже если формат совпадает. Адаптация не переписывается молча; её согласованное преобразование — отдельная проверяемая работа. Контрольная сумма подтверждает целостность относительно manifest, а не доверенность неизвестного источника.

```text
операция U: прочитала входы --- проверила кандидата --- пытается переключить
операция W:                 изменила адаптацию
проверка:                  хеши различаются -> U не активирует кандидат

операция U: переключила и проверила -> W начинает новую разрешённую работу
проверка: новая работа использует подтверждённую основу; старый контекст не подменяется молча
```

Для своих изменяющих операций предлагается локальная блокировка и журнал, при update — отсутствие активной работы в проекте. Внешний редактор не обязан соблюдать блокировку: строгая транзакция с произвольным несотрудничающим процессом не обещается. P5 обязан проверить оба порядка завершения, обрыв до/после переключения, неудачный откат и чужие изменения; глобальный git reset запрещён. Старый пакет не удаляется при update, активная задача держит исходную поставку, а новый сеанс явно получает новую. Несовместимые входы навыков/загрузчика требуют отдельного плана, не скрытой замены.

## 7. Проверка путей, масштаба и переносимости

Входные файлы, отчёты и содержимое проекта — данные, а не источник новых полномочий. Команды не склеиваются из пользовательских строк. Корень задаётся явно/определяется из проверенного входа, соседние проекты не обходятся. Для записей проверяются абсолютные разрешённые границы, reparse points/junction, `..`, регистр, пробелы, кириллица, занятые файлы. Нельзя развернуть пакет за корень или восстановить поверх чужой последующей правки.

На 10x/100x объёма первыми растут полный аудит, загрузка документации и обработка отчётов. Области и чтение по задаче уменьшают обычную нагрузку, но не отменяют полный аудит init. Потоковое чтение/кэш добавляются лишь при измеренной необходимости. Пределы размера и временные бюджеты измеряются на представительных данных; p99 пока неизвестен. Сам CLI не делает запросы к отдельной модели, не создаёт базы, очереди или фоновые сервисы.

## 8. Связь с планом и проверками

Критерии первого выпуска и проверки отрицательных случаев находятся в [единой матрице плана](../plans/first-release.md). Здесь нет второго списка P1–P6. Исторический подробный вариант сохранён в архивном снимке этой консолидации; его механизмы не становятся обязательствами от наличия текста.

Кандидат готов к выбору двух тренировочных проектов автора. До их испытаний не заявляются пользовательская приёмка, совместимость произвольных версий Codex/OpenSpec, лицензирование всего состава или переносимость самих установленных плагинов. Фактическая проверка — в [отчёте кандидата](../reviews/p3-p6-candidate-review.md).
