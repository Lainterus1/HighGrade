# Задача: последовательная инициализация проекта с сохраняемым обследованием

Статус: передано в HG-0045 → HG-0046 → HG-0047. Исходная согласованная задача; текущие требования, выполнение и доказательства находятся в specs/.
Основание: обсуждение в текущем чате. Пользователь выбрал JSON со схемой и читаемым представлением из него.

## 1. Цель

Подготовить новый или существующий проект к дальнейшей работе по High Grade через последовательное обследование и обоснованную адаптацию. Агент должен понимать устройство проекта, источники требований, ограничения и разрешённые действия, сохранять эти знания между сеансами и выполнять дальнейшие задачи без повторного исследования уже установленных фактов.

Инициализация считается полезной, когда следующий исполнитель может найти источник требования, область изменения, подходящую проверку и критерий завершения. Наличие шаблонных файлов само по себе недостаточно.

## 2. Подтверждённые исходные условия

- Текущий init уже предусматривает обследование, вопросы, адаптацию и проверки, но не задаёт единый структурированный сохраняемый результат обследования.
- inventory возвращает файлы и хеши, читая содержимое; содержит исключения прежнего установщика, исключает корневую .highgrade, имеет ограничения числа и размера файлов.
- inspect --bootstrap проверяет семь шаблонных путей, кандидатов и связи; это предварительная диагностика документов, не содержательная карта проекта.
- Обычный inspect уже поддерживает назначение документных ролей существующим нестандартным путям. Его возможности следует переиспользовать.
- Структурная корректность, содержательная проверка агентом, разрешение изменений, фактическое подключение и человеческая приёмка различаются.

Исходные владельцы: kit/procedures/init.md, kit/references/audit.md, kit/references/tools/diagnostics.md, kit/templates/INSTRUCTIONS.md; реализация — src/bootstrap.rs, src/install.rs, src/inspect.rs, src/main.rs.
Связанные действующие требования: HG-0009 (обследование и документы), HG-0010 (адаптация и продолжение), HG-0036 (диагностические статусы), HG-0043 (достаточность проверок и области доказательств).

## 3. Границы результата

Изменить общий маршрут init, стандарт обследования, необходимую поддержку CLI, связанные инструкции и проверки. Адаптировать использование результата в текущем проекте High Grade без искусственного повторного подключения уже настроенного проекта.

Сохранить полезные существующие документы, местные правила, исключения, навыки и продуктовые гарантии. Подключение High Grade само по себе не разрешает переписывание продукта, смену стека, перенос всей истории спецификаций, запуск внешних сервисов, публикацию или развёртывание.

Не вводить постоянную роль обследователя, новый обязательный навык, отдельную систему задач либо копию жизненного цикла specs. Обследование принадлежит проекту; центрального реестра проектов нет. Поставка остаётся самостоятельной после установки.

## 4. Последовательность инициализации

### 4.1. Предварительный обзор и ключевые решения

Прочитать действующие инструкции и доступные входные документы, определить новый/существующий/уже подключённый проект. Выполнить только необходимую предварительную диагностику. До глубокого обследования выяснить решения, которые определяют его границы.

Фиксируется перечень решений, а не обязательное повторение всех вопросов. Для каждого решения сохраняются ответ, источник и область применимости. Принятое решение не запрашивается заново без нового существенного обстоятельства; предположение не помечается решением пользователя.

| Решение | Что выяснить |
|---|---|
| Цель подключения | Подключить текущий процесс, согласовать его с общим маршрутом или подготовить более широкую реорганизацию |
| Область | Весь проект, подсистема либо явно названный набор компонентов; соседние проекты автоматически не включаются |
| Гарантии сохранения | Поведение, интерфейсы, данные, способы запуска, совместимость и процессы выпуска, которые должны сохраниться |
| Допустимые изменения | Документы/правила; также проверки/автоматизация; отдельно названные изменения реализации |
| Местные правила и навыки | Какие решения обязательны; как разбирать выявленные пересечения и исключения |
| Среда и доступ | Ограничения чтения, запуска проверок, доступа к сервисам, платных операций и работы с закрытыми областями |
| Предел поручения | Обследование и план либо также адаптация; ответ берётся из исходного запроса, если уже определён |

В вопросе о сохранении поведения и вопросе о глубине изменения процесса не смешивать разные решения. «Полностью переписать проект» не является режимом подключения. Вопросы задавать коротким раундом с рекомендацией и последствиями вариантов; уникальные факты спрашивать прямо. Детали будущей публикации выяснять при необходимости, а не заставлять пользователя заранее описывать весь жизненный цикл.

### 4.2. Обследование

Получить обзор всей согласованной области. Углублённо читать источники, влияющие на адаптацию и существенные риски. Не требовать прочтения каждого независимого компонента. Отличать обнаруженный файл, прочитанный источник, вывод из источника и результат выполненной команды.

Заполнить структурированный документ. Обозначить факты, противоречия, неизвестные области и последствия пробелов. Автоматически найденное имя файла, фреймворка или компонента является кандидатом для проверки, а не установленной архитектурой.

Для нового проекта отсутствующие компоненты описывать как предполагаемые или неприменимые; команды и существующие гарантии не выдумывать.

### 4.3. Проектирование адаптации

На основании обследования определить конкретные изменения: что переиспользовать, что добавить, какие конфликты разрешить, какие исключения сохранить. Для существенного изменения указать основание, затрагиваемые источники, проверку и сохраняемые гарантии.

Переход разрешён, когда нет нерешённого вопроса, влияющего на выбранные действия. Независимая неизвестная область не останавливает весь процесс. Согласованное поручение на адаптацию не требует дополнительного формального подтверждения каждого этапа.

### 4.4. Адаптация

Назначить документные роли, согласовать местную инструкцию, навигацию, область спецификаций, теги и реальные проверки. Использовать существующие документы на месте. Переносы, разделение и устранение конкурирующих маршрутов должны иметь конкретное основание.

Выбрать порядок записей, сохраняющий работоспособность: подготовить новый маршрут, проверить его, затем переключить входные инструкции. Не обещать общей транзакции изменений проекта, если она не реализована. После прерывания сохранять фактический результат и понятный следующий шаг; не помечать частичную адаптацию завершённой.

### 4.5. Проверка и завершение

Выполнить применимые doctor/inspect и проверки затронутого поведения. Проверить одну существующую типовую задачу по цепочке «запрос → источник требований → область изменения → проверка → критерий завершения» без обязательного изменения кода.

Чтение маршрута подтверждает доступность и согласованность информации. Исполнимость команды подтверждается фактическим запуском только при наличии соответствующего утверждения и полномочий. Непроверенные условия явно сохраняются.

Независимое ревью назначается по действующим критериям значимости, а не для каждого заполненного поля. Полное обследование не загружается в контекст любой последующей задачи: входные документы направляют к нужной области.

## 5. Стандарт документа обследования

Основной источник — проектный JSON с версией схемы. Читаемое представление формируется из него, не редактируется как второй источник. Предлагаемый путь по умолчанию: .highgrade/project/survey.json; окончательные имена команды и файла определить в спецификации.

Обязательные смысловые разделы:

1. Идентификация обследования: корень/область, назначение, наблюдаемая редакция, этап и пределы.
2. Решения пользователя и гарантии сохранения: источник, состояние и область применимости.
3. Карта проекта: компоненты, ответственность, пути, существенные связи и точки входа.
4. Источники знаний: владельцы требований, архитектуры, инструкций, команд и исторических решений.
5. Рабочие процессы: разработка, проверки, сборка, публикация и эксплуатационные границы.
6. Агентские инструменты: местные навыки и автоматизация, назначение и пересечения ответственности.
7. Источники наблюдений: область чтения, существенные отпечатки, команды и ссылки на результаты, если команды выполнялись.
8. Находки и неизвестное: основание, последствия, зависимые действия и необходимость решения.
9. Предложения адаптации и сведения о фактическом результате: ссылки на единственный план/спеку, если они нужны.
10. Продолжение и завершение: незавершённый этап, следующий шаг, итог и владельцы актуальных знаний после подключения.

Каждый существенный вывод различает подтверждённое, предложенное, неизвестное и неприменимое. Подтверждение факта агентом не является человеческой приёмкой. Необязательные разделы допускают неприменимость с причиной, а не фиктивное заполнение.

Записывать несколько реально характерных типов задач и их маршруты, если они помогают адаптации; не вводить обязательную квоту и универсальный список для всех проектов. Ссылаться на команды и документы владельцев вместо копирования.

## 6. Минимальная поддержка CLI

### Сбор исходных данных

- Разделить быстрый обзор структуры без чтения содержимого всех файлов и снимок хешей явно выбранных источников.
- Сделать существенные проектные настройки доступными обследованию; не исключать весь .highgrade без различения конфигурации, временных данных и выпусков.
- Согласовать безопасность обходов: границы корня, ссылки/reparse points, закрытые и генерируемые области, проектные исключения, ограничение объёма работы и вывода.
- При допустимой частичной недоступности сохранять полученный результат с перечнем непросмотренного и признаком неполноты. Неверный корень или небезопасные параметры должны давать явный отказ, а не пригодный к адаптации снимок.
- Не запускать проектный код и сеть во время структурного сканирования. Не выводить содержимое закрытых файлов; их ограничения фиксировать без закрытых значений.
- Сохранить совместимость прежних потребителей inventory. Новые режимы не должны превращать неполный снимок в действительное подтверждение для legacy-install.

### Работа с обследованием

Предоставить минимальные операции: получить схему, создать без перезаписи существующего документа, прочитать краткую/полную область, безопасно изменить документ, проверить структуру и актуальность, получить читаемое представление. Конкретные команды объединять, если отдельная операция не даёт самостоятельной пользы.

Проверять типы, версию схемы, идентификаторы и ссылки, безопасные пути, требуемые основания решений и согласованность состояний. Запись должна защищать от потери конкурентного изменения и оставлять прежний документ целым при ошибке. Неизвестную версию схемы не переписывать автоматически.

Чтение и проверка не запускают тесты, не изменяют проект и не ставят отметку смысловой готовности от имени агента или пользователя. CLI отдельно показывает структурную корректность, обнаруженные изменения источников, нерешённые зависимости и записанный результат смысловой проверки.

Обследование работает до создания specs и documents.json. Для его начала нельзя требовать предварительно завершённой инициализации. Проектный каталог specs создаётся на соответствующем этапе адаптации, если это входит в поручение.

### Bootstrap и итоговый inspect

Сохранить назначение bootstrap как предварительной диагностики. При повторном init сначала использовать действующий реестр и обычный inspect; если потребуется расширение bootstrap, описать новый режим явно и сохранить прежний контракт. Уже поддерживаемые нестандартные роли не реализовывать второй раз.

Не превращать bootstrap в автоматический семантический анализатор проекта. Интеграция с обследованием должна переиспользовать результаты инструментов и показывать конкретные пробелы, не создавать единственный двусмысленный статус «всё готово».

## 7. Актуальность и повторное подключение

Во время активного обследования фиксировать значимые зависимости выводов. Изменение выбранного источника требует пересмотра связанных выводов; изменение постороннего файла или одного Git SHA не аннулирует всё обследование. Для обзорной карты учитывать также изменения состава выбранной области, когда они способны сделать карту неполной.

Не включать сам изменяемый документ обследования и формируемые представления в их собственные входные отпечатки. Запись служебного продолжения не должна вызывать ложный дрейф источников.

После завершения документ становится историческим основанием адаптации. Актуальные правила, архитектура и команды имеют существующих владельцев; обследование не превращается в обязательную параллельную документацию. Повторный init переиспользует прежние решения и создаёт явную новую редакцию обследования, сохраняя основание предыдущего подключения. Обновлять только затронутые области; не сбрасывать решения пользователя из-за технического дрейфа.

## 8. Проверяемые критерии готовности

1. Новый проект получает честный план без выдуманной архитектуры и команд.
2. Существующий проект с нестандартными документами подключается с сохранением полезных источников и проверенных гарантий.
3. Известные ответы не спрашиваются повторно; существенное противоречие не разрешается молча.
4. Недоступная независимая область остаётся ограничением; пробел, влияющий на действие, блокирует именно это действие.
5. Валидный JSON с непрочитанными источниками не выдаётся за содержательно завершённое обследование.
6. Частичный обход и изменение существенного источника видимы; посторонние изменения не вызывают полного переобследования.
7. Прерванная адаптация продолжается с фактического состояния, без потери решений и ложной отметки завершения.
8. По завершении можно пройти сквозной маршрут типовой задачи и найти владельцев знаний без чтения всего отчёта.
9. Старые команды и legacy-потребители сохраняют предусмотренные гарантии; новые результаты не подменяют прежний audit receipt.
10. Шаблон, схема, справочник и процедуры доступны из установленной Поставки без репозитория разработки.

## 9. Маршрут проверок при реализации

| Область | Достаточное доказательство |
|---|---|
| Опрос, границы этапов, полномочия, достаточность | Таблица решений и независимое смысловое ревью |
| JSON и операции записи | Контрактные тесты корректного изменения, отказов, конкурентной записи, неизвестной схемы и сохранности |
| Обход и снимки | Адресные автоматические фикстуры структуры, исключений, закрытых областей, ссылок, ограничений и частичных результатов |
| Актуальность и продолжение | Тесты значимого/постороннего изменения, добавления источника, самоссылки и возобновления |
| Связь с существующими инструментами | Регрессии inventory/legacy/bootstrap/inspect; переиспользование имеющегося покрытия |
| Документация и установленный выпуск | Генерация, ссылки, схема/шаблон, доступность материалов без исходного репозитория |
| Итог реализации | Применимый проектный барьер один раз для итогового состава, независимое ревью и адресные повторы после замечаний |

Малые изменения формулировок не запускают упражнения агентов на импровизированных проектах. Автоматические фикстуры нужны для изменённого кода CLI и сохранности данных. Текущий High Grade можно использовать для смысловой проверки карты и навигации без повторной активации/миграции его настроек. Если останется существенный вопрос о фактическом поведении модели, обозначить его отдельно; нормативное ревью не объявлять таким наблюдением.

## 10. Предлагаемая разбивка на спецификации

Предварительно достаточно трёх связанных спецификаций:

1. **Обследование и решения:** модель результата, схема, состояния, границы этапов, достаточность и жизненный цикл. Сформулировать изменения действующих требований, не создавать их дубликаты.
2. **Инструментальная поддержка:** сбор структуры/снимков, операции с JSON, проверка актуальности и совместимость существующих команд.
3. **Маршрут подключения:** опрос, процедуры init/audit, продолжение, адаптация, проверка сквозного маршрута, шаблоны и самостоятельность Поставки.

Порядок: согласованный контракт → инструменты → связанный маршрут и итоговые проверки. При выполнении один Planner координирует цепочку, задачи хранятся в спеках; новые постоянные реестры задач не добавляются. Этот документ служит входом для спецификации, после переноса требований не становится вторым backlog.

Текущий результат ограничен проработкой задачи. Версия будущего выпуска и поручения на его активацию/публикацию этой задачей не назначаются.
