# Задача: два маршрута init и подготовка нового проекта

Статус: реализация поручена; уточнение автора — init заканчивается оформлением репозитория и начальных спек, дальнейшая проработка и реализация запускаются отдельно.
Основание: обсуждение создания проекта с нуля и продолжения существующего; действующая Поставка 0.3.2. Цель и принципы — в [README](../../README.md).

## 1. Результат

Init выбирает маршрут по намерению пользователя, готовит проект к работе по Поставке и заканчивается подготовленным репозиторием и начальными спеками с логичным порядком задач. Новый проект получает понятный минимальный репозиторий; существующий сохраняет полезное устройство и согласованные гарантии.

Использовать существующие task/spec/work, survey, inventory, doctor и inspect. У каждого решения и требования остаётся один основной источник. Доработки инструментов определяются конкретными препятствиями выбранному маршруту.

## 2. Выбор маршрута и предел поручения

Первый смысловой выбор init:

> С чего начинаем?
> 1. Продолжаем существующий проект: сохраняем согласованное поведение и адаптируем процесс.
> 2. Создаём новый проект: определяем первый результат и готовим основу для реализации.

Если намерение уже однозначно выражено, сохранить ответ с источником и не спрашивать повторно. Короткий осмотр каталога проверяет исходное состояние, но не заменяет намерение автора. Шаблон или несколько файлов не превращают новый проект в существующий продукт; пустая папка может предназначаться для переноса проекта. При существенном расхождении уточнить только его.

Отдельно определить состояние подключения High Grade и предел поручения: обследование/план, подготовка репозитория и начальных спек; реализация продукта — отдельное поручение после init. Повторный init продолжает относящиеся решения. Переписывание существующего продукта не становится неявным режимом подключения.

## 3. Существующий проект

Сохранить маршрут обследования и минимальной адаптации: реальные компоненты, владельцы знаний, процессы, ограничения и изменения с основанием. Не запускать первичное проектирование продукта заново, если цель уже известна. Перестройку дерева обосновывать конкретной пользой и полномочиями; не переносить файлы ради соответствия демонстрационному шаблону.

## 4. Новый проект: первичные требования

Init передаёт проработку в task, сохраняя контекст. Обязательна проверка полноты ключевых решений; уже полученные ответы не спрашиваются заново.

| Решение | Что должно быть определено |
|---|---|
| Назначение | Проблема, пользователи и полезный результат |
| Первый сценарий | Законченное действие пользователя или потребителя API/CLI |
| Критерий прототипа | Наблюдаемая демонстрация, отличающая полезный результат от одного каркаса |
| Границы | Обязательное в первой версии, исключённое и отложенное |
| Данные и интеграции | Источники, хранение, внешние зависимости; реальные данные или явно обозначенные заменители |
| Среда | Место запуска, обязательные технологии, доступы, ограничения затрат и эксплуатации |
| Предел работы | Обследование/план либо подготовка репозитория и начальных спек; выполнение продукта отдельно |

Дополнительные вопросы об интерфейсе, доступах, безопасности и эксплуатации задавать по применимости. Агент предлагает обычные технические решения с кратким основанием; существенный выбор уточняет до зависимой работы. Не требовать от автора выбора библиотек без связи с целью.

Достаточность: можно сформулировать первую спеку с проверяемым исходом, известными границами и необходимыми предпосылками. Неизвестное вне первого результата не блокирует его. Существенное неизвестное не скрывается предположением.

Описание продукта первоначально может находиться в README. Отдельный PRODUCT.md вводить только по объёму/ответственности. Survey хранит решения и ссылки на владельца требований, а не вторую редакцию продуктовой спеки.

## 5. Устройство репозитория

Определить переносимые критерии аккуратной структуры:

- Корень содержит входные документы и требуемую стеком конфигурацию.
- У каталогов понятная ответственность; по README можно найти код, проверки, требования, команды и проектные решения.
- Код группируется по функциональности, где это помогает локально изменять возможность; сохраняются полезные соглашения выбранного стека.
- Общие модули выделяются при действительной необходимости. Монорепозиторий, apps/packages, сервисы и архитектурные слои не создаются заранее.
- Временные файлы, воспроизводимые кэши и обязательные доказательства имеют определённые места и правила хранения.
- Нет пустых каталогов, фиктивных команд и документов-заглушек, выдаваемых за принятую основу.

Дать небольшой адаптируемый пример: README.md, AGENTS.md, .highgrade/project/, docs/, specs/ и принятые стеком каталоги реализации/проверок. Tests могут находиться рядом с кодом. Scripts/assets/deploy добавляются по необходимости. Пять ролей документов распределить по действующему контракту; допускается совмещение ролей, отдельный файл на каждую роль не обязателен.

Подготовка репозитория различает каталог файлов, локальный Git и удалённый репозиторий. При поручении оформить новый Git-репозиторий допустим локальный git init; существующий .git сохраняется. Remote, публичность, лицензия, коммит, push и развёртывание определяются поручением и известными решениями, не выбираются молча. Для локального проекта отсутствие Git не является дефектом само по себе.

## 6. Обследование нового проекта

### Существующие инструменты

| Инструмент | До подготовки | После подготовки |
|---|---|---|
| inventory structure | Однократно установить пустоту/шаблон/существующие файлы и границы | Сверить фактическую созданную структуру |
| survey new/read/edit | Сохранить решения, обнаруженные факты, предложения и неизвестное | Обновить карту и результат разрешённой подготовки |
| survey snapshot | Закрепить реально существующие значимые источники; не ссылаться на будущие файлы как существующие | Закрепить созданные инструкции и конфигурацию |
| survey review/check | Проверить предпосылки ближайшего действия отдельно от полномочий | Проверить подключение, актуальность и оставшиеся пробелы |
| inspect bootstrap | По необходимости интерпретировать ожидаемые отсутствия; не повторять бессодержательную диагностику пустоты | Проверить основу, затем применять обычный inspect по реестру |
| doctor | Проверить необходимые предпосылки выбранного маршрута | Совместимость и доступность применимых инструментов; запуск подтверждается отдельно |

Сформулировать единое различение:

1. Обнаружено и существует.
2. Решение принято, реализация ещё предстоит.
3. Предложено, но не принято.
4. Неизвестно.
5. Неприменимо по конкретной причине.

Проверить достаточность нынешних state/basis/sources и sections/adaptation. Confirmed означает подтверждение конкретного утверждения: принятое решение о будущем компоненте не доказывает наличие компонента. «Ещё не создано» не заменять not_applicable. Обследованное отсутствие отличается от пустого необследованного раздела. Не создавать фиктивные положительные записи ради completion_ready.

Снимок без существующих источников не доказывает прочтение кода или готовность продукта. При изменениях во время подготовки сохранять фактический этап; до завершения обновлять необходимые снимки и ревью. Сохранить CAS, no_go, обнаружение дрейфа и историю completed/reopen.

### Когда менять CLI

Сначала пройти компактные примеры существующим интерфейсом и назвать конкретный разрыв. Инструкций достаточно, если состояния можно представить однозначно и получить правильную готовность. Менять CLI/схему только если текущая модель требует искажения фактов либо не позволяет проверить нужный переход.

Не добавлять флаг new во все команды, второй комплект инструментов, универсальный генератор приложений или обязательный набор адаптеров. При необходимом расширении обеспечить совместимое чтение прежнего survey и явную обработку неизвестной версии; global-update проектные данные не мигрирует.

## 7. Завершение init и дальнейшая проработка

Маршрут init: намерение → первичные требования → решения об устройстве → минимальная основа → начальные спеки и порядок задач → проверка подготовки и передача.

Init заканчивается репозиторием, сохранёнными требованиями и определённым следующим шагом. Продуктовую функциональность и демонстрационный прототип он не реализует. Не требует рабочего продукта для завершения. Техническая подготовка не порождает фиктивные требования на каждый каталог.

Ближайшую спеку проработать по имеющимся данным: цель, границы, конкретные задачи в логичном порядке, известные требования и проверяемые исходы. В следующих спеках допустимы явные вопросы и незавершённые детали; пустые шаблоны не выдаются за содержательную подготовку. Не создавать спеки далёких неопределённых возможностей. Требования и задачи принадлежат спекам; survey и итоговая передача ссылаются на них без второго backlog.

Черновик не объявляется готовым к реализации или проверенным. Для каждого незавершённого результата указать недостающее и первое действие проработки. Позже task/spec уточняют ту же спеку с сохранением ID; work начинается после достаточной проработки. Рекомендуемая очередность отличается от depends_on: зависимость задаётся по действительной необходимости результата, а не для сортировки списка.

Для существующего проекта сохранить действующие спеки и оформить только требования согласованной области; полная формализация продукта и миграция не обязательны. При отсутствии новых требований не создавать фиктивные спеки ради завершения init.

Проверять подготовленную основу применимыми инструментами. Не запускать генерацию приложения или создавать fake check ради зелёного gate. Если код/runner пока не нужны, отсутствие их запуска явно отражается и не блокирует подготовку. Решения, необходимые только будущей продуктовой реализации, остаются вопросами соответствующей спеки, не выдуманными блокерами завершения init.

## 8. Критерии готовности

1. Намерение создания/продолжения и состояние подключения различаются; известные ответы не переспрашиваются.
2. Новый проект проходит достаточный первичный опрос и получает проверяемый первый результат с границами.
3. Init заканчивается подготовкой репозитория и начальных спек; продуктовая реализация не входит в его готовность.
4. Survey различает существующее, принятые будущие решения и неизвестное; не требует фиктивных фактов или потери блокеров.
5. Ожидаемое отсутствие до создания и невыполненное обязательство после этапа интерпретируются различно, без подавления исходной диагностики.
6. Структура репозитория понятна, минимальна и согласована со стеком; нет обязательного разрастания каталогов и документов.
7. Первая спека описывает законченный результат; требования не дублируются в survey и плане.
8. Существующий проект, повторный init, сохранность файлов и история обследования не ухудшены.
9. У каждого изменения инструмента есть конкретный воспроизводимый разрыв и достаточная регрессионная проверка; ненужные изменения CLI исключены.
10. Документация, шаблоны и генерируемые навыки согласованы. Новых обязательных ролей, внешних пилотов и нерелевантных проверок нет.

## 9. Маршрут и проверки будущей реализации

Основные владельцы: [init](../../kit/procedures/init.md), [task](../../kit/procedures/task.md), [audit](../../kit/references/audit.md), [survey](../../kit/references/tools/survey.md), [diagnostics](../../kit/references/tools/diagnostics.md), шаблон INSTRUCTIONS и затронутые документы проекта. Код при подтверждённой необходимости: src/survey.rs, discovery.rs, bootstrap.rs, inspect.rs и связанные тесты.

Сверить действующие HG-0045–0047 и HG-0048–0050; новые нормативные ожидания оформлять отдельным изменением, не переписывать завершённую историю. Предварительно достаточно одной спеки маршрута двух видов проектов; отдельная вторая оправданна самостоятельным изменением машинного контракта survey/CLI. ID назначаются при поручении подготовки спек. Примеры и технические исправления входят в задачи этих спек.

| Случай | Проверка |
|---|---|
| Пустой каталог, поручен только план | Нормативная таблица: продукт/файлы не создаются, неизвестное явно |
| Новый проект из шаблона | Существующие файлы сохраняются; отсутствие продукта не выводится из числа файлов |
| Существующий продукт и повторный init | Сохранение текущего маршрута, решений и области изменений |
| Часть ответов известна, остался существенный вопрос | Нет повторного опроса; остановлено только зависимое действие |
| Нет кода/runner/документов до подготовки | Честное представление отсутствия и применимости текущими командами |
| Нужный файл не появился после подготовки | Пробел остаётся видимым; «будет создан» не закрывает готовность |
| Git отсутствует / уже есть / remote не определён | Нет перезаписи истории или самовольной публикации |
| Подготовка прервана и продолжена | Фактический этап, CAS, снимок, ревью, история и конкретный Next |
| Разные типы проектов | Нормативные примеры небольшой CLI и приложения: функциональная структура адаптируется, UI/deploy не обязательны |

Для процедур достаточно смыслового ревью diff и таблицы решений. Для проверяемого машинного поведения — небольшие изолированные фикстуры пустого каталога/шаблона и адресные контрактные тесты; это не разработка импровизированных продуктов. Существующие тесты переиспользовать, новые писать для конкретного непокрытого риска. Итоговая матрица — DEVELOPMENT: без изменений Rust нет основания для полного Rust-прогона; при изменении CLI — один итоговый барьер и независимое ревью. Реальный внешний пилот требует отдельного поручения.

## 10. Граница текущего поручения

Существенных недостающих решений для постановки нет. Пользователь поручил реализацию через highgrade-planner после уточнения границы init. Разрешены относящиеся спецификации и изменения High Grade; активация, коммит, публикация и изменения других проектов не назначены. При реализации несовместимая миграция или расширение существенных полномочий требует отдельного решения; обычные детали интерфейса и структуры выбираются в пределах этой задачи.

## Передача

Основной источник требований и выполнения — HG-0051. Проверка текущей CLI на изолированных данных подтвердила представимость пустого/шаблонного проекта; изменение схемы и вторая спека не потребовались.
