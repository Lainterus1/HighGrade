# Задача: переносимый и соразмерный workflow после первого пилота

Статус: передано в реализацию HG-0048–HG-0050; документ сохраняет согласованное основание, актуальное состояние — в спеках.
Основание: анализ чата «Инициализировать High Grade» (01a0de2a-f4a1-7d80-ae51-f822703706a1), пилот SNAF и поручение пользователя оформить объективные масштабируемые улучшения. Исходная проверенная Поставка — v0-3-1.

## 1. Цель

Сократить повторяемую техническую работу агента при подключении проектов и выполнении задач, сохранив доказательность, местные правила, совместимость и полномочия. Обследование должно отражать фактическое состояние, доказательства — оставаться доступными в согласованном способе передачи, а CLI — предоставлять устойчивый интерфейс для обычных последовательных операций.

Критерий полезности — устранение конкретной ошибки или повторяемого ручного действия. Число правил, команд, тестов и документов само по себе результатом не является. Цели и принципы — в [README](../../README.md#цель-проекта).

## 2. Проверенные факты и границы выводов

| Полные проверки выполнялись для документационной адаптации и малой UI-задачи | Init полезно выявлять стоимость, дубли и основания местной матрицы | Агент нарушил соразмерность: полный gate прямо требовался SNAF; отменять его без решения нельзя |
| Markdown содержит String("completed"), кавычки и пустые поля | Подтверждён дефект читаемого представления | Нужен второй редактируемый отчёт или новая система документации |
| Несогласованные бюджеты многократно объяснялись отдельно от готовности | Структурные ошибки, неизвестные значения и принятые ограничения нужно показывать раздельно | Неизвестность можно считать измеренным PASS или скрывать ошибки по произвольному исключению |

Длительности одного пилота не использовать как SLA или доказательство количественного ускорения. Сбои Windows ACL, локальный PATH, адрес сайта и версии Node/pnpm относятся к среде пилота; универсальными требованиями Поставки они не становятся.

## 3. Область и полномочия

В будущую реализацию входят необходимые изменения CLI, общих процедур, справочников, схем/шаблонов и адресных контрактных тестов. Существующие требования уточнять по смыслу, новые изменения оформлять только для нового нормативного поведения.

Сейчас разрешено подготовить эту задачу. Не изменять SNAF, его приёмку, доказательства, правила тестирования, права, deployment и каталоги. Не запускать новые внешние пилоты, не создавать постоянные роли, центральный реестр проектов, универсальную платформу тестирования или обязательный журнал всех действий. Реализация, выпуск, активация и push сейчас не выполняются.

## 4. Изменения по приоритету

### P1. Жизненный цикл доказательств и переносимость результата

- В init определить существующего владельца доказательств, постоянное место, способ передачи и применимые ограничения хранения. Переиспользовать действующее решение; новый документ для этого не обязателен.
- Различать локальную техническую готовность, человеческое решение и пригодность выбранного состава к передаче. Отсутствие публикации не делает локальную задачу незавершённой.
- Перед локальным принятием/передачей проверять обязательные зависимости выбранных результатов: отчёты и невосстановимые входы должны присутствовать в выбранном составе либо иметь явно указанное устойчивое место хранения. В Git учитывать tracked/untracked/ignored, включая исключения расширений; наличие файла на диске недостаточно.
- Давать конкретные пути и причины. Для проекта без Git проверять объявленный состав передачи; если он не задан, обозначать переносимость как непроверенную, без обязательной инициализации Git.
- Не реализовывать загрузку во внешние хранилища, управление их доступом или автоматическую публикацию. Внешняя ссылка сама по себе не подтверждает доступность и срок хранения.
- Не добавлять файлы в Git, не менять ignore и не пересчитывать человеческие решения автоматически. Минимальные доказательства отбирать по проверяемому утверждению; приватные данные и тяжёлые воспроизводимые артефакты сохранять по политике проекта.

Владельцы: [work](../../kit/procedures/work.md), [approve](../../kit/procedures/approve.md), [init](../../kit/procedures/init.md), [verification](../../kit/references/tools/verification.md), src/specs и существующая диагностика. Сначала расширить имеющийся механизм проверки/передачи; отдельная команда оправданна лишь самостоятельным применением.

### P1. Survey: фактический этап и готовность конкретного действия

- Различать возможность представить обследование/план, технические предпосылки адаптации и завершение согласованного объёма. Название и справка должны явно отделять эти статусы от разрешения и приёмки.
- Сохранять нерешённый вопрос при выдаче плана; не требовать удалять его blocks только ради готовности независимого результата.
- Связывать блокер с определённым действием/переходом. Не полагаться на незаметную разницу произвольных строк вроде adaptation и execute-adaptation: системные действия имеют определённый контракт, прочие зависимости сохраняются отдельно.
- Разрешить актуализацию находок во время выполнения с сохранением фактического этапа. Существенное изменение инвалидирует относящееся подтверждение и требует проверки перед зависимым действием, а не фиктивной перемотки этапов.
- Не требовать записывать промежуточные этапы задним числом ради завершения. При продолжении отражать наблюдаемое состояние и основание; не заявлять, что CLI контролирует все изменения, выполняемые вне него.
- Сохранить CAS, запрет ложной актуальности, no_go, обнаружение дрейфа, историю completed/reopen и запрет автоматической человеческой приёмки.
- Сохранить чтение survey v1 и честную интерпретацию прежних состояний. Если нужен несовместимый формат, предусмотреть явный проверяемый переход; global-update не мигрирует проектные данные.

Владельцы: src/survey.rs, [survey](../../kit/references/tools/survey.md), init; действующие HG-0045–0047. Не вводить универсальный движок workflow или новый реестр разрешений.

### P2. Совместимость с инструментами проекта и стоимость проверок

В обследовании, в уже существующих разделах процессов/находок, проверить:

- Какие файлы создаёт подключение, кто владеет их сериализацией и какие форматтеры, линтеры, ignore и CI их захватывают.
- Какие проверки обязательны по местным правилам, что они подтверждают, где повторяются сборки/запуски и когда пригоден актуальный результат.
- Где закреплена среда и как штатная команда вызывает дочерние инструменты. Сначала использовать имеющийся проектный способ, не устанавливать новую среду по шаблону.

До адаптации предложить минимальные точные настройки. Исключать из чужой сериализации только принадлежащие CLI данные; авторские инструкции, реестры и обычные JSON проекта остаются в принятом маршруте. Не изменять автоматически CI, gate или контроль секретов. Оценка соразмерности — рекомендация с основанием; строгая местная политика может быть обоснованной.

Одинаковый подход должен работать для formatter без JSON, проекта без форматтера, строгого CI и локального проекта без CI. Новые обязательные поля survey нужны только если существующие разделы не позволяют однозначно хранить решение.

Владельцы: init, [audit](../../kit/references/audit.md), шаблон INSTRUCTIONS; смысл достаточности уже определён HG-0043 и проектной матрицей проверок.

### P2. Runner: отделить запуск от сопоставления отчёта

- Поддержать различие аргумента отбора теста и идентификатора результата без переписывания JUnit и без анализа внутренностей конкретной библиотеки агентом.
- Старые checks/runners сохраняют прежний смысл. Явно определить точность, экранирование и передачу аргументов; данные не превращать в shell-код.
- Для первого необходимого подключения runner дать короткий воспроизводимый путь проверки: выбранный тест выполнен, однозначно найден, skipped/missing/duplicate/failed не дают passed даже при exit 0.
- Использовать существующие spec-run/import и снимки входов. Не создавать фиктивную продуктовую спеку ради проверки настройки. Если отдельный механизм действительно нужен, его назначение ограничивается проверкой адаптера.
- Не делать набор готовых адаптеров обязательной частью init. Пример Vitest допустим как необязательный пример применения общего контракта; такое же поведение проверить на нейтральном runner.

Владельцы: src/specs/checks.rs, verification, схемы checks/runners.

### P2. Устойчивый интерфейс последовательных CLI-операций

- Дать документированный именованный доступ к CAS, основному результату и созданным путям, не зависящий от позиции в measurements. Сначала выбрать минимальный совместимый вариант; не переписывать все ответы CLI без необходимости.
- Сохранить существующие потребители и выходные коды. Области хешей различаются: store_sha256, survey_sha256 и другие нельзя выдавать за взаимозаменяемый expected.
- Возвращать фактическое расположение каталога/указателя при создании. Не заставлять агента угадывать стандартный путь после его явного переопределения.
- Привести короткий пример безопасной последовательной записи с проверкой exit/status до следующей зависимой операции. Бессмысленные повторные read и самодельные циклы сокращать только при сохранении CAS.

Владельцы: src/lib.rs (Report), src/main.rs, соответствующие команды, [CLI](../../kit/references/cli.md). Ошибка вызова должна указывать отсутствующий параметр, где это возможно, вместо общей неинформативной причины.

### P3. Читаемое представление и понятные ограничения

- Исправить String("completed"), кавычки машинной сериализации и пустые подписи; обеспечить читаемую иерархию и сохранность значимых оснований, ограничений и источников. JSON остаётся единственным редактируемым источником.
- Дать короткий способ получить представление без ручной сборки текста. Обязательная запись survey.md не требуется; если добавляется экспорт, он должен иметь явные пути и правила перезаписи.
- В итоговой диагностике разделять структурные ошибки, неизвестные показатели и явно принятые ограничения с источником решения. Сохранить исходные findings, неизвестные значения и возможность проверить основания.
- Не вводить общий механизм подавления диагностик ради одного BudgetNotAgreed. Для бюджета сначала использовать существующие поля и инструкцию; новая схема допустима только при доказанной невозможности однозначного представления. Блокирующая ошибка не становится допустимой от одного комментария.

Владельцы: src/survey.rs, src/inspect.rs, survey/diagnostics. Исправления представления по неизменному контракту включить как технические задачи, без дублирующей спеки.

## 5. Проверка отсутствия привязки к SNAF

Каждое новое правило должно иметь независимый от пилота пример и контрпример, где оно не применяется:

1. Git с ignored evidence / проект без Git / локальный результат без порученной публикации.
2. План без разрешения адаптации / разрешённая частичная адаптация с независимым неизвестным / завершённая история и повторный вход.
3. Строгий formatter / отсутствующий formatter; короткая нормативная правка / изменение CLI или данных.
4. Совпадающие селекторы / различающиеся селекторы / нулевое или неоднозначное сопоставление отчёта.
5. Известный бюджет / несогласованный бюджет / принятая неопределённость рядом с реальной структурной ошибкой.

Эти варианты — компактные контрактные фикстуры и таблицы решений, не новые реальные проекты или обязательные упражнения агентов. Не фиксировать пути SNAF, pnpm, CSS, конкретные версии инструментов и число тестов как условия успешности Поставки.

## 6. Критерии готовности

1. Минимальные обязательные доказательства выбранной передачи не теряются молча из-за ignore; локальная готовность/приёмка при этом не подменяются статусом публикации.
2. План выдаётся с сохранением зависимых неизвестных; готовность действия и полномочия различимы без чтения оговорок в нескольких местах.
3. Изменение survey во время адаптации отражает фактический этап и инвалидирует нужные подтверждения; завершение не требует выдуманной истории переходов.
4. Init выявляет влияние новых файлов на инструменты проекта до финального gate, сохраняя местные полномочия и обязательные проверки.
5. Разные селекторы запуска/отчёта поддержаны общим контрактом; skipped, missing и неоднозначность остаются непрохождением.
6. Последовательные операции CLI не требуют знания индекса measurements; ошибочная запись не маскируется успехом следующей команды.
7. Читаемое представление не содержит отладочной сериализации и не расходится по смыслу с JSON.
8. Неизвестные бюджеты и принятые ограничения видны отдельно от реальных ошибок, без автоматического PASS или выдуманных чисел.
9. Совместимость старых данных/потребителей подтверждена; проектные данные, решения человека и поставка обновляются раздельно.
10. Все изменения имеют переносимое обоснование; новых обязательных ролей, документов, внешних пилотов и нерелевантных запусков не добавлено.

## 7. Маршрут реализации и проверки

Предварительно достаточно трёх связанных спек, окончательные ID назначит CLI при отдельном поручении реализации:

1. **Доказательства и адаптация среды:** переносимость выбранного результата, совместимость машинных файлов и обследование матрицы проверок.
2. **Обследование и диагностика:** семантика этапов/блокеров, актуализация, совместимость данных и представление ограничений; сопутствующее исправление Markdown.
3. **Интерфейсы инструментов:** именованный доступ к результатам и CAS, разделение селекторов и проверка настройки runner.

Проверить связи с HG-0004, HG-0009, HG-0011, HG-0021/0026, HG-0040/0043 и HG-0045–0047. Не дублировать уже принятые требования; изменения нормативного ожидания оформлять новыми операциями. Зависимости между тремя спеками назначать по данным/контракту, а не только по порядку списка. Координация — один Planner при запуске реализации; этот документ после передачи становится основанием, а не вторым backlog.

| Область | Достаточная проверка и основание |
|---|---|
| Процедуры и матрица выбора | Смысловое ревью diff и таблиц из раздела 5; новое поведение модели не заявляется |
| Переносимость evidence | Изолированная Git-фикстура с tracked/untracked/ignored; проект без Git; исчезнувший обязательный отчёт; никакой реальной публикации |
| Survey | Адресные tests переходов, редактирования, блокеров, дрейфа, no_go, истории и чтения v1; CAS и сохранность при отказе |
| Форматтер/ignore | Таблица решений; реальная короткая инструментальная проверка только для поставляемой исполнимой интеграции |
| Runner | Существующие контрактные тесты плюс neutral runner: разные идентификаторы, метасимволы, skip/missing/duplicate/failure, актуальность снимка |
| CLI и Markdown | Контракт именованных значений и старого ответа, конкретных ошибок и путей; небольшие семантические примеры представления |
| Общий итог | Один полный Nextest/trace для окончательного Rust/форматного состава, генерация, структура и inspect по DEVELOPMENT; независимое ревью |

Для маленькой правки промпта/инструкции не запускать приложения на импровизированных проектах. Расширять проверки только при новом исполнимом контракте или конкретном неустранённом риске. Повторные проверки определять по изменившимся входам. Новая реальная проба нужна лишь для существенного вопроса, который не закрыт чтением и контрактными тестами, и по отдельному поручению.

## 8. Условия передачи

Существенных недостающих решений пользователя для постановки задачи нет. Выбор полей/названий команд и деталей совместимой реализации относится к подготовке спецификаций с учётом перечисленных ограничений. Если минимальное решение потребует несовместимой миграции, обязательного внешнего сервиса или изменения местных полномочий, уточнить только этот выбор до зависимой работы.

При завершении будущей реализации сопоставить критерии с доказательствами и отдельно сообщить ограничения, коммит, активацию, публикацию и человеческую приёмку. Этот запрос не назначает выпуск и не разрешает реализацию этих действий.

Требования и задачи перенесены в HG-0048, HG-0049 и HG-0050. Этот документ сохраняет согласованное основание; текущее выполнение и критерии ведутся в нативных спеках.
