Базовые решения: [D1–D33, кроме снятого D31](../workflow/SPECIFICATION.md), [контекст и документация](../workflow/CONTEXT.md). Имена ниже — предложенные интерфейсы, не существующие команды.

## 1. Результат и границы

High Grade выпускает набор проектных навыков, правил и небольших утилит. Каждый целевой репозиторий получает выбранную копию основы и собственную адаптацию. После установки работа не требует доступа к High Grade или сети. Первая проверяемая среда — Windows, отдельно приложение Codex и CLI.

Техническая рекомендация: четыре навыка, один локальный CLI, короткий вход через AGENTS.md и обычные файлы в репозитории. Не нужны сервер, централизованный реестр проектов, база знаний, второй диспетчер задач, собственный BDD-движок или зависимость от личных навыков автора.

Правила штатного сопровождения применяются при выполнении любой задачи. Навык актуализации дополнительно обследует состояние по запросу; он не является условием архивации или обновления документации.

## 2. Упаковка и зависимости

По принятому [WF-DISTRIBUTION-01](../workflow/SPECIFICATION.md) пока распространяются только исходники через GitHub-репозиторий. Готовые бинарные сборки и установочные пакеты отложены. CLI собирается локально по будущей инструкции; выбранная основа применяется в целевом проекте. Конкретный способ подготовки локальной поставки ещё обсуждается. Проверка новых выпусков и скачивание — только по запросу; установка не запускает автоматическое обновление OpenSpec или Codex.

По принятому [WF-RUST-01](../workflow/SPECIFICATION.md) общий CLI разрабатывается на Rust. Собственные плагины также входят в направление постепенного переноса, но имеют отдельные планы оценки и миграции; код ещё не менялся. Rust не ограничивает язык целевого проекта. OpenSpec остаётся внешним компонентом со своими требованиями к среде; выбор Rust сам по себе их не устраняет.

Для первого этапа предусматривается локальная сборка CLI пользователем под поддерживаемую платформу; готовые сборки не публикуются. Конкретные версии toolchain, цели сборки, зависимости и способ выбора бинарного файла ещё не определены. Для файловых операций используется стандартная библиотека там, где достаточна; JSON, Markdown и хеширование требуют отдельного выбора подходящих средств с проверкой лицензий. Прежняя рекомендация стандартных модулей Node больше не применяется. Подсчёт точных токенов необязателен: метод оценки и недоступность отображаются явно.


Для первого выпуска предлагается проектная установка навыков, без глобального изменения ~/.codex. Официальная документация поддерживает .agents/skills в репозитории и загрузку полного SKILL.md при выборе навыка. Нативный плагин можно рассмотреть позже как способ доставки; он не нужен для подтверждения автономной работы проекта. [Источник](https://learn.chatgpt.com/docs/build-skills).

## 3. Дерево целевого проекта и владение

Имена `.highgrade`, `highgrade-*` и `highgrade.exe` ниже — примеры будущей структуры под новым названием. Существующий локальный реестр проекта разработки остаётся `.mycodex/project/documents.json`; фактическое устройство описано в [ARCHITECTURE](../ARCHITECTURE.md).

```text
project/
  AGENTS.md                         # адаптация: порядок работы и ссылки
  README.md                         # адаптация: назначение и навигация
  docs/
    ARCHITECTURE.md                  # действующее устройство
    ENGINEERING.md                   # проектные инженерные соглашения
    DEVELOPMENT.md                   # команды и процедуры
    decisions/                      # ADR, когда есть значимые решения
    plans/                          # только задачи вне OpenSpec
    archive/                        # исторические документы и итоги гипотез
  openspec/                         # штатные артефакты OpenSpec
  .agents/skills/
    highgrade-init/                    # короткие входы в выбранную основу
    highgrade-work/
    highgrade-refresh/
    highgrade-update/
  .highgrade/
    bin/highgrade.exe                 # предложенный вход Windows; механизм ещё обсуждается
    active.json                     # выбранная поставка + хеш manifest
    releases/<release-id>/           # неизменяемая общая основа
      manifest.json
      rules/                        # общие принципы, порядок сопровождения
      procedures/                   # процедуры навыков
      templates/                    # заготовки при инициализации
      presets/                      # необязательные стартовые предпочтения
      cli/                          # CLI и включённые зависимости
      licenses/
    project/
      settings.json                 # команды, runtime, области проекта
      documents.json                # роли, пути, связи и бюджеты
      accepted-gaps.json             # только согласованные исходные пробелы
    state/<task-id>.json             # ссылка на задачи + Next + доказательства
    feedback/                       # локальные замечания к workflow
    evidence/                       # компактные сохраняемые доказательства
    local/                          # временные отчёты/логи/кэш, gitignored
    transactions/                   # журнал незавершённых локальных операций
```

Это карта ответственности. Не создаём пустые ADR, планы и архивные записи «для полноты». В готовом проекте подходящие существующие пути переиспользуются через реестр, а не копируются в параллельное дерево. Пять согласованных ролей остаются обязательными; миграция структуры и архитектуры выполняется по согласованному плану, не ограничивается добавлением ссылок.

Содержимое releases — общее и проверяется по manifest; его не редактируют для конкретного проекта. Все проектные решения находятся снаружи. Изменение общих правил в целевом проекте оформляется как явная адаптация или предложение к High Grade. AGENTS и ENGINEERING ссылаются на конкретные разделы общей основы, не копируют их целиком.

В Git сохраняются выбранная основа, адаптация, документы, полезные записи состояния/обратной связи и компактные доказательства. Логи, временные staging-копии и локальные блокировки не коммитятся. Секреты не хранятся в этих файлах. Везде используются относительные к корню пути; абсолютный путь runtime обнаруживается локально и не становится переносимой настройкой.

## 4. Четыре навыка

| Навык | Вход и результат | Когда используется |
|---|---|---|
| highgrade-init | Контекст + интервью → устройство проекта, адаптация, начальные бюджеты и план | По запросу создать/подключить проект; заканчивает планом, не начинает реализацию без соответствующего поручения |
| highgrade-work | Согласованная задача → реализация, проверки, документы, архив и точка продолжения | Основная процедура существенных изменений; маленькая задача остаётся одним проходом |
| highgrade-refresh | Область/весь проект → картина состояния, разрешённые исправления и остаточные вопросы | Только явно запрошенная актуализация; режим «только анализ» ничего не исправляет |
| highgrade-update | Выбранный пакет → проверенный кандидат и добровольное переключение | Только по запросу обновить workflow |

Не делаем отдельные навыки для каждого счётчика, архива и fallback: это общие процедуры. Doctor и проверки связей — команды CLI, доступные из навыков и вручную. Навыки ссылаются на один maintenance-порядок в общей основе; их тексты не дублируют этот порядок.

Входные SKILL.md остаются короткими и стабильными: определяют корень проекта, читают active.json, затем нужную процедуру из выбранной поставки. Их совместимость входит в manifest. Корень ищется от пути навыка или явно передаётся, а не угадывается по последней папке терминала. Несовместимость загрузчика обозначается до переключения версии.

Для refresh/update/init рекомендуется policy.allow_implicit_invocation=false, чтобы обычная задача не вызывала глобальную уборку, обновление или повторное интервью. Явный вызов доступен; при естественной просьбе об актуализации агент направляет к соответствующей процедуре с явным намерением пользователя. Точное поведение такого перехода проверяется в обоих интерфейсах; не предполагается, что отключённая неявная активация сама обработает свободную фразу. [Политика навыков](https://learn.chatgpt.com/docs/build-skills).

## 5. Начальная установка и инициализация

Есть два разных действия: подключить инструменты и спроектировать сам проект. Пользователь получает исходники из GitHub, следует инструкции локальной сборки и подключения. Предлагаемая процедура подключения сначала показывает список файлов и конфликты; никакого поиска других проектов нет. Первая установка добавляет только выбранную основу, входы навыков и минимальную навигацию, не преобразует приложение.

Существующий AGENTS.md не заменяется шаблоном. Инициализатор читает действующие инструкции; добавление короткого блока маршрутизации готовится как обычный diff, сохраняя правила владельца. При конфликте инструкций сначала выясняется смысл, а не выбирается самая новая версия текста. Совпадающее имя чужого навыка не перезаписывается. Повторное подключение той же поставки не плодит копии.

Первая установка также транзакционная: bootstrap сохраняет журнал, исходные хеши затрагиваемых файлов и план публикации. Сначала размещает и проверяет общую основу и загрузчик, затем active.json, затем входы навыков, а блок AGENTS добавляет последним. До завершения журнал явно показывает неполную установку; ранний вызов опубликованного входа выдаёт «установка не завершена», не выполняет проектные действия. Повторный запуск читает журнал и предлагает/выполняет разрешённое продолжение или восстановление: удаляет только созданные этой операцией неизменённые файлы, возвращает прежний текст лишь при совпадении ожидаемых хешей. Чужая последующая правка сохраняется и обозначается как конфликт восстановления. Глобальный git reset и перезапись всего AGENTS недопустимы. Завершение подтверждается проверкой загрузчика, полного набора файлов и маршрутов; обнаружение навыков в обоих интерфейсах отдельно проверяется на этапе P1.

Далее highgrade-init обследует код, документы, команды и уже принятые решения. Он спрашивает только недостающие существенные вещи и определяет минимальный состав адаптации. Выход: согласованный документ устройства и авторитетный список задач. Для OpenSpec-изменения — его tasks; для чисто технической миграции — docs/plans. Создание кода и архитектурное преобразование переходят в highgrade-work после разрешения выполнять этот план.

Необязательный авторский preset по D17 — отдельный файл предпочтений в поставке, применяемый только по выбору при интервью. Его пункты становятся согласованной адаптацией, не скрытым источником приоритета. По умолчанию используется универсальная основа; выбранные проектные решения всегда видимы. Обновление preset не переписывает уже принятую адаптацию.

Новый проект без Git может пройти интервью и получить план. До изменяющей миграции определяются способ сохранения исходного состояния и проверки отката; отсутствие Git не исправляется диагностикой автоматически. Незнакомый runtime или тестовый стек не вызывает немую подстановку привычного стека автора.

## 6. Минимальные машинные контракты

JSON выбран для машинных файлов как читаемый формат без дополнительного YAML-runtime. У документов Markdown остаётся гибкая структура. Реестры не содержат копий требований, инженерных правил или списка задач.

| Файл / запись | Минимальные поля и смысл |
|---|---|
| settings | пути, области проекта, команды с cwd/executable/args/timeout, ссылки на основные документы; команды не склеиваются из пользовательских строк |
| documents | стабильный doc_id, role, path, scope, loading=entry/task/history, связанные источники, budget и состояние последнего обзора |
| budget | единица, согласованная база и верхняя граница, текущий бюджет, обоснование, событие пересмотра, история изменений относительно базы |
| traceability (производный результат) | По WF-TRACE-01 извлекается из отметок автоматизированных тестов; не редактируется как второй источник связей. Формат, путь и представление ранее разрешённых ручных доказательств ещё обсуждаются |
| accepted-gaps | scenario_id, причина, ссылка на согласование и исходное состояние; изменение сценария прекращает автоматическое применение старого исключения |
| task state | ссылка на OpenSpec/tasks или технический план, текущий шаг, один Next, блокеры, ссылки на evidence и относящиеся файлы |
| evidence | команда/проверка, результат, проверенные входы и хеши, среда, время, источник отчёта и границы подтверждения |
| feedback | процедура, версия основы, ожидание, факт, доказательство, причина или гипотеза, локальное исправление; без автоматической отправки |

Карточка временного обхода живёт у связанной задачи: причина, код, проверка, условие удаления и статус пересмотра. Если обход пережил задачу, ссылка на незавершённое обязательство сохраняется в её основном реестре задач; закрытие или архивирование не может сделать обход невидимым. Не создаётся второй backlog High Grade. Технический индекс ссылок можно генерировать, он не владеет задачами.

Пример записи документа (условные поля; бюджет задаётся при инициализации, не универсальными числами):

```json
{
  "id": "architecture",
  "role": "current-architecture",
  "path": "docs/ARCHITECTURE.md",
  "scope": ["src/", "services/"],
  "loading": "task",
  "related": ["engineering"],
  "budget": null,
  "review": {"status": "not-assessed"}
}
```

null — требуется первичная оценка, не бесконечный разрешённый бюджет. Новая папка вне карты областей вызывает «область не классифицирована», а не автоматическое включение в успешно проверенное покрытие.

## 7. Локальный CLI: небольшой набор операций

Все команды ниже — интерфейс будущего инструмента, а не инструкция запуска уже готового ПО. Предложенный вход для Windows: .highgrade/bin/highgrade.exe <operation>; точный путь и механизм выбора поставки ещё обсуждаются. CLI не вызывает другую LLM и не запускает рекурсивный Codex.

| Операция | Что делает | Изменения |
|---|---|---|
| doctor | Доступность runtime, конфигурации, команд и нужных файлов; версии и явные ограничения | Только отчёт; без установки и запуска сервисов |
| inspect --scope <task-or-path> | Размеры, ссылки, применимые инструкции, затронутые источники, наступившие условия | Только отчёт; полный охват — явно --all |
| trace --change <id> | Целостность сценариев, связей, исключений и фактических результатов | Только отчёт; тесты сами не запускает |
| update prepare / update activate | Проверка локального кандидата и переключение основы | Только явно выбранные файлы установки; адаптация автоматически не переписывается |

inspect включает списки кандидатов, не выдает эвристический вывод о смысле за факт. Проверка ссылок различает внутренние пути, якоря, HTTP и исторические цели; сеть для проверки URL по умолчанию не используется. Ссылки на стандартные Markdown-заголовки проверяются выбранным и протестированным алгоритмом; неизвестный диалект показывается как ограничение.

Отчёт JSON: operation, scope, observed_inputs, measurements, findings[{id,kind,location,evidence,affected_scope}], checks[{id,status,reason}], limitations. Краткий Markdown — представление того же отчёта. Статусы проверки: passed / failed / not-run / unknown. Отдельный вывод о смысловой согласованности создаёт агент со своей областью, а не скрипт.

Коды завершения: 0 — операция измерения выполнена (предупреждения возможны); 1 — проверенный контракт нарушен; 2 — запуск/сбор не завершён. Агент читает статус и область, не превращает любой ненулевой код в остановку всего проекта. Нулевой код inspect не означает, что тесты прошли или проект глобально согласован.

## 8. Штатный рабочий цикл

```text
Задача -> нужный контекст и область изменений
       -> исполнение + целевые проверки
       -> синхронизация связанных документов
       -> размеры / ссылки / сценарии / временные обходы
       -> архивирование подтверждённо завершённого
       -> повтор затронутых проверок и сохранение Next/результата
```

Перед значимой правкой агент определяет связанные требования и источники, не сканирует всё дерево каждый раз. После изменения выполняет inspect в затронутой области и нужные проектные тесты; исправляет смысловые расхождения. Изменение общих инженерных правил расширяет область проверки. Завершение задачи включает проверку того, что текущие ссылки не указывают на заменённые правила.

Это часть highgrade-work и короткого порядка в AGENTS для задач без явного вызова навыка. Архивирование, сопровождение временных обходов и бюджетов не откладываются до refresh. Никакое количество маленьких правок не разрешает молча пересогласовать диапазон бюджета.

Сигналы размера требуют внимания, не являются жёстким gate. Существенный подтверждённый конфликт блокирует только зависимую часть; работа по его устранению разрешена. Пропущенный тест не заменяется структурно правильной ссылкой. Нельзя заявить глобальное здоровье по успешной локальной задаче.

По принятому [WF-CHECKS-01](../workflow/SPECIFICATION.md) общий запускатель `verify` исключён: команды проекта запускает агент напрямую. Предложенные адаптеры отчётов служат проверке доказательств и связей, а не новому механизму запуска тестов.

## 9. Хуки отложены за первую версию

Принято [WF-HOOKS-01](../workflow/SPECIFICATION.md): первая версия работает без хуков, обязательные проверки остаются частью явной процедуры. Повторяющиеся подтверждённые пропуски на испытаниях — основание пересмотреть решение, а не автоматически включить обработчик.

Исходная идея необязательного уведомляющего Stop-обработчика сохранена в [архивном техническом предложении](../archive/designs/2026-09-22/mycodex-technical-design.md). Его поддержка и поведение не проверены. При возвращении к идее потребуется отдельная проверка совместимости в приложении и CLI; отсутствие хука в первой версии не является ошибкой установки.

## 10. Дополнительная актуализация

Вызов: «актуализируй проект» или явный выбор навыка. Агент уточняет область только если запрос неоднозначен; режим «покажи состояние, ничего не меняй» остаётся read-only. По запросу исправить/актуализировать выполняются обычные обратимые исправления в согласованных границах, без повторного одобрения каждой ссылки.

Проход: doctor → inspect --all (либо указанная область) → смысловая проверка источников и кода → проверка связей и ранее известных обходов → разрешённые исправления/архив → повтор затронутых проверок → отчёт. Полный запуск тестов выбирается по риску и цели, а не автоматически из слова «актуализация»; внешние/платные действия не получают новое разрешение.

Выход отвечает на четыре вопроса: что сейчас подтверждено; где расхождения; что исправлено; чего мы не знаем и как это проверить. Активные планы и следующие действия показываются ссылками на источники. Отчёт — снимок обследования, не постоянная копия состояния проекта и не новый диспетчер задач.

## 11. Бюджеты и покрытие контекстом

Оцениваются три уровня: цепочка применимых AGENTS; документы маршрута конкретной задачи; архив вне обычной загрузки. Бюджет каждого документа не заменяет бюджет совокупного маршрута. Базовые поля реестра учитывают размер, роль, область, связи, дату/событие проверки и причины выбранного диапазона.

Начальное предложение строится на значимых компонентах, связях и типовых задачах, затем согласуется автором при init. Агент может менять current внутри согласованного диапазона; базу и ceiling меняет только после решения автора. До/после пересмотра сохраняются измерения и основания; накопленный рост не обнуляется. Сначала рассматриваются удаление повторов и вынос самостоятельной области по согласованным правилам.

Строки и байты считаются точно; токены считаются доступным подходящим токенизатором или показываются как оценка с методом. Неизвестный полный контекст сеанса не заменяется фиктивным «осталось 40%». Сигналы качества не сводятся в единый балл: размер, целостность, смысловая проверка и полнота карты областей имеют разные статусы.

При изменении связанных файлов последняя смысловая проверка становится кандидатом на пересмотр, а не доказанно ложной. Изменение README не инвалидирует автоматически весь набор тестов. При этом изменение общего инварианта требует расширить область, даже если размер файла уменьшился.

## 12. BDD, OpenSpec и настоящие доказательства

BDD-часть использует реальную бизнес-логику через быстрые локальные проверки. Часы, внешние сервисы, случайность и хранилища заменяются управляемыми границами там, где это обосновано; сама проверяемая логика не заменяется её копией в тесте. Интеграционные и браузерные проверки остаются для внешних контрактов. Качество LLM проверяется отдельными eval-наборами.

High Grade не обещает тысячи сценариев в секунду. Измеряются отдельно обнаружение, подготовка, исполнение, объём сценариев и типы проверок; холодный/повторный запуск не смешиваются. Выбор архитектуры определяется проверяемостью правил, а не целью набить счётчик спек.

OpenSpec владеет specs и артефактами changes; его design описывает реализацию изменения, tasks — задачи. Для долгоживущих причин выбора создаётся ADR со ссылками, для текущего устройства обновляется ARCHITECTURE. Важно: штатный archive OpenSpec может применять дельты к основным спекам. [Источник](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md).

Предлагается сохранить стандартную схему OpenSpec, добавив минимальные ссылки в openspec/config.yaml, не форкать движок и не вводить собственный параллельный формат спек. Конфигурация поддерживает контекст и правила артефактов; они направляют к ENGINEERING/AGENTS, не копируют их содержание. Возможности конкретной версии проверяются до генерации. [Источник](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/customization.md).

По принятому [WF-TRACE-01](../workflow/SPECIFICATION.md) ссылки на требования и сценарии записываются в тестах, карта связей собирается автоматически. Отдельный ручной реестр этих связей исключён. Для стороны OpenSpec предлагаются стабильные ID в названиях сценариев, совместимые с выбранной схемой; конкретная конвенция и отметки штатных тестов ещё обсуждаются. Конвенция ID должна пройти проверку OpenSpec на создании, изменении и архивировании. Переименование текста при сохранённом ID не должно рвать связь; удаление сценария, дубль ID или повторное использование старого ID обнаруживаются.

По принятому [WF-TRACE-02](../workflow/SPECIFICATION.md) до первого выпуска схема проверяется на штатных тестах Rust и Playwright Test. Выбор средства запуска/отчёта Rust и конкретного синтаксиса отметок остаётся открытым; принцип отметок принят в WF-TRACE-03. Эта пара не навязывается целевым проектам; реализации и результатов испытаний пока нет.

По принятому [WF-TRACE-03](../workflow/SPECIFICATION.md) первая версия извлекает отдельные отметки рядом с тестами; имена тестов свободные. Комментарии Rust и аннотации Playwright — кандидаты синтаксиса, требующие проверки извлечения и сопоставления с отчётами. Позднее запланирована программная обёртка наподобие Covers поверх штатных инструментов. Она сохраняет ID сценариев, не вводит универсальный BDD-движок и не является условием первого выпуска.

По принятому [WF-EVIDENCE-01](../workflow/SPECIFICATION.md) исходный машинный отчёт сохраняется вместе с компактной записью команды, области, состояния кода, времени, инструмента и ссылки на отчёт. Чтение отчётов отделяется от сопоставления тестов со сценариями; общие статусы имеют единый смысл. Отсутствие результата не доказывает отсутствие запуска. Полный единый отчёт по тестам остаётся условным развитием по потребности, без изменения отметок требований ради формата отчётности.

Адаптер проекта получает от его тестового инструмента инвентарь выбранных тестов и результаты с состояниями passed/failed/skipped/not-run. Только существования файла недостаточно. Если адаптер не может подтвердить сбор/исполнение, статус unknown; отчёт общего процесса «exit 0» не подтверждает каждый сценарий. Ручная проверка хранит кто/что/когда/какое состояние проверил, а не выдуманный test pass.

Сценарии активного изменения проверяются вместе с относящимися действующими спеками; будущие дельты не объявляются уже внедрёнными. Пробелы D22 применяются только к согласованному исходному состоянию. Модификация исключённого сценария требует новой проверки; падение теста не создаёт исключение.

## 13. Архив и временные решения

По принятому [WF-ARCHIVE-01](../workflow/SPECIFICATION.md) отдельного архиватора нет. Агент сохраняет восстанавливаемое исходное состояние, проверяет границы и коллизии, перемещает подтверждённые материалы штатными средствами и обновляет ссылки. Общие проверки контролируют сохранность и связи. Ошибка оставляет операцию незавершённой; агент исправляет перенос или восстанавливает собственные изменения без потери чужих правок. Конкретный формат записи операции ещё обсуждается.

Архивирование завершённого OpenSpec-изменения делегируется проверенной штатной процедуре OpenSpec после подтверждения задач и доказательств. Агент не подменяет её простой операцией move. Перед вызовом сохраняются manifest и снимки затрагиваемых specs/change; после проверяются перенесённые дельты, статус change и ссылки. При частичной неудаче восстановление ограничено этими снимками и проверкой отсутствия чужой правки; успешное завершение не заявляется. Совместимость такого восстановления с выбранной версией OpenSpec входит в P5. Отклонённый/отменённый change не направляется в обычный archive с применением дельт: сохраняется как исторический материал с явным статусом и без изменения действующих specs. Для первой реализации возможен отдельный manifest переноса в docs/archive/rejected-changes; после него проверяется неизменность основных specs.

Заменённый ADR обычно остаётся на прежнем пути со статусом superseded и ссылкой на замену. Физический перенос не нужен, если ломает устойчивые ссылки. Код удалённой функции сохраняет Git; архивирование документа не разрешает удалить функцию. Большие артефакты сохраняются по явной политике проекта, не добавляются все подряд в Git.

Временный обход не исчезает из контроля вместе с закрытой задачей. Условие пересмотра проверяется при затронутой работе и при refresh; истечение срока вызывает обзор, не автоматическое удаление кода. Продление явно объясняется; если меняются требования или гарантии, нужно новое решение автора. Поиск try/except и слова fallback выдаёт кандидатов для анализа, не запреты.

## 14. Добровольное обновление и восстановление

Первый выпуск поддерживает автоматическое переключение только совместимых поставок: тот же протокол входных навыков/загрузчика и читаемая обоими выпусками адаптация. Несовместимая миграция не запускается автоматически: возвращается конкретный план отдельного преобразования, старая версия продолжает работать. Это ограничение первого механизма, а не разрешение отказаться от D21.

Структурная совместимость необходима, но недостаточна. До активации агент сопоставляет diff новых общих правил с действующими AGENTS, ENGINEERING, архитектурными решениями и проектными исключениями. Смысловой конфликт блокирует кандидат по D21 даже при неизменной JSON-схеме; новые существенные решения согласуются автором. Итог проверки содержит рассмотренную область, правила кандидата и хеши проверенной адаптации. CLI activate требует эту запись без незакрытых конфликтов и проверяет актуальность её входов; он не выдаёт наличие записи за автоматическое доказательство правильности смыслового анализа. Неизвестная совместимость не считается совместимостью. Если согласованное разрешение конфликта требует изменения адаптации, оно выполняется отдельным проверяемым преобразованием до активации с сохранением работоспособности прежней основы.

```text
локальный пакет -> проверка manifest и форматов -> отдельный releases/<candidate>
              -> смысловая совместимость с адаптацией + проверки кандидата
                 с явным release-id, без смены active
              -> повтор проверки хешей адаптации и старого active
              -> атомарная замена маленького active.json
              -> постпроверка; при её неудаче возврат прежнего указателя
```

Содержимое проекта и адаптация не переписываются этой операцией. До активации candidate не используется повседневной работой. Старый release не удаляется в ходе update. Контрольная сумма доказывает целостность относительно полученного manifest, а не доверенность неизвестного источника; пакет берётся из явно выбранного автором источника.

Для архивирования и update — локальная блокировка на изменяющую операцию, журнал, хеши до/после и отказ от перезаписи при конфликте. Все наши writers соблюдают блокировку. Внешние редакторы её не обязаны соблюдать: поэтому update проводится при отсутствии активной работы в этом проекте, а непосредственно перед активацией сверяются затронутые файлы. Нельзя обещать строгую транзакцию между произвольными несотрудничающими процессами. Риск проверяется тестами и объясняется при конфликте.

Прерывание до переключения оставляет прежний active; после переключения journal позволяет различить завершённое переключение и незавершённую постпроверку. Восстановление проверяет реальное состояние, а не удаляет lock по возрасту. Для уже выполняющейся задачи release-id фиксируется в начале операции; смена active не подменяет правила посередине неё. Новая сессия загружает новую основу; уже прочитанный контекст не считается магически обновлённым.

Bootstrap и стабильные адаптеры не заменяются обычным совместимым update. Их новая несовместимая версия требует отдельного плана установки с сохранением старой. На Windows запрещены обходы через junction за пределы проекта, небезопасная распаковка ../, коллизии регистра и destructive reset чужих изменений.

## 15. Ошибки и проверяемые границы

| Сбой | Реакция и что видит пользователь |
|---|---|
| Нет CLI подходящей сборки либо внешней зависимости, включая среду OpenSpec | Doctor, если доступен, либо входная процедура показывает недостающий компонент; ничего не устанавливает |
| Не найдена основа / повреждён manifest | Конкретный сбой загрузки; инструкции не берутся молча из другой установки |
| Не прочитана часть проекта | Отчёт partial/unknown с областью; никакого «всё актуально» |
| Превышен бюджет | Warning, причина, текущий диапазон и пересмотр по D27 |
| Обнаружено смысловое противоречие | Доказательство и зависимая область по D28; исправление в границах или вопрос автору |
| Тест отсутствует/пропущен/результат устарел | Раздельные статусы; не считается успешным исполнением |
| Архивирование прервано | Агент проверяет фактическое состояние и восстанавливает собственные изменения; конфликт с чужими правками виден |
| Кандидат несовместим / не прошёл проверки | Прежний active; новый пакет не активирован |

Не ведём транскрипты пользователя ради диагностики, не отправляем проектные файлы в High Grade. CLI не читает соседние проекты. Проектные команды проверок являются исполняемым кодом: они запускаются только в разрешённой среде и области. Диагностика наличия команды не запускает её потенциально изменяющий сценарий.

## 16. Проверка первой реализации

| Группа | Обязательный наблюдаемый результат |
|---|---|
| Новый/готовый проект | Init даёт подходящий план; посторонний AGENTS и изменения сохранены; обязанности пяти документов распределены; обрыв первой установки восстанавливается без потери последующих чужих правок |
| Оба интерфейса | Чистая установка, обнаружение каждого навыка, нужная процедура и продолжение задачи отдельно в приложении/CLI на Windows |
| Обычная задача | Без вызова refresh обновляются документы, исполняются проверки, архивируется завершённое, учтён временный обход |
| Актуализация | По запросу находит заранее внесённые расхождения; режим анализа не меняет файлы; отчёт обозначает неизвестное |
| Бюджеты | Несколько повышений не обходят ceiling; размер остаётся warning; потеря требования при сжатии обнаруживается смысловой проверкой |
| Связи и тесты | Удалённый/пропущенный тест, пустой suite, дубли ID, изменённый исключённый сценарий, устаревший результат не проходят как verified |
| Архив | Разрыв ссылки, коллизия и прерывание восстанавливаемы; отклонённый OpenSpec change не меняет текущие specs |
| Обновление | Конфликт, некорректный пакет, обрыв и postcheck failure сохраняют/восстанавливают прежнюю основу без потери адаптации; кандидат с тем же форматом, но противоречащим ENGINEERING правилом не активируется |
| Windows | Пути с пробелами/кириллицей, CRLF, регистр, файл занят, junction за границу; нет обязательного Bash/Bun/Python |
| Независимость | Нет gstack и авторского профиля; сеть отключена после установки; проект продолжает работать |

Статические тесты проверяют CLI и форматы. Поведение навыков проверяется настоящими сессиями с заранее подготовленными случаями, включая «не запускай актуализацию» и «ничего не меняй». Тесты не объявляют смысловую безошибочность; независимый обзор оценивает конкретные результаты. До этих проверок не заявляется совместимость с произвольными версиями Codex/OpenSpec.

## 17. Возможная последовательность будущей реализации

По принятому [WF-RELEASE-01](../workflow/SPECIFICATION.md) выпуск workflow не ожидает миграций SVG и CHA. Их отдельные планы не входят в зависимость P1–P6; текущее смешение языков допустимо до завершения миграций.

1. **P1 — совместимость и подключение.** Маленький прототип загрузчика и одного навыка, определение поддерживаемых версий, проверка в обоих интерфейсах. Результат: переносимая установка и однозначный выбор основы. Остальная реализация опирается на это доказательство.
2. **P2 — реестры и диагностика.** settings/documents, doctor/inspect, JSON-отчёт, пути Windows, отсутствие скрытых изменений. Результат: воспроизводимые измерения без выводов о смысле.
3. **P3 — рабочие процедуры.** Init/work/refresh, пять документов, штатное сопровождение, минимальное состояние и ограниченная автономность. Результат: две показательные задачи на новом и готовом проекте.
4. **P4 — поведенческие доказательства.** OpenSpec-интеграция, стабильные IDs и один реальный проектный тестовый адаптер, затем второй стек как проверка переносимости. Не строить каталог адаптеров до потребности.
5. **P5 — архив и update.** Процедура архивирования агентом с общими проверками, различение завершённых и отвергнутых changes; для update — проверяемое переключение и сохранение старой основы. Отдельные проверки отказов и конкурентных правок.
6. **P6 — испытание выпуска.** Полная матрица применимых проверок, лицензии/инструкции и подтверждение штатного сопровождения без хуков. Повторяющиеся пропуски фиксируются как основания пересмотра WF-HOOKS-01; хук не входит в первый выпуск.

Это план будущей реализации, не текущие выполненные задачи. Точки P1/P5 могут выявить необходимость изменить упаковку; такую находку следует показать до расширения объёма. Не требуется повторно согласовывать каждое имя файла, но изменение принятых границ D1–D33 возвращается автору.


## Статус проверки

Прежняя проверка относится к архивному оригиналу. Текущая организация проверяется в [отчёте](../reviews/project-organization-review.md). Реализация, установки, совместимость и поведение будущих инструментов не проверены.
