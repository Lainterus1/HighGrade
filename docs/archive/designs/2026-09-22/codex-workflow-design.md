# Переносимый workflow для Codex

Дата: 2026-09-22. Версия документа: 0.6.
Статус: D1–D30, D32 и D33-A согласованы; тема версионирования снята автором; технические механизмы обсуждаются; техническая реализация не проверена.
Режим: SELECTIVE EXPANSION.
Документ фиксирует решения текущего разговора. Он не означает создания, установки или публикации workflow.

## Цель и границы

Создать распространяемый через GitHub workflow для работы Codex внутри конкретного проекта. Он применяется как при создании нового проекта, так и при преобразовании существующего. Репозиторий разработки workflow (MyCodex) служит для улучшения и выпуска самого workflow, а не для управления целевыми проектами.

Пользователь проекта задаёт замысел, ограничения и предпочтения ведения работы. Workflow помогает сформировать архитектуру под эти потребности, выполнять изменения и получать проверяемый результат. Общая основа не зависит от личной установки автора. Публикация на GitHub предполагается в будущем; текущая задача — проектирование, не публикация.

Признаки полезности: меньше повторного объяснения контекста; требования связаны с проверками; следующий исполнитель может продолжить работу; обновление не уничтожает проектные решения. Количество файлов, навыков, токенов или сценариев в секунду не является самостоятельным критерием качества.

## Что уже существует и переиспользуется

- Исследование подхода Рината Абдуллина в текущем разговоре: требования, событийные сценарии, быстрые проверки, дерево документов и небольшие проверяемые изменения. Последняя версия его BDD-движка не исследована по исходникам; заявленная скорость не является нашей гарантией.
- OpenSpec: требования, изменения, задачи. Это выбранный внешний компонент, а не предложение заменить его собственным аналогом.
- Текущий подход plan-and-run-goal: продолжение многоэтапной работы, минимальное состояние, проверки доказательств. Переносимая процедура должна входить в распространяемую основу; ссылка на личный путь автора недопустима как обязательная зависимость.
- Команды, тесты и документация целевого проекта: обследуются и переиспользуются при преобразовании.
- gstack: используется для нынешнего проектирования. Установка gstack у потребителя не требуется.

## Инициализация

Инициализатор сначала изучает доступный контекст, затем спрашивает только то, что действительно меняет решение. Он не задаёт заранее фиксированную длинную анкету и не требует повторять уже известное.

Области интервью: назначение и успех продукта; поведение и последствия ошибок; стек, интеграции, данные и ограничения; организация работы; автономность агента; поддержка и восстановление.

```text
Замысел + существующие материалы, если они есть
                   |
             обследование
                   |
     недостающие существенные решения -> интервью
                   |
      применение архитектурных принципов
                   |
      устройство + причины + план + проверки
                   |
        согласование результата автором
                   |
       передача в общий процесс выполнения
```

Новый проект получает минимальную согласованную основу. Существующий — план преобразования, учитывающий действующие контракты, код, тесты и документы. Реализованное поведение не считается автоматически правильным: конфликт с требованиями должен быть обозначен.

Инициализатор не должен самостоятельно менять продуктовые решения под удобную архитектуру. Существенные выборы делает автор; локальные детали в согласованных границах выбирает исполнитель.

## Выполнение и автономность

Небольшая задача выполняется за один проход. Многоэтапная работа использует минимальное состояние продолжения. Задачи OpenSpec не копируются в независимый список другого инструмента. Наличие сложной задачи само по себе не является запросом на запуск Goal.

Агент самостоятельно выбирает локальные детали, устраняет ошибки и выполняет необходимые проверки в согласованной области. Изменение продуктового поведения, объёма, существенных зависимостей, расходов или эксплуатационных обязательств возвращается автору, если оно не было уже разрешено. Полученные разрешения не спрашиваются повторно. Обсуждение, техническая проверка, публикация и пользовательская приёмка не подменяют друг друга.

## Поведенческие проверки и прослеживаемость

Сценарий описывает исходную ситуацию, действие и наблюдаемый результат. Исполняется настоящая логика приложения. Внешние эффекты изолируются там, где иначе проверка ненадёжна или слишком дорога. Интеграционные и браузерные проверки сохраняются для свойств, которых такая изоляция не доказывает. Качество LLM оценивается отдельно от детерминированных правил приложения.

```text
Требование -> сценарий -> исполняемая проверка -> результат запуска
                  |                 |
                  +--- проверка связей ---+
```

Проверка связей обнаруживает сценарии без предусмотренной проверки, устаревшие ссылки, дубли идентификаторов и отключённые обязательные проверки. Она не доказывает смысловую правильность тестов. Явная ручная проверка допустима там, где она предусмотрена; её наличие не означает, что она проведена.

По D22 при подключении готового проекта составляется конкретный список непокрытых сценариев. Автор согласует, какие исходные пробелы временно сохраняются. Новые и изменяемые сценарии должны получать предусмотренные проверки. Исключение относится к конкретному сценарию, а не ко всей папке. Пробелы не увеличиваются незаметно: новое исключение не может появиться как автоматическое следствие неуспешного запуска.

Отчёт отдельно показывает результат текущего изменения и оставшиеся исходные пробелы. Согласованный пробел не делает упавший тест успешным и не разрешает автоматически отключать проверки. Работу над изменением можно подтвердить в её границах, но весь проект нельзя объявить полностью проверенным при наличии пробелов.

Проверяемые следствия D13/D22: согласованный старый пробел остаётся в отчёте; новый сценарий без проверки обнаруживается; изменение ранее исключённого сценария требует предусмотренной проверки; устаревшая ссылка или удалённый тест обнаруживаются; падение теста не переписывает список исключений. Это критерии будущей проверки реализации, а не проведённые тесты.

## Диагностика готовности

Локальное действие проверяет готовность окружения, необходимых сервисов и применимых команд, доступность обязательных проверок. Отчёт различает готовность, проблему и невозможность проверки. Диагностика не заменяет полный прогон тестов, не устанавливает зависимости и не изменяет окружение автоматически. Значения секретов не выводятся.

Конкретный набор проверок и способы вызова определяются при инициализации. Переиспользуются существующие средства проекта; новая тяжёлая инфраструктура ради диагностики не требуется.

## Добровольные обновления

Проект сохраняет выбранную версию общей основы. Обновление выполняется по запросу, показывает изменения и конфликты, сохраняет проектные решения и проверяет совместимость. Общие файлы и проектная адаптация находятся в разных областях.

```text
Работа на выбранной версии
          |
    запрос обновления
          v
Сравнение версий и проектной адаптации
          |
    конфликты видимы
          |
    согласованное совместимое решение
          v
Проверка обновления -> успех -> активация новой версии
          |
          +-- конфликт / отказ / неуспех -> прежняя версия остаётся рабочей
```

Разделение файлов само по себе не гарантирует смысловую совместимость: новое общее правило может противоречить прежней адаптации. По D21 агент показывает конкретный конфликт, предлагает необходимую адаптацию и способ её проверки. Новая версия становится рабочей только после согласования совместимого решения и успешной проверки. При отказе, неразрешённом конфликте или неуспешной проверке прежняя версия остаётся рабочей. Автоматическое переписывание проектных правил и активация заведомо несовместимого сочетания не допускаются. Технический механизм подготовки обновления и сохранения прежней версии предстоит определить при инженерной проработке.

## Локальная обратная связь

Замечания к workflow сохраняются в специализированной области целевого проекта. Пример имени — workflow-feedback; точный путь пока не выбран.

Запись содержит версию workflow и процедуру; ожидаемое и фактическое поведение; подтверждение или локальную ссылку; причину либо помеченную гипотезу; локальное исправление и проверку; предложение для общей основы, если оно известно.

Ошибки приложения остаются в проекте, особенности адаптации — в адаптации, недостатки общей процедуры могут быть предложены для разбора в MyCodex. Автоматической передачи, телеметрии, создания GitHub issues или доступа к соседним проектам нет. Экспорт возможен по желанию пользователя; локальные ссылки сами по себе не делают переносимую запись самодостаточной.

## Не входит в состав

- Централизованное управление целевыми проектами и общий реестр их состояния: прямо исключены пользователем.
- Автоматический обход соседних репозиториев и перенос решений между ними: не соответствует назначению этого проекта.
- Собственный универсальный BDD-движок и обязательный Gherkin: выбран существующий тестовый стек проекта.
- Одна структура исходников, фиксированные архитектурные категории, обязательные микросервисы или event sourcing: выбран каркас по потребностям автора.
- Обязательная установка gstack и зависимость от личных навыков автора: выбрана самостоятельная основа.
- Автоматические обновления и отправка обратной связи: выбрана добровольность.
- Новая панель управления, сервер координации или фоновый сервис: не выбраны.
- Поддержка Linux и macOS в первой версии: по D23 сначала подтверждается Windows; переносимость архитектуры не считается доказательством работы на других системах.
- Реализация, установка в рабочие проекты, push и публикация в рамках текущего обсуждения: сейчас проектирование.

## Подробный разбор концепции

### 1. Архитектура

Границы ответственности согласованы: MyCodex разрабатывает workflow; целевой проект содержит выбранную общую основу, адаптацию и свои требования. Инициализатор передаёт согласованный план исполнителю. OpenSpec владеет задачами изменения поведения. Дублирующих диспетчеров, общих реестров проектов и обязательного gstack нет.

```text
Автор -> инициализатор -> согласованное устройство -> исполнитель
                  ^                              |
                  |                              v
           контекст проекта              код + документы + тесты
                                                 |
                                    проверяемый локальный результат
```

При росте числа проектов нет центрального сервиса, который станет узким местом. При росте числа сценариев растут локальные затраты на их обнаружение, исполнение и просмотр. Предусмотрены существующие инструменты проекта и загрузка нужного контекста по ссылкам. Полное повторное чтение всех документов на каждой задаче не требуется.

Единственная точка принятия существенных продуктовых решений — автор проекта. Его отсутствие не разрешает агенту менять требования. Работа внутри уже согласованного результата продолжается согласно D12.

Новых противоречий в архитектурных границах не найдено. Физическое разделение обновлений дополнено D21; его техническое обеспечение подлежит инженерной проработке.

### 2. Ошибки и восстановление

Коды ниже — имена классов ситуаций для проектирования, не существующие классы исключений программы. Реальные исключения и способ сериализации ошибок определяются после выбора реализации.

| Операция | Ситуация | Код ситуации | Основание реакции | Что должен видеть пользователь |
|---|---|---|---|---|
| Интервью | Нет ответа на существенный вопрос | CONTEXT_MISSING | D9/D12: не принимать существенное решение за автора | Конкретный вопрос и зависимая часть плана |
| Обследование | Нет ожидаемого документа | CONTEXT_NOT_FOUND | Сначала обследование, затем вопросы; отсутствие не считать подтверждением | Что отсутствует и зачем это нужно |
| Обследование | Документ существует, но недоступен | CONTEXT_UNREADABLE | Не делать вид, что документ прочитан | Причина недоступности и непроверенный вывод |
| Диагностика | Нет зависимости или сервиса | ENVIRONMENT_UNAVAILABLE | D14: диагностика без автоматических изменений | Блокер и инструкция по подготовке |
| Проверка связей | Нет теста, устарела ссылка, повторён ID | TRACEABILITY_INVALID | D13/D22: обнаружить, не замаскировать старым исключением | Конкретный сценарий и проблема связи |
| Запуск проверки | Тест упал | CHECK_FAILED | D22: не делать падение успешным | Проверка, наблюдаемое отличие, команда воспроизведения |
| Запуск проверки | Обязательная проверка пропущена или не запустилась | CHECK_NOT_EXECUTED | D13/D14/D22: не выдавать отсутствие доказательства за успех | Проверка и причина отсутствия результата |
| Продолжение работы | Сохранённый результат относится к старому состоянию | EVIDENCE_STALE | Принятый подход выполнения проверяет фактическое состояние | Что больше не подтверждено и что перепроверить |
| Обновление | Новое правило конфликтует с адаптацией | UPDATE_CONFLICT | D21: новая версия не активируется | Конфликт и согласуемый вариант адаптации |
| Обновление | Проверка кандидата не прошла | UPDATE_CHECK_FAILED | D21: рабочей остаётся прежняя версия | Неудача обновления, версия, которая остаётся рабочей |
| Запись замечания | Нельзя сохранить запись | FEEDBACK_WRITE_FAILED | D19: не утверждать, что запись сохранена | Неудача записи и подготовленный текст |

Автоматические повторы внешних действий и молчаливые исправления требований из этих правил не следуют. Запись диагностических сведений не должна раскрывать секреты. Для каждой ситуации будущая реализация должна проверять не только внутренний помощник, но и действие, вызываемое пользователем.

Отдельно требуется технически проверить прерывание изменяющих операций и конкурентные изменения файлов: гарантии D20/D21 не являются доказательством того, что конкретный механизм записи их выполняет.

### 3. Безопасность

Новых серверных API, учётных записей и централизованного доступа не предусмотрено. Основные границы — локальная файловая система, исполнение проектных команд, материалы целевого проекта и источник обновления.

| Риск | Вероятность / влияние | Принятое ограничение или обязанность реализации |
|---|---|---|
| Секрет в диагностике | Средняя / высокое | D14: значения секретов не выводятся |
| Автоматическая отправка проектных данных | Средняя / высокое | D19: автоматической передачи нет |
| Перезапись адаптации | Средняя / высокое | D20/D21: отдельные области, совместимость до активации |
| Изменения вне согласованного проекта | Средняя / высокое | D12/D15: локальная область работы, нет управления соседними проектами |
| Скрытая зависимость от установки автора | Высокая / среднее | D18: самостоятельная поставка и проверка в чистом окружении |
| Несоблюдение лицензии заимствованного компонента | Средняя / высокое | D18: проверка происхождения и условий до распространения |

Применение файлов из произвольных путей, смешивание данных интервью с исполняемой командой, обход области записи через ссылки и доверие инструкциям из исходного проекта требуют инженерной проверки. Существующие системные правила и разрешения Codex не переопределяются профилем workflow.

Процесс добровольного извлечения feedback не должен автоматически превращаться в отправку материалов на GitHub. Пользователь определяет содержимое передачи.

### 4. Потоки данных и прерывания

```text
Контекст -> обследование -> интервью -> решения -> план
    |           |             |           |        |
 отсутствует  недоступен    нет ответа   конфликт  не согласован
    +-----------+-------------+-----------+--------+
              видимое ограничение; нет выдуманного успеха
```

Пустой новый проект является допустимым входом. Нечитаемый существующий проект не равен пустому. Пустой список тестов не равен успешному выполнению предусмотренных проверок. Отсутствие согласованных старых исключений не означает разрешения автоматически добавлять новые.

```text
Замысел -> уточняется -> согласованный план -> выполнение -> проверка
               ^               |                |             |
               +-- новый существенный выбор ---+          результат
```

Состояние «проверено» требует фактического результата. Состояние «план согласован» не является состоянием «реализовано». Повторный вход должен использовать принятые решения и фактическое состояние проекта, а не начинать интервью заново.

Обновление и текущая работа над адаптацией могут пересекаться:

```text
Обновление                 Другая работа              Состояние
прочитать адаптацию v1                                v1
                           сохранить адаптацию v2     v2
попытаться активировать
по проверке адаптации v1                              риск устаревшей проверки
```

Обратный порядок также проверяется: кандидат готов, затем адаптация изменяется до активации. Механизм предотвращения такого нарушения пока не выбран; последовательный код сам по себе не предотвращает изменение другим процессом. Это инженерная обязанность сохранения адаптации, а не разрешение вводить централизованный сервис.

### 5. Качество и простота

Ответственность документов разделена; полный план не копируется между OpenSpec и исполнителем. Общая основа не содержит пути или учётные записи автора. Проектная структура определяется интервью, а не классификатором фиксированных архитектур.

Небольшие адаптированные компоненты допустимы, но не означают разрешения переписать OpenSpec или каждый используемый тестовый инструмент. Свою инфраструктуру добавляем только при подтверждённой потребности. Формат пакета, язык вспомогательных скриптов и названия команд ещё не выбраны; при реализации действует согласованный принцип минимальных зависимостей.

Кода для оценки сложности функций, дублирования реализации и обработки конкретных исключений пока нет. Проверены границы проектируемых обязанностей, а не качество несуществующей реализации.

Быстрые детерминированные проверки проверяют служебную логику. Проверки в подготовленных проектах подтверждают действие целиком. Поведение интервью и качество архитектурного предложения требуют отдельных наблюдений в сессиях агента; статическая проверка Markdown их не заменяет. Начальные контрольные случаи следует сохранять для сравнения при изменении процедур, а не судить об улучшении по самооценке агента.

Главная проверка перед выпуском: новый пользователь получает согласованный план в чистом Windows-окружении, а добровольное обновление сохраняет адаптацию при конфликте и прерывании. Наиболее опасный отрицательный сценарий: команда успешна, но обязательные тесты не выполнились. Проверка отказоустойчивости: прервать обновление между подготовкой и активацией, затем продолжить работу на прежней версии.

Это будущие критерии, не уже выполненные тесты. Целевая частота сценариев в секунду не задана.

### 7. Производительность

Три потенциально дорогие операции: первичное обследование большого репозитория, обнаружение тестов, фактическая регрессия приложения. Требование быстрой обратной связи не разрешает пропускать обязательные проверки. Длительные проверки отделяются от короткой диагностики, а выполненные проверки не повторяются без изменения или нового сомнения в доказательствах.

Нет нового сервера, БД, очереди или пула соединений workflow; рекомендации по их индексам и масштабированию здесь неприменимы. Размер контекста и результаты команд следует ограничивать релевантными материалами. Численные p99, объёмы памяти и скорость без реализации и замеров неизвестны; обещания не даются.

### 8. Наблюдаемость

Достаточные сведения для каждой операции: что выполнялось, к какому проекту и версии workflow относится результат, какие проверки прошли, какие отсутствуют, что блокирует следующий шаг. Старые пробелы, ошибка текущего изменения и сбой окружения различимы.

Локальная запись feedback служит разбору недостатков самого workflow; она не заменяет диагностику приложения. Не нужны центральные панели, телеметрия или оповещения: они исключены границами продукта. При невозможности сохранить отчёт нельзя утверждать, что он сохранён.

Проверки выполняются до заявления об успешной активации. Стратегия возврата не может означать сброс чужих изменений репозитория.

Точный дистрибутив, команды установки и матрица совместимости Codex/OpenSpec требуют инженерной проверки. Поддержка Windows согласована; Linux/macOS не входят в первую версию. В текущей задаче ничего не публикуется и не устанавливается.

### 10. Сопровождение

Риск сопровождения сосредоточен в стыках с Codex, OpenSpec и тестовым стеком проекта. Их версии и возможности должны быть проверены перед заявлением совместимости, а не выведены из существования файлов. Минимальные зависимости уменьшают внешний объём, но адаптированный код всё равно требует поддержки.

Разделение основы, адаптации и необязательного профиля упрощает объяснение новому пользователю. Сама концепция обратима; конкретная миграция исходников может быть значительно менее обратимой и требует собственного плана. Общая оценка обратимости концепции: 4/5; это не гарантия отката любой миграции приложения.

Принятые дополнения поддерживают основную цель. Исключённый control center не является скрытой зависимостью ни для обновлений, ни для извлечения feedback. Для обратной связи достаточно добровольного переноса записей.

### 11. Пользовательский путь

Отдельного графического интерфейса нет. Пользователь взаимодействует через разговор и документы. Сначала он видит понятую цель, затем существенные выборы, затем конкретное предлагаемое устройство. Подробный процесс обсуждения этого стандарта не должен становиться обязательным количеством вопросов при каждой инициализации.

            |                   |                    v
