# Контекст, документация и временные решения

Дата: 2026-09-22. Статус: решения D25–D30, D32 и D33-A приняты; тема версионирования снята автором; технические механизмы остаются предложениями, реализации нет.
Дополнение к codex-workflow-design.md v0.6. Ранее принятые D1–D24 сохраняются.

## Запрос автора

Включить в workflow поддержание качественного контекста и документации; согласованный универсальный набор документов с разделённой ответственностью; создание дополнительных документов отдельным решением; измерение размеров и сигналы риска; динамический пересмотр бюджетов; правила оформления; контроль накопления временных обходных решений; архив устаревших материалов и результатов гипотез. Реализация может использовать скрипты, навыки и хуки, но их состав пока не выбран.

## 1. Что считаем качественным контекстом

Размер — один показатель, а не гарантия безопасной работы. Короткий документ может противоречить коду; большой архив не опасен, если он не попадает в обычный маршрут чтения. Контроль должен отдельно отвечать:

- Можно ли найти действующее правило и понять, какой источник главный?
- Совпадает ли описание с существенным поведением и устройством проекта?
- Покрыты ли важные области проекта документацией и проверками?
- Какой объём надо прочитать для конкретного класса задач?
- Остались ли устаревшие решения, исключения и обходные пути без пересмотра?

Предлагается говорить о риске недостаточного/избыточного контекста, а не о математически доказанной безопасной зоне. Неизвестный показатель обозначается как неизвестный. Документальная полнота не заменяет тестовое покрытие и смысловую проверку D13.

## 2. Принятый состав документов — D25

Пять обязательных документов плюс машинный реестр: README, AGENTS, ARCHITECTURE, ENGINEERING, DEVELOPMENT. OpenSpec и задачи сохраняют ранее выбранные роли. Дополнительные семейства включаются по потребности отдельным решением; их назначение приведено ниже. Точные пути и формат реестра определяются технически.

| Документ | Единственная основная ответственность | Что сюда не переносится |
|---|---|---|
| README.md | Назначение проекта, границы продукта и навигация по актуальным источникам | Полные требования, инструкции агенту, повтор команд |
| AGENTS.md | Правила работы агента, границы полномочий и маршруты чтения по задачам | Подробная архитектура, журнал работы, копии общих инструкций workflow |
| ARCHITECTURE.md | Текущее устройство, границы компонентов, потоки данных и инварианты | Пошаговая установка, история всех попыток, задачи |
| ENGINEERING.md | Инженерные соглашения: обработка ошибок, тестируемость, зависимости, совместимость и критерии качества изменений | Текущее устройство системы, команды запуска и продуктовые сценарии |
| DEVELOPMENT.md | Воспроизводимые процедуры подготовки, запуска и проверок; эксплуатационные процедуры в применимой части | Требования к продукту, архитектурный трактат, сохранённые результаты каждого запуска |
| Машинный реестр документов и бюджетов | Роль, путь, область, режим чтения, бюджет, основание и условие пересмотра | Второй пересказ содержания документов |

Реестр не добавляет обязательный шестой текстовый обзор. Числа и правила диагностики хранятся в одном месте; отчёт генерируется. Точный формат реестра определяется технически.

README владеет замыслом и навигацией; OpenSpec — проверяемым поведением. ARCHITECTURE владеет действующей схемой; запись архитектурного решения при необходимости объясняет выбор и альтернативы. ENGINEERING владеет инженерными правилами и требованиями к проверкам; DEVELOPMENT — командами; AGENTS направляет к нужным источникам. Состояние выполнения содержит следующий шаг и ссылки на OpenSpec, а не новый список задач.

Дополнительные документы допускаются по отдельному решению: зачем нужен самостоятельный источник, кто отвечает за обновление, какая информация переносится, как исключается дублирование. После согласования семейства документов, например спецификаций OpenSpec, создание очередной записи в рамках этого семейства не должно само по себе запускать новое согласование устройства документации. Это трактовка для обсуждения, не молчаливо принятое исключение из запроса автора.

### Дополнительные семейства и ADR

ADR фиксирует причины значимого решения, альтернативы, последствия и условия пересмотра. Он нужен для решений с долгосрочным влиянием, дорогой отменой, существенными альтернативами или исключением из инженерных принципов, а не для каждой спецификации. OpenSpec описывает требуемое поведение; проектирование изменения — способ его реализации; ARCHITECTURE — действующее устройство. Между спеками и ADR возможны связи многие-ко-многим. Причины решения не копируются во все документы.

Принятый ADR сохраняет историю выбора. Новый ADR может заменить старый; старый получает статус и ссылку на замену, сохраняя устойчивую ссылку. Принятое решение ещё не доказывает, что оно реализовано: целевое и фактическое устройство различаются явно.

TESTING выделяется для самостоятельной стратегии тестирования; OPERATIONS/RUNBOOK — для эксплуатации и восстановления; SECURITY — для самостоятельных требований безопасности и модели угроз; CONTRIBUTING — для внешних участников; CHANGELOG — для изменений опубликованных версий; ROADMAP — для долгосрочных приоритетов. Их темы учитываются по применимости, но отдельные файлы не создаются без потребности. Общие принципы workflow не копируются в проектные документы: адаптация содержит конкретизацию и согласованные исключения.

### Сквозная согласованность — D26

Непротиворечивость проверяется для всей применимой системы документов, включая дополнительные семейства, локальные инструкции и общую основу workflow. Проверка охватывает соответствие коду, тестам и фактическим результатам. Она не ограничивается размерами или исправностью ссылок.

У каждого факта или правила есть основной источник в своей области ответственности. Универсальной иерархии «любой документ X всегда сильнее Y» нет: спецификация определяет требование, код показывает реализацию, тест — ограниченное доказательство. Расхождение между ними не устраняется автоматически переписыванием требований под код или признанием теста окончательной истиной.

При изменении определяется затронутая область и связанные источники; проверяются последствия для них. Общие инварианты и правила требуют более широкого просмотра, локальная правка не требует перечитывать весь архив. Полный применимый набор проверяется при инициализации и актуализации. В отчёте указываются область проверки, обнаруженные расхождения и то, что осталось непроверенным; нельзя заявлять глобальную согласованность по локальной проверке.

Расхождение описывается конкретно: конфликтующие положения и пути, влияние на работу, действующий или предлагаемый статус и вариант устранения. Очевидную рассинхронизацию после уже согласованного изменения агент исправляет в его границах. Если устранение требует нового продуктового или архитектурного выбора, применяется D12: зависимая часть работы ждёт решения, независимая может продолжаться. Более новый файл сам по себе не является разрешением менять правило. Конфликт не прячется в исключение или новый fallback.

Скрипт проверяет структуру, ссылки и известные машинные условия. Агент оценивает смысл и сопоставляет документы с кодом и проверками. Ни один из этих способов сам по себе не гарантирует отсутствия всех противоречий. Архивные и отклонённые материалы маркируются как исторические: отличие от действующего решения допустимо и не считается неразрешённым конфликтом.

Критерии будущей проверки: противоречивое правило в дополнительном документе обнаруживается; несогласованная новая версия не вытесняет действующее требование; принятое, но не реализованное ADR не выдаётся за текущую архитектуру; архивное решение не становится действующим; локальная проверка не даёт глобального статуса; исправление уже согласованной рассинхронизации не требует повторного разрешения.

## 3. Три уровня чтения

1. Постоянная точка входа: короткие инструкции и навигация.
2. Контекст задачи: нужные части архитектуры, процедуры, спецификации и код затрагиваемой области.
3. История: архив и заменённые решения, открываемые при расследовании или пересмотре.

Обязательность документа не означает обязательное полное чтение при каждом действии. Вложенный AGENTS допустим только при реальной локальной области ответственности; он не должен копировать корневой. Контроль учитывает применимую цепочку инструкций, а не только размеры файлов по отдельности.

## 4. Измерения и сигналы

| Сигнал | Что измеряет инструмент | Что требует оценки агента |
|---|---|---|
| Размер | Байты UTF-8, строки, токены или явно обозначенная оценка, изменение с последней проверки | Полезность и необходимость содержания |
| Загрузка | Цепочка применимых инструкций, размер заранее определённых маршрутов чтения | Достаточность маршрута для реальной задачи |
| Целостность | Отсутствующий файл, битая ссылка, повтор ID, ссылка из активного маршрута на заменённый документ | Противоречия между источниками |
| Актуальность | Изменения в связанных областях после проверки, истёкшее условие пересмотра | Устарело ли описание по смыслу |
| Покрытие | Области из карты проекта без назначенного источника/проверки | Полнота самой карты, существенность новой области |
| Временные решения | Просроченные записи и ссылки; кандидаты из diff/поиска | Является ли код допустимой деградацией или маскировкой ошибки |

Количество строк — вспомогательный показатель. Токены зависят от токенизатора; отчёт должен назвать метод подсчёта. Объём файлов не равен всему занятому контексту сеанса: есть история, инструменты, системные инструкции и вывод команд. При отсутствии доступа к этим данным нельзя выдавать оценку файлов за остаток окна модели.

Вместо одного общего процента предлагаются раздельные состояния: в пределах бюджета; нужен пересмотр; нарушен проверяемый контракт; не удалось проверить. Отчёт показывает затронутую область и причину. Зеленый размер не скрывает противоречия или неизвестное покрытие.

## 5. Динамический бюджет

Принято D27-B: при инициализации автор согласует рабочие бюджеты и диапазоны самостоятельного пересмотра, включая верхние границы. Агент может обоснованно менять рабочий бюджет внутри диапазона до следующего пересмотра. Выход за согласованный диапазон требует решения автора. Конкретные числа зависят от проекта и сейчас не назначены.

Измерения и сигналы автоматические. Удаление повторов, исправление ссылок и актуализация без изменения смысла выполняются самостоятельно в рамках задачи. Изменение ответственности документов не разрешается одним лишь увеличением бюджета.

Каждый пересмотр сохраняет прежний и новый бюджет, причину роста, рассмотренную возможность сокращения и условие следующей проверки. Накопленное изменение показывается относительно последней согласованной автором базы: серия малых повышений не сдвигает верхнюю границу и не обнуляет историю роста. Повтор измерений подтверждает новый размер, а смысловая проверка — сохранение требований и инвариантов. Неудачная проверка остаётся видимой и не заменяется повышением лимита.

Бюджеты назначаются не пропорционально строкам исходников. Учитываются число значимых областей, связи между ними, риск ошибки, обязательные инструкции и результаты пробных задач. Рост проекта обычно требует улучшить навигацию и выделить самостоятельные области, а не бесконечно удлинять корневые документы.

Для каждого ключевого документа или маршрута хранится текущий бюджет, фактический размер, основание выбора, версия оценки и событие следующего пересмотра. Возможные события: существенная смена архитектуры, добавление области, заметный рост, достижение границы либо контрольная дата. Точные числа выбираются при инициализации и уточняются по опыту проекта.

Навык актуализации:

```text
Сбор измерений и diff
       -> анализ ответственности, повторов и актуальности
       -> оставить / сократить / предложить разделение / расширить
       -> обоснование и список затронутых правил
       -> решение в согласованных полномочиях
       -> повтор измерений и проверка сохранения смысла
```

Увеличение лимита только потому, что файл вырос, недопустимо как автоматический способ убрать предупреждение. Временное расширение имеет причину и условие пересмотра. Сначала рассматривается удаление повторов и устаревшего содержания. Сокращение не должно уничтожать инварианты, причины решений и необходимые инструкции.

Начальные бюджеты — гипотеза. Для калибровки агент в новой сессии должен суметь найти место изменения, соответствующее требование и проверку, продолжить незавершённую задачу и различить действующее и архивное решение. Результаты таких проб дают основания для пересмотра; универсальную гарантию безопасности они не создают.

## 6. Штатное сопровождение и дополнительная актуализация — D32

Уточнение автора к D32-B: документация, архивирование, контроль объёма и временных обходов поддерживаются штатно в ходе работы. Отдельный навык актуализации — дополнительный комплексный контроль по запросу, когда автору нужно разобраться в состоянии проекта. Предыдущая трактовка «весь комплекс сопровождения только по вызову навыка» отменена.

Штатное сопровождение входит в обычное выполнение задач и применяется к затронутым материалам:

- При изменении поведения или устройства обновляются связанные документы и проверяется непротиворечивость по D26.
- При росте ключевых документов проверяются размеры, выдаются сигналы и при необходимости пересматриваются бюджеты в пределах D27.
- При завершении плана или подтверждённой замене материала выполняется архивирование по D29 с проверкой ссылок; ждать отдельного вызова актуализации не нужно.
- При добавлении или изменении временного обхода ведётся запись по D30; при наступлении известного условия пересмотра он пересматривается. Автоматическое удаление кода из этого не следует.
- Перед завершением задачи проверяется состояние связанных документов, открытых вопросов и выполненных проверок; локальный результат не выдаётся за обследование всего проекта.

Отдельный навык обследует проект шире текущей задачи: собирает фактическое состояние, проверяет актуальность и согласованность источников, пропущенную архивацию, бюджеты и забытые временные решения. Он использует те же правила и вспомогательные скрипты, выполняет разрешённые исправления и проверяет результат. Новые существенные решения возвращаются автору по D12. Вызов только для анализа не разрешает изменения.

Результат актуализации: понятная картина текущего состояния — что подтверждено, что устарело или противоречиво, что исправлено, что заблокировано и что осталось неизвестным. Содержит область обследования и результаты повторных проверок. Он не создаёт второй независимый набор задач или требований; задачи и доказательства остаются в своих основных источниках.

Скрипты собирают измерения и проверяют детерминированные условия, агент оценивает смысл. Выбор технических точек запуска штатных проверок (внутри процедуры, скриптом или хуком) ещё не сделан; D32 не запрещает их автоматизацию. Сам дополнительный комплексный навык запускается по запросу. Это не обещание фонового мониторинга вне активной работы; старый отчёт не подтверждает последующие изменения автоматически.

Критерии будущей проверки: завершённый материал архивируется без вызова навыка; изменённые документы и временный обход проверяются в обычной задаче; отдельная актуализация обнаруживает пропуски вне её области; результат локальной проверки не выдаётся за глобальную согласованность.

Принято D28-A: превышение бюджета вызывает предупреждение и пересмотр, но само по себе не останавливает работу и не блокирует завершение изменения. Существенное противоречие или отсутствие необходимого для решения контекста останавливает только зависимую часть задачи до устранения; независимая работа продолжается. После исправления проводится повторная проверка затронутой области. Непроведённая проверка не считается успешной, а известный конфликт не скрывается за общим статусом согласованности. Возраст файла сам по себе не основание для остановки. Предполагаемое смысловое противоречие, найденное эвристикой, требует оценки влияния; совпадение ключевых слов не доказывает конфликт. Конкретные события и технический способ обеспечения этой политики ещё не реализованы.

## 7. Актуализация и оформление

D31 снят автором: отдельную политику версионирования функциональности или документов в этот workflow сейчас не добавляем. Действующие документы обновляются на месте без собственных номеров редакций. Ранее согласованные добровольные обновления поставки workflow (D16/D20/D21) сохраняются.

Дата «проверено» меняется после содержательной проверки, а не после форматирования. Для проверки сохраняются область и привязка к проверенному состоянию исходников; одна дата не доказывает актуальность. Это учёт доказательств, а не отдельная схема версионирования документов.

Принято D33-A: обязательные правила оформления и минимальное содержание по роли документа, гибкая структура под проект. Единый набор заголовков и обязательные пустые разделы не навязываются.

- В начале указаны назначение и границы документа.
- Действующие правила, предложения и исторические сведения различаются явно.
- Заголовки предметные, разделы короткие и самостоятельные, на нужную часть можно сослаться.
- У каждого правила один основной источник; остальные документы дают ссылку.
- Неочевидные ограничения сопровождаются причинами.
- Команды, пути и примеры проверяемы; непроверенные примеры обозначаются явно. Команды по возможности ссылаются на штатные скрипты и не копируются между инструкциями.
- История работы и длинные отчёты не накапливаются в основных документах: там остаются действующее состояние и ссылки на доказательства.

При сокращении агент проверяет сохранение требований, исключений, инвариантов и причин решений. Меньший размер сам по себе не означает улучшения. Скрипт проверяет доступные структурные признаки и ссылки, агент — смысл и полноту; гибкая структура не отменяет обязательного содержания. Обнаруженные проблемы обрабатываются по D28, косметические отличия не останавливают работу.

Критерии будущей проверки: разные разумные структуры одного типа документа допустимы; отсутствующее необходимое содержание отмечается; предложение не принимается за действующее правило; непроверенный пример не выдаётся за проверенный; сокращение не теряет важное исключение. Это требования к будущим проверкам, не результаты их запуска.

## 8. Защита от накопления обходных решений

Нужно различать предусмотренное поведение при отказе, временный обход и скрытое подавление ошибки. Например, согласованное обслуживание из кэша при недоступном сервисе может быть нормальным поведением; пустой успешный ответ после любой ошибки способен скрывать поломку. Проверка по словам fallback/try/except не различает их надёжно.

Принято D30-A: агент может добавить временный обход внутри согласованной задачи, если он сохраняет требования, не скрывает ошибку и имеет проверку и условие удаления. Для каждого обхода фиксируются причина, затронутый код, проверка, условие удаления и ссылка на задачу в существующей системе; не нужен отдельный независимый backlog. Формат идентификатора и место хранения записи определяются технически. Изменение поведения, ослабление гарантий или существенные последствия согласуются с автором по D12. Неуспешная проверка остаётся неуспешной.

При наступлении условия агент пересматривает обход. Молчаливое продление недопустимо: если обход остаётся, явно записываются причина и следующее условие пересмотра; новые существенные последствия возвращаются автору. Срок пересмотра не разрешает автоматически удалять работающий код: сначала проверяется возможность удаления без нарушения поведения. Предусмотренное спецификацией поведение при отказе не считается временной заплаткой. Новые кандидаты из diff требуют оценки; общий поиск служит подсказкой, не доказательством.

Скрытое превращение ошибки в успех недопустимо. Если требуется изменить предусмотренное поведение при отказе, это отдельное продуктовое решение по D12, отражаемое в требованиях и проверках. Обычное разрешённое исправление не получает дополнительную бюрократическую остановку. Постоянная деградация должна иметь спецификацию, наблюдаемость и тест; временное решение не может становиться постоянным по молчанию.

## 9. Архив

Принято D29-A: агент самостоятельно архивирует завершённые планы, явно заменённые документы и разобранные неудачные гипотезы по подтверждённому статусу. Возраст файла сам по себе не является основанием. Если завершение/замена неоднозначны или материал ещё нужен текущей работе, агент сохраняет его активным и обозначает вопрос.

При архивировании сохраняются причина, статус, ссылки на замену (если она есть) и доказательства; входящие ссылки проверяются и при необходимости корректируются. Если проверка не проходит, перенос не объявляется завершённым: агент исправляет ссылки в пределах разрешённой задачи либо восстанавливает прежнее расположение без потери содержимого. Исторические ссылки, нужные для расследования, остаются доступными. Обычные редакции сохраняются в Git. D29 не разрешает удалять рабочую функциональность или автоматически уничтожать архив.

Архив — исторический источник с причиной завершения, заменой и ссылкой на доказательства. Он исключён из стандартных маршрутов чтения и обычного поиска активных документов, но доступен явно. Точный каталог пока не выбран; уже существующий архив OpenSpec не дублируется копиями.

| Материал | Предлагаемое действие |
|---|---|
| Обычная предыдущая редакция актуального документа | История Git; не отдельная ручная копия |
| Закрытый план или заменённое самостоятельное описание | Перевод в архив со статусом и ссылкой на замену |
| Неудачная гипотеза | Краткий итог, условия эксперимента, результат, доказательства и условия возможного пересмотра |
| Удалённый функционал | Причина удаления и ссылка на коммит/тег; исходники сохраняет Git |
| Большие временные результаты | Ссылки/хеши и выбранная политика хранения; не автоматическое добавление всех файлов в Git |

Перемещать неиспользуемый исполняемый код в archive/ внутри дерева сборки рискованно: он может остаться в импортировании, тестах или поставке. Архивирование функциональности означает отдельное согласованное удаление из активного приложения с проверками, а не перенос папки ради меньшего размера. Текущий запрос не разрешает автоматически удалять рабочее поведение.

Срок и момент архивации привязаны к замене/завершению и проверке входящих ссылок, а не только к возрасту файла. Если активное правило ещё ссылается на старый материал, сначала уточняется зависимость. Значимые текущие причины отклонённых вариантов сохраняются коротко в действующем контексте со ссылкой на подробности: иначе агент повторит уже проверенную неудачную гипотезу.

## 10. Проверка самого механизма

Будущие сценарии: документ вырос и вызвал сигнал; лимит не увеличился сам; документ короткий, но с нарушенной ссылкой; часть карты проекта неизвестна; вложенные инструкции переполняют применимую цепочку; временное исключение просрочено; архив ошибочно включён в активный маршрут; прерывание актуализации не теряет исходники; сжатие сохраняет инварианты; часть обследования не выполнена и это не выдано за успех. Отдельно — реальные задачи новой сессии в приложении и CLI.
