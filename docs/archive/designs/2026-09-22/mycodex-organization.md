## Назначение

MyCodex — единое место разработки собственных инструментов и описания личного рабочего процесса в Codex. Проект должен позволять быстро найти решение, понять его назначение и состояние, продолжить доработку, проверить результат и отдельно подключить его к рабочей установке.

Первое содержимое — готовые SVG Vectorizer и Code Health Audit. Будущий UI workflow со Storybook и собственными элементами учитывается как направление, но сейчас не разрабатывается.

- D5, вариант C: организовать проект по направлениям, а не по типам артефактов. Каждое направление объединяет относящиеся к нему инструменты и инструкции.

## Предлагаемая иерархия

Ниже — проект целевого устройства, а не перечень уже созданных файлов. Кроме этого документа структура ещё не реализована. Имена и распределение обязанностей предлагаются к подтверждению вместе с документом.

```text
MyCodex/
|-- README.md                         назначение, быстрый вход и навигация
|-- AGENTS.md                         правила работы агента в этом проекте
|-- CATALOG.md                        решения, зрелость и ссылки на направления
|-- solutions/
|   |-- vectorization/
|   |   |-- README.md                 задачи направления и вход в инструменты
|   |   `-- plugins/
|   |       `-- svg-vectorizer/       исходный пакет целиком
|   `-- code-quality/
|       |-- README.md
|       `-- plugins/
|           `-- code-health-audit/    исходный пакет целиком
|-- docs/
|   |-- workflow.md                   общий рабочий процесс и связи инструментов
|   |-- development.md                добавление, изменение и проверка решений
|   |-- installation.md               подключение, обновление и откат
|   |-- designs/                      согласуемые проекты устройства
|   |-- decisions/                    принятые существенные решения и причины
|   `-- plans/                        ограниченные планы работ и их состояние
`-- config/
    `-- examples/                     общие переносимые примеры настроек
```

Каталоги появляются только вместе с полезным содержимым. При появлении нескольких независимых инструментов внутри направления сохраняется та же схема. Другие типы материалов размещаются рядом с plugins только тогда, когда реально появляются.

UI workflow пока представлен записью в CATALOG и будущем плане. Папка solutions/ui-workflow, Storybook, библиотеки компонентов и зависимости сейчас не создаются.

При подготовке подключения можно использовать штатный каталог `.agents/plugins/marketplace.json` с путями к вложенным пакетам. Создание каталога, выбор его имени и переключение текущих установок требуют отдельного плана подключения; данный документ не задаёт новый marketplace и не меняет профиль Codex.

## Правила размещения и документации

- Направление определяется основной задачей пользователя: преобразовать графику, оценить качество кода, построить интерфейс. Дополнительные применения обозначаются ссылками, без копирования инструмента в несколько направлений.
- CATALOG — единственный общий реестр решений: название, направление, назначение, зрелость и ссылка. Подробности проверок и ограничения находятся у самого решения.
- Зрелость предлагается обозначать как planned, experimental, ready, archived. Ready означает подтверждённые проверки заявленного сценария, но не факт установки в текущем Codex. Версия пакета остаётся в его манифесте, а не дублируется в реестре.
- README направления объясняет, когда оно нужно и с чего начать. Команды, параметры и подробные проверки плагина остаются в его собственной документации.
- Общие инструкции находятся в docs. Специфичные для направления инструкции находятся в нём. Настройка, нужная только одному инструменту, хранится рядом с ним; config/examples содержит только действительно общие примеры.
- AGENTS.md содержит правила изменения проекта и ссылки на подробности, а не пересказ всей документации. Инструкции внутри навыков описывают использование инструмента и сохраняются в пакетах.
- Существенное решение фиксируется с причиной и последствиями. Планы отделены от действующих инструкций, завершённые планы имеют явный статус. Отдельный журнал создаётся только при первой соответствующей записи.
- При изменении решения обновляются его проверки и затронутые инструкции. Общий реестр меняется только при изменении назначения, расположения или зрелости.
- Пользовательские токены, журналы сессий, кеш Codex, виртуальные окружения и установленные зависимости не включаются в переносимые исходники.

## Путь от изменения к использованию

```text
CATALOG -> направление -> исходники и документация решения
                              |
                              v
                       изменение и проверки
                              |
                              v
                       проверенная версия
                              |
                   отдельный шаг подключения
                              |
                              v
                    установленная копия Codex
```

До успешного подключения рабочая установка продолжает использовать прежнюю версию. Проверка исходников и проверка установленной копии дают разные доказательства; в отчёте они указываются отдельно.

## План переноса готового

Это предложение последовательности для последующего CEO review, не выполненные действия.

1. Сопоставить исходные каталоги и установленные пакеты. При несовпадениях показать различия и определить переносимую версию; не выбирать автоматически по времени изменения.
2. Сформировать перечень исходников, тестов, инструкций, примеров и закреплённых зависимостей. Проверить назначения путей и исключить кеши, окружения и локальные данные.
3. Скопировать выбранные пакеты в направления с сохранением внутренней структуры. Оригиналы пока сохранить; ничего не переустанавливать и не менять поведение плагинов.
4. Сверить состав и хеши копий, проверить относительные ссылки и указания старых путей. Перенос окружений не использовать: при необходимости создать новые по существующим инструкциям пакетов.
5. Выполнить существующие проверки из новых расположений и записать команды, результаты и ограничения. Не исправлять функциональные дефекты скрыто под видом переноса; расхождение сначала отразить в отчёте.
6. Зафиксировать MyCodex как место дальнейшей разработки. Записать происхождение импортированной версии и роль сохранённых оригиналов как резервных копий. Если проверки не пройдены, импорт остаётся непроверенным и не становится основной рабочей версией.

Критерий успешного переноса: выбранное содержимое сохранено, проверки выполняются из нового места, документация ведёт к новым исходникам, работающая установка не изменена. Удаление оригиналов не требуется для успеха.

## Рассмотренные альтернативы

- Минимальная коллекция с единым справочником: не выбрана пользователем.
- Разделение верхнего уровня по типам артефактов: не выбрано пользователем.
- Направления с собственными инструментами и инструкциями: выбраны пользователем; добавляют уровень вложенности, но объединяют материалы по решаемой задаче.

## Критерии готовности проекта организации

- Из корневого README можно найти каждое готовое решение, его исходники, проверки и инструкцию использования.
- Для каждого документа и инструмента есть одно основное место; общие материалы связаны ссылками.
- Добавление третьего направления не требует перестройки существующих двух.
- Граница между планом, проверенной разработкой и установленной версией явно описана.
- Схема подходит текущим пакетам без объединения их зависимостей и без переписывания реализации.
- Будущий UI workflow виден как запланированное направление и не выглядит уже реализованным.

## Границы и открытые вопросы

Не входят сейчас: разработка UI workflow, запуск Storybook, изменение функций плагинов, собственный установщик, автоматическая синхронизация профиля, публикация, push, удаление прежних каталогов и переключение установленного Codex.

Для дальнейшего plan-ceo-review остаются: режим review; проверка точных правил и критериев переноса; объём первоначального наполнения общей документации; начало Git-истории и порядок подключения. Полный профиль пользователя и все сторонние инструменты этим документом не инвентаризируются.

Согласование этого документа подтверждает устройство проекта; оно не означает выполнение переноса, активацию новых версий или завершённый CEO review.
