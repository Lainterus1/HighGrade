# Как выглядит задача в High Grade

Исторический пример формата v1. Описания store ниже относятся к этому формату; актуальный каталог v3 показан в [новом примере](../../../examples/spec-catalog/README.md).

**Учебный пример:** не разрешать резерв товара сверх остатка. Он создан установленным CLI v0.2.12; это отдельный демонстрационный корень, а не задача или требования самого High Grade. Кода товара и тестов здесь нет.

## Что создаёт инструмент

| Файл | Назначение |
|---|---|
| [template.json](template.json) | Точная заготовка spec-new: единые поля и начальные ID, содержание пустое |
| [change.json](change.json) | Заполненный объект изменения: цель, границы, задачи, требование и три сценария |
| [store.json](.highgrade/specs/store.json) | Фактическое хранилище инструмента: schema_version, действующие требования, изменения и происхождение |

В обычном проекте основным источником служит **один store.json**. template.json и change.json здесь оставлены как учебные снимки «до/после», а не как три обязательных параллельных документа. Markdown-пояснение — только инструкция к примеру; это не автоматически создаваемая вторая спека.

## Содержание простыми словами

**Цель:** нельзя обещать покупателю больше товара, чем есть.

**Граница:** один товар и последовательные запросы. Платежи, доставка, отмена и конкурентное резервирование исключены.

| Исходное состояние | Действие | Наблюдаемый результат |
|---|---|---|
| Остаток 3 | Зарезервировать 4 | Отказ; все данные товара сохранены |
| Остаток 3 | Зарезервировать 2 | Успех; остаток 1 |
| Остаток 3 | Зарезервировать 3 | Успех; остаток 0 |

Первый сценарий в настоящем формате:

```json
{
  "id": "DEMO-RESERVE-S1",
  "given": "Остаток товара — 3; название и цена заполнены. Сохранена копия всех полей товара.",
  "when": "Покупатель пытается зарезервировать 4 единицы.",
  "then": "Получен отказ. Все поля товара равны сохранённой копии; остаток остаётся 3.",
  "verification": "План: tests.test_reservation.test_insufficient_stock создаёт товар с остатком 3, вызывает настоящую reserve с количеством 4 и сравнивает ответ и весь товар до/после. Запуск: python -m unittest tests.test_reservation -v."
}
```

## Где что находится в change

| Поле | Что агент записывает |
|---|---|
| goal / rationale / scope | Нужный результат, причина, границы |
| questions | Неотвеченные вопросы; здесь пусто |
| tasks | Действия исполнителя и их done; здесь все false |
| operations | Изменения требований: add, modify или remove; здесь add |
| requirement | ID, заголовок, правило, сценарии given/when/then и способ проверки |
| baseline / imports | Исходные редакции и происхождение; защищены инструментом |
| evidence | Наблюдения, исходы и хеши файлов после настоящей проверки; здесь пусто |
| review | Автор, вердикт и редакция независимого ревью; здесь null |
| archived / abandoned_reason | Завершение либо отказ от изменения; здесь false / null |

Версия формата находится на уровне store.schema_version, а не внутри каждого change. Поле store.requirements пока пусто: новое правило ещё не включено в действующие требования.

## Что уже проверено

- spec-new → spec-save → spec-validate: **PASS** — форма и обязательное содержание заполнены.
- spec-check: **FAILED, ожидаемо** — задачи не выполнены, доказательств нет, ревью отсутствует.
- spec-integrate не вызывался; ни один тест поведения не выдаётся за выполненный.

Воспроизвести проверку установленным highgrade.exe можно с `--root <этот-каталог>` и `--id DEMO-RESERVE`: сначала spec-read, затем spec-validate и spec-check. Ожидаемый код последнего — 1.

Дальше исполнитель создаст настоящие тесты и исправление, сохранит доказательства через spec-evidence, затем результат пройдёт независимое ревью. После успешного spec-check команда spec-integrate включит требование и архивирует изменение. Коммит, активация и публикация остаются отдельными действиями.
