# Проверки и доказательства

Команды используют `--root PATH`; записывающие операции — CAS `--expected HASH`.

| Операция | Параметры |
|---|---|
| spec-evidence | --id HG-ID --input evidence.json |
| spec-evidence-batch | --input batch.json |
| spec-review | --id HG-ID --verdict go\|no_go --reviewer NAME --conclusion TEXT |
| spec-check | --id HG-ID; --brief true для кратких причин |
| spec-stats | --id HG-ID; чтение числа и длительности попыток |

Пример evidence input (заполняется по реальному запуску):

```json
{
  "scenario": "HG-CART-S1",
  "method": "native_report",
  "command": "python -m unittest tests.test_cart",
  "captured_at": "2026-09-24T00:00:00Z",
  "outcome": "passed",
  "observation": "test_rejects_negative_quantity выполнен и проверил неизменность корзины",
  "inputs": ["cart.py", "tests/test_cart.py", "pyproject.toml"],
  "report": "evidence/cart-run.txt"
}
```

Для ручного упражнения method=manual; report содержит условия, действия, наблюдения и предел проверки. Допустимые исходы: passed, failed, skipped, unknown. Состав входов проверяет агент и ревью: CLI не может обнаружить незаявленную зависимость или доказать подлинность отчёта. Хеши фиксируются во время записи; агент обязан сопоставить их с состоянием настоящего запуска. Изменение общего правила обесценивает его сценарии, изменение одного сценария — только его доказательство; изменение входа или отчёта — ссылающиеся доказательства. Сам по себе новый Git SHA не обесценивает неизменённую проверку.

Для передачи между `work`, `approve` и `push` используй `spec-check --id HG-CHANGE --brief true`. Поле `measurements[].brief` содержит технический и человеческий статус, `change_sha256`, `inputs_sha256`, состояние ревью и, при действующей приёмке, `verified_revision`. При пробеле `blockers` называет сценарий или проверку, причину и изменившийся/недоступный путь; общие структурные ошибки остаются в `findings`. Это чтение не запускает проверки и не создаёт отдельный отчёт. Используй тот же снимок, пока заявленные входы и состав не изменились; `null` вместо `inputs_sha256` означает, что один из входов недоступен, а не подтверждённый результат. Обычный `spec-check` сохраняет прежний полный ответ для совместимости.

Для trace путь к catalog.json (либо legacy store) включается в spec_files. Его source_hashes использует **trace_sha256 из spec-list**, хеш эффективных требований без доказательств и задач; остальные файлы используют SHA-256 байтов. Это исключает самоссылку при записи evidence. Конфликтующие активные изменения одного требования требуют разрешения до trace. Перенесённые требования исключаются из прежнего владельца по origins, остальные Markdown-требования остаются видимыми. Исходный формат run-record и поддержанные раннеры прежние.

## Привязки и явный запуск

`checks` в change: `{id, scenario_ids, runner, file, selector, preparation, action, observation, inputs}`. scenario_ids и inputs — массивы строк. Один тест может проверять несколько сценариев, один сценарий — несколько тестов. preparation/action/observation описывают воспроизводимые условия, действие и результат. `runner: null` обозначает ручную проверку; для неё допустимы пустые file/selector. Ручное наблюдение записывается через spec-evidence.

Проектный `runners.json` хранит именованные штатные команды. Добавь конфигурацию через `spec-runner-set --id ID --input runner.json --expected HASH`. Формат: `{ "program":"cargo", "args":["test","--test","{target}","{selector}","--","--exact"], "cwd":".", "format":"cargo-test", "timeout_seconds":60 }`. Для JUnit используй format=junit и аргумент `{report}`: инструмент подставляет уникальный путь отчёта. Доступны `{file}` (абсолютный тестовый файл), `{target}` (его имя без расширения), `{selector}`. Все пути входов и cwd относятся к корню проекта; executable — имя из PATH или проектный относительный путь. Shell не добавляется. Команда является исполняемым кодом проекта и требует обычного ревью.

`spec-run --id HG-0001 --check CHECK_ID|all --expected HASH` запускает только явную выборку. Чтение, фильтры и schema ничего не запускают. cargo-test требует единственного точного прошедшего теста; JUnit — единственного testcase с name=selector либо classname::name=selector. Пустая выборка, пропуск, ошибка, тайм-аут и изменение входов не дают passed. Настрой штатный раннер так, чтобы он завершал дочерние процессы; на Windows тайм-аут завершает дерево taskkill, на остальных платформах — прямой процесс.

`spec-stats --root PATH --id HG-CHANGE` читает сохранённые `runs`: общее число попыток и измерений, последнюю длительность, число сопоставимых попыток, медианную и максимальную длительность в миллисекундах. Сопоставимы только попытки с текущей привязкой и совпадающими до/после отпечатками всех объявленных входов; при недоступном входе сопоставимого времени нет. Признаки `latest_current_revision` и `latest_comparable` не дают принять старый результат за текущий. Медиана для чётного числа измерений — верхнее из двух средних значений. Старые попытки без `duration_ms` учитываются как неизмеренные; незапущенные проверки показывают null, а не выдуманное время. Длительность измеряет работу раннера от запуска до завершения; ошибочный исход не становится успешным из-за времени. Статистика не запускает тесты, не меняет store и не решает, какие проверки достаточны; актуальность и качество определяют `spec-check` и ревью. Необъявленные влияющие входы инструмент не обнаружит; их полноту проверяет ревью. Штатные отчёты JUnit могут содержать подробные времена отдельных тестов.

runs сохраняет команду, cwd, время начала, длительность завершённого запуска, результат, исходные хеши вместе с отчётами в files и снимок inputs_after. Не запущенная проверка получает unknown с причиной и без длительности. Автоматически добавляются тестовый файл, конфигурация раннеров и проектный executable; остальные значимые исходники/конфиги укажи в inputs. Состав входов и подлинность внешнего отчёта проверяются ревью. Все привязанные автоматические проверки должны пройти; один успех не скрывает соседнюю ошибку.

Повторные spec-run/spec-evidence/spec-review разрешены для интегрированной спеки: требования и spec.json сохраняются, results.json пополняется. Существенное изменение контракта, наблюдения, исхода, определения проверки или входа обесценивает прежнее ревью/приёмку. Эквивалентный повтор сохраняет актуальность: время, длительность и новый путь отчёта не входят в существенную редакцию. Сам отчёт по-прежнему проверяется на целостность. brief отдельно показывает contract_sha256; change_sha256 также учитывает существенные доказательства. Старые отпечатки проверяются прежним алгоритмом; первое обновление старых доказательств может потребовать новое ревью и решение. История остаётся. Изменение требований или нормативных сценариев требует нового change; исправление реализации по прежнему контракту обновляет results. Новый Git SHA сам по себе не требует новой спеки.




`spec-evidence-batch --root PATH --expected HASH --input batch.json` принимает массив `{id, evidence}`; evidence имеет схему одиночного spec-evidence. Весь пакет проверяется до записи; ошибка отменяет пакет, точный повтор не создаёт историю. Ревью и приёмка остаются отдельными. Предел входа и транзакции — 8 МиБ; слишком большой пакет нужно разделить до применения.

Для штатного JUnit-отчёта до запуска получите `snapshot` через `spec-run-inputs --root PATH --id HG-ID --check all` (или ID проверки). После запуска передайте `spec-run-import --root PATH --expected HASH --input import.json`: `{snapshot, report: "relative/report.xml", command: ["actual-command", "argument"]}`. Один отчёт может содержать несколько тестов; каждый selector должен однозначно находить успешный testcase. Входы и определение проверки должны совпадать со снимком. Без снимка до запуска актуальность не подтверждена. Импорт не запускает runner; failed/skipped/missing и устаревший вход отклоняют весь импорт. Точный повтор не добавляет runs. Подлинность отчёта, полнота входов и фактическая команда требуют ревью. Остальные форматы сохраняют spec-run или spec-evidence.

Условия достаточности, выбор входов и ревью определяет [work](../../procedures/work.md#доказательства-и-ревью); здесь описаны операции и форматы.
