# Команды глобальной поставки High Grade

Собери выбранный исходный каталог командой `cargo build --release --locked`. Первый выпуск распространяется исходниками для Windows. Передавай абсолютные пути. `--profile` обозначает домашний каталог пользователя, например `$env:USERPROFILE`, а не целевой проект. Команды установки и обновления не сканируют соседние проекты или весь домашний каталог.

```powershell
& '<исходник>/target/release/highgrade.exe' global-install --profile '<домашний-каталог>' --source '<исходник>/kit' --candidate-exe '<исходник>/target/release/highgrade.exe'
& '<домашний-каталог>/.highgrade/global/releases/<active>/highgrade.exe' global-status --profile '<домашний-каталог>'
& '<домашний-каталог>/.highgrade/global/releases/<active>/highgrade.exe' doctor --root '<проект>'
& '<исходник>/target/release/highgrade.exe' inspect --bootstrap --root '<проект>'
& '<домашний-каталог>/.highgrade/global/releases/<active>/highgrade.exe' inspect --root '<проект>' --registry '.highgrade/project/documents.json'
```

Установка создаёт общие маршрутизирующие файлы в `<домашний-каталог>/.agents/skills/highgrade-*/SKILL.md`, а неизменяемую поставку — в `<домашний-каталог>/.highgrade/global/releases/<release>/`. Один активный указатель переключается после проверки хешей и версии. Чужой навык с тем же именем — конфликт. Общие навыки и CLI в проект не копируются. Init после аудита и в разрешённой области готовит `.highgrade/project/INSTRUCTIONS.md` и короткую ссылку из AGENTS.

Обновление всей пользовательской поставки выполняется явно. Сначала preview, затем смысловое сравнение правил, затем применение с тем же `candidate_sha256`. CLI проверяет рабочую команду `doctor` до переключения и после установки. Отпечаток связывает манифест со всеми материалами и байтами исполняемого файла. Ранее установленные SKILL.md шести исходных маршрутизаторов остаются побайтно одинаковыми. При переходе с v0-2-6 новые `highgrade-approve` и `highgrade-push` создаются до переключения указателя; прежний `highgrade-deploy` удаляется после проверки новой версии. При ошибке postcheck CLI пытается восстановить прежний активный выпуск; после сбоя фактическое состояние проверяют по [процедуре Update](../procedures/update.md#повтор-и-ошибки). После успеха собственные файлы старых выпусков удаляются, чужие сохраняются с предупреждением. После прерванного переключения установи фактическое состояние через global-status; ошибка диагностики не подтверждает исправность активной поставки. Неактивный остаток не даёт полномочий. Проектные инструкции проверяются при следующей работе с конкретным проектом.

```powershell
& '<кандидат>/target/release/highgrade.exe' global-update --profile '<домашний-каталог>' --source '<кандидат>/kit' --candidate-exe '<кандидат>/target/release/highgrade.exe'
& '<кандидат>/target/release/highgrade.exe' global-update --profile '<домашний-каталог>' --source '<кандидат>/kit' --candidate-exe '<кандидат>/target/release/highgrade.exe' --apply true --candidate-sha256 '<отпечаток-из-preview>'
```

`doctor`, `inspect`, `inventory` и `trace` работают на чтение с `--root <проект>`. `doctor` обнаруживает путь CLI, но не запускает его и не сверяет версию; закреплённую версию проверяют командой проекта. Штатные тесты запускаются командами проекта. Отсутствующая инструкция или неизвестный инструмент остаются состоянием unknown, а не успешной проверкой. Старые проектные `install`/`update` сохранены только для исторического кандидата как библиотечный контракт и явно названные команды `legacy-install`/`legacy-update`; новые проекты используют глобальный маршрут.

## Предварительная проверка документов (v0-2-5)

`inspect --bootstrap --root <абсолютный-путь>` работает до создания реестра. JSON-отчёт `measurements[0]` содержит `slots` для семи путей: `README.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/ENGINEERING.md`, `docs/DEVELOPMENT.md`, `.highgrade/project/INSTRUCTIONS.md`, `.highgrade/project/documents.json`. `path_state` показывает точное наличие, `candidates` — ограниченные возможные альтернативы по имени файла или подписанной Markdown-ссылке, `candidate_status=not_needed` означает наличие точного пути; `not_found_in_scan` не означает отсутствия содержания. `required_links` отдельно показывает шесть обязательных связей: из README к четырём документам, из AGENTS к проектной инструкции, из неё к реестру. `--bootstrap` нельзя сочетать с `--registry` или `--scope`. Неверный корень даёт `failed`; отсутствующий точный путь или связь — структурное `failed`; недоступная область или предел — `unknown` в находках. Результат не создаёт и не переносит файлы.

`candidate_scan=performed` означает поиск альтернатив для отсутствующих путей. Если все семь точных путей есть, `candidate_scan=not_needed`, дерево не обходится и `visited_entries=0`; обязательные связи и список исключений всё равно проверяются. Структурный `failed` на ещё не подключённом проекте даёт задачи адаптации, а не отменяет аудит. Ошибка корня или отсутствие пригодного JSON-отчёта останавливает зависимую работу. Содержание и решение о переносе агент фиксирует в таблице адаптации из процедуры init.

Когда поиск кандидатов нужен, обход включает новые файлы и скрытые инструкции без зависимости от Git. Читаются только `.highgrade/project/inventory-exclusions.json` и три канонических источника ссылок — README, AGENTS, проектная инструкция. Валидные проектные исключения применяются до обхода; свободный текст их причин не выводится. Некорректный список даёт `unknown` и не применяется частично. `.git`, `node_modules`, `target`, `.pnpm-store`, `.output`, `.tanstack`, `.highgrade/releases`, кэши, известные закрытые имена, символические ссылки и Windows reparse points не читаются; `.highgrade/project` остаётся в области. Исключения не доказывают одобрение аудита.

Пределы: 50 000 записей, 128 чтений, 64 КиБ на входной файл, 12 кандидатов на роль, 32 показанных исключения, 200 байт на путь, глубина 64 и 64 КиБ на JSON-отчёт. Достижение предела отмечается как `unknown`; непоказанная область остаётся задачей агента. Обычный `inspect` требует реестр и проверяет соответствие роли каноническому пути, обязательные связи, прочие зарегистрированные ссылки и бюджеты. Он не заменяет смысловой аудит и не исправляет проект автоматически.

## Начальный реестр документов

Основа `.highgrade/project/documents.json` для init приведена ниже. Укажи реальные области `scope`, дополнительные источники и согласованные бюджеты; `null` намеренно даёт `BudgetNotAgreed`, а не PASS. `active: true, loading: history` проверяет источник и ссылки, исключая его из обычного маршрута; `active: false` вообще исключает строку из проверки. Не назначай широкую область ради скрытия `AreaUnclassified`.

```json
{
  "schema_version": 1,
  "documents": [
    {"id":"readme","path":"README.md","role":"purpose-navigation","loading":"entry","scope":[],"budget":null},
    {"id":"agents","path":"AGENTS.md","role":"agent-rules","loading":"entry","scope":[],"budget":null},
    {"id":"architecture","path":"docs/ARCHITECTURE.md","role":"current-architecture","loading":"task","scope":[],"budget":null},
    {"id":"engineering","path":"docs/ENGINEERING.md","role":"engineering-rules","loading":"task","scope":[],"budget":null},
    {"id":"development","path":"docs/DEVELOPMENT.md","role":"commands-procedures","loading":"task","scope":[],"budget":null}
  ],
  "additional_sources": [
    {"path":".highgrade/project/INSTRUCTIONS.md","role":"project-adaptation","active":true,"loading":"entry","scope":[".highgrade/project/documents.json"]}
  ],
  "route_budget": null
}
```

Путь и `scope` задаются относительно корня проекта. Для согласованного бюджета используется объект `{"unit":"bytes","agreed":true,"min":1000,"baseline":2000,"current":2000,"ceiling":3000,"history":[],"review_trigger":"после двух задач"}`; числа здесь иллюстративные, переносить их как принятые нельзя. Изменение `current` сохраняет цепочку `history` с `from`, `to`, `reason`, `reduction_considered`, `next_review`. Уникальные роли пяти основных документов и канонические пути обязательны.

## Совместимость проекта

1. Проверь выбранный выпуск командой `global-status --profile <профиль>` и проект командой `doctor --root <проект>` через CLI этой Поставки. Отсутствие местной инструкции ожидаемо при init; для задачи с зависимыми местными решениями сначала нужна адаптация.
2. Поддерживается заголовок `highgrade_project_schema: 1` между отдельными строками `---` в начале UTF-8 файла (LF или CRLF). `project_instruction=compatible` имеет границу `compatibility_scope=schema-only`; `semantic_compatibility=not_assessed`. Это не проверка заполнения, согласованности содержания или готовности проекта. Неизвестную схему не понижай автоматически до 1.
3. Агент сверяет только применимые к задаче местные источники, реальные команды/среду, требования активных процедур и полномочия. Для обязательного инструмента проверь реальную версию, если она закреплена. Отсутствующий способ проверки остаётся пробелом; известное принятое исключение применяется в своей области без повторного вопроса.
4. При новой несовместимости назови правило, местное положение, зависимое действие и исправление. При отсутствии адаптации используй init; при устаревшей/противоречивой — clear в разрешённом режиме. Неизвестная публикация не блокирует независимую локальную работу; обязательный неизвестный тест не позволяет объявить задачу завершённой. Известный конфликт обязанностей местного навыка не разрешается молчаливым выбором одного пути.
5. После изменения затронутой конфигурации повтори соответствующую проверку. Результат проверки и ограничения сохраняй кратко в основном артефакте задачи, без второго реестра. В новой сессии сверяй актуальную Поставку и входы; внутри сессии неизменённое не перечитывай и не проверяй повторно без причины.

Global-update меняет только общую установку. Совместимость смысла проектных инструкций он не подтверждает и сами инструкции не переписывает. Восстановление прежней установки при неудачном update и восстановление приложения при его активации — разные механизмы.

Код самого CLI: 1 — failed, 2 — unknown, 0 — остальные состояния (включая предупреждения). Фиксируй `$LASTEXITCODE` сразу после команды, до следующего процесса; код оболочки или инструмента-обёртки может отличаться. При расхождении с JSON не угадывай код, повтори минимальную диагностику с явным захватом.

## Структурированные спецификации

Нативный формат v3 — проектный каталог `specs/`: `catalog.json` хранит версию и счётчик, `requirements/<ID>.json` — действующие требования, `changes/<ID>/spec.json` — изменение, `results.json` — доказательства, историю проверок и решения человека. Пустые результаты не создаются. Каталог принадлежит проекту и сохраняется при удалении High Grade. Не перемещай принятые спеки: статус хранится в данных. Для новых проектов OpenSpec не требуется; в инструкции укажи `highgrade_spec_format: native-v1` (маркер семейства workflow, версия store задаётся отдельно). Исторические проекты могут явно сохранять прежний маршрут. CLI работает без Node/Rust/OpenSpec у потребителя; штатные тесты требуют собственную среду проекта.

Все команды возвращают JSON Report: `findings` с кодом и расположением проблемы, `measurements` с результатом, `limitations` с пределами проверки. `spec-read` возвращает объект `change` внутри measurements; редактируй и передавай именно этот объект, не весь Report. `spec-schema` возвращает JSON Schema directory_format (catalog/spec/results/tags/runners), legacy store, change/evidence_input/decision_input, сгенерированную из типов CLI. Неизвестная версия или поле отвергаются. Структура не доказывает качество смысла.

| Команда (общий параметр `--root PATH`) | Параметры и результат |
|---|---|
| `spec-schema` | Схемы и обязательные поля для клиента |
| `spec-list` | JSON-сводка; необязательные `--tag ID --technical STATUS --human STATUS`; selected/total и краткие зависимости |
| `spec-new` | `--title TITLE --expected HASH`; следующий HG-номер и одинаковый шаблон |
| `spec-read` | `--id HG-CHANGE` либо `--requirement HG-REQ`; выбранный объект |
| `spec-save` | `--id HG-CHANGE --expected HASH --input edit.json`; сохранение редакции change |
| `spec-diff` | `--id HG-CHANGE`; операции и текущие требования для сравнения |
| `spec-validate` | `--id HG-CHANGE`; наполненность требований, сценариев и задач, вопросы и база |
| `spec-evidence` | `--id HG-CHANGE --expected HASH --input evidence.json`; запись наблюдения и хешей |
| `spec-review` | `--id HG-CHANGE --expected HASH --verdict go\|no_go --reviewer NAME --conclusion TEXT`; вердикт для точной редакции |
| `spec-check` | `--id HG-CHANGE`; завершённые задачи, актуальные доказательства и положительное ревью |
| `spec-integrate` | `--id HG-CHANGE --expected HASH`; после check включить требования и архивировать change |
| `spec-abandon` | `--id HG-CHANGE --expected HASH --reason TEXT`; сохранить отвергнутый черновик в истории без изменения требований |
| `spec-migrate` | `--expected HASH --to directory`: v1/v2 → каталог; без --to сохраняется прежний переход v1 → v2 |
| `spec-decide` | `--expected HASH --input decisions.json`; атомарная запись решений человека по выбранным версиям |
| `spec-import` | `--id HG-IMPORT --expected HASH --input requirement.json --source legacy.md`; черновик выборочного переноса |

Первый `spec-list` возвращает `store_sha256: absent`. Передавай его в spec-new. Для следующих записей используй `store_sha256` из чтения именно редактируемого снимка. Любая конкурентная запись вызывает StoreConflict: перечитай, сопоставь изменения и повтори только свою правку. `id`, `baseline`, `imports`, `evidence`, `review`, `archived`, `abandoned_reason`, `created_at`, `acceptance`, `history`, `runs` — защищённые поля spec-save. Для операции add/modify передай requirement; для remove — id и непустую reason. ID требований и сценариев используют заглавный префикс проекта и сегменты через дефис, например HG-CART-R1 и HG-CART-S1. ID не переиспользуются после удаления.

Пример evidence input (заполняется по реальному запуску):

```json
{
  "scenario": "HG-CART-S1",
  "method": "native_report",
  "command": "python -m unittest tests.test_cart",
  "captured_at": "2026-09-24T00:00:00Z",
  "outcome": "passed",
  "observation": "test_rejects_negative_quantity выполнен и проверил неизменность корзины",
  "inputs": ["cart.py", "tests/test_cart.py", "pyproject.toml"],
  "report": "evidence/cart-run.txt"
}
```

Для ручного упражнения method=manual; report содержит условия, действия, наблюдения и предел проверки. Допустимые исходы: passed, failed, skipped, unknown. Состав входов проверяет агент и ревью: CLI не может обнаружить незаявленную зависимость или доказать подлинность отчёта. Хеши фиксируются во время записи; агент обязан сопоставить их с состоянием настоящего запуска. Изменение общего правила обесценивает его сценарии, изменение одного сценария — только его доказательство; изменение входа или отчёта — ссылающиеся доказательства. Сам по себе новый Git SHA не обесценивает неизменённую проверку.

Для trace путь к catalog.json (либо legacy store) включается в spec_files. Его source_hashes использует **trace_sha256 из spec-list**, хеш эффективных требований без доказательств и задач; остальные файлы используют SHA-256 байтов. Это исключает самоссылку при записи evidence. Конфликтующие активные изменения одного требования требуют разрешения до trace. Перенесённые требования исключаются из прежнего владельца по origins, остальные Markdown-требования остаются видимыми. Исходный формат run-record и поддержанные раннеры прежние.

Импорт принимает Requirement по схеме, исходный Markdown с заголовками `### Requirement: [ID]` / `#### Scenario: [ID]`. Инструмент сверяет полный набор сценарных ID и сохраняет оригинальный блок в imports. Это черновик, а не автоматическое подтверждение перевода: смысл, полнота переноса и доказательства проверяются до integrate. Старые файлы не удаляются; после integrate JSON становится владельцем выбранных ID. Неподдержанный Markdown оставь историческим источником до отдельного решения.

Legacy store продолжает читаться; запись v1 требует миграции. Для нового каталога правила записи и восстановления приведены ниже. Прямое редактирование файлов обходит проверки инструмента.

### Номера, версии и приёмка

Обычный spec-new сам назначает `HG-0001`, `HG-0002` и т.д.; заголовок пишет агент. `next_number` и изменение сохраняются одной транзакцией; отмена не освобождает номер. `--id` оставлен для совместимости прежних клиентов и выборочного импорта; для новых задач его не задавай. Зависимые ID получают суффиксы R1/S1/T1. `title` можно менять, `id` и дату создания — нельзя. `created_at` и `decided_at` — секунды UTC от Unix epoch; даты решений выставляет инструмент. Нумерация относится к одному каталогу: независимые Git-ветки не имеют общего счётчика. Создавай задачи в согласованном основном каталоге до разветвления; конфликт одинаковых ID при объединении требует явного разрешения, не автоматического выбора одной версии.

CLI читает v1 без изменения байтов, но запись требует spec-migrate. Он сохраняет точную копию `.highgrade/specs/backups/v1-<sha>.json` перед атомарной заменой; повтор безопасен. ID, доказательства и старые ревью сохраняются. Неизвестные title/created_at остаются пустыми/null, приёмка — пустой историей; не выдумывай даты. Backup принадлежит миграции JSON, прежние OpenSpec-файлы не меняются. Новая версия сама не мигрирует чужие проекты.

`spec-list` вычисляет `technical`: in_progress, ready, abandoned; `human`: pending, accepted, needs_changes, stale. summary содержит количества по каждому признаку; эти два набора не складываются между собой. Завершённые задачи без актуальных доказательств и положительного ревью не дают ready. Включённые изменения тоже проверяются по своим входам и отчётам; потеря файла оставляет пробел. Прежние решения остаются в `change.acceptance`, даже когда их версия устарела.

Перед передачей человеку получи spec-read: `change_sha256` закрепляет редакцию спецификации и доказательств, `inputs_sha256` — фактическое состояние заявленных входов и отчётов. Передай оба хеша вместе с точным идентификатором проверенной реализации (Git SHA или неизменяемый build ID). Затем после явного решения подготовь:

```json
{
  "decisions": [{
    "id": "HG-0001",
    "decision": "accepted",
    "decided_by": "владелец проекта",
    "change_sha256": "хеш из переданной человеку версии",
    "inputs_sha256": "хеш её проверенных входов",
    "verified_revision": "точный Git SHA или build ID",
    "comment": ""
  }]
}
```

Для needs_changes комментарий обязателен. Один неверный/устаревший элемент отклоняет весь пакет. `accepted` требует текущего spec-check; запись решения не обесценивает техническое ревью. Решение относится только к указанным хешам; позднейшая правка не наследует приёмку. Не подменяй переданные человеку хеши свежими после его ответа. При доработке активного change сохраняй его историю; включённое изменение неизменяемо, исправление оформляй новым change. Нет ответа — pending, разрешение реализации не является приёмкой. Инструмент не удостоверяет личность человека, достоверность build ID или полноту declared inputs: эту границу соблюдают агент и ревью. Пакетная приёмка не требует коммита, публикации или принятия всех остальных задач.

### Каталог, миграция и восстановление

При разрешённой инициализации вызови `spec-init --root PATH`, либо `--directory docs/specs`. Каталог должен быть пустым или отсутствовать; чужие документы не присваиваются. Нестандартный путь записывается в проектном `specs-location.json`, независимо от `.highgrade`. Без init первый spec-new создаёт каталог по умолчанию. `spec-read` возвращает объединённый редактируемый объект change, физически spec и results разделены.

Для существующего v1/v2 нужен явный `spec-migrate --root PATH --expected HASH --to directory`. Точные исходные байты сохраняются в `specs-backup-<SHA>.json` в корне проекта. Старый store остаётся историческим; изменение его старой CLI вызывает LegacyStoreConflict, а не молчаливый выбор данных. Сохраняются ID, требования, происхождение, наблюдения, ревью и решения. Никакой массовой конвертации OpenSpec. Общая установка и миграция проекта — разные операции.

Каждая запись меняет только затронутые файлы под одним lock. Незавершённый `transaction.json` блокирует чтение; `spec-recover --root PATH --expected HASH` с хешем из ошибки проверяет все старые/новые байты и явно завершает запись. Не удаляй журнал вручную. После аварии сначала проверь владельца write.lock; только подтверждённо осиротевший lock можно убрать. Staging восстанавливается из журнала. Лимит документа и одной транзакции — 8 МиБ; достижение лимита возвращает ошибку, не обрезает историю. Это восстановление прерванной операции, не гарантия против повреждения диска.

### Связи и теги

В change доступны `depends_on` и `related_to`: массивы `{ "id": "HG-0001", "reason": "Нужен реализованный контракт" }`. Ссылка должна существовать; циклы зависимостей запрещены. depends_on требует интегрированной, не отменённой зависимости перед готовностью; related_to служит навигацией. Содержание не наследуется. `links` в ответе содержит только краткий контекст, включая изменения тех же требований; тексты читаются отдельно.

`tags` — массив ID из плоского `tags.json`. Команды: `spec-tags`; `spec-tag-set --id ID --title TITLE --description TEXT --expected HASH`; `spec-tag-remove --id ID --expected HASH`; `spec-tag-merge --from OLD --into NEW --expected HASH`. Используемый тег не удаляется, merge одной транзакцией меняет ссылки и реестр. Выбирай несколько широких предметных областей; не дублируй статусы и даты. Теги — навигационные данные: их редактура не меняет техническую редакцию. Фильтр не гарантирует полноту контекста; summary описывает весь каталог, selection — выбранную часть.

### Привязки и явный запуск

`checks` в change: `{id, scenario_ids, runner, file, selector, preparation, action, observation, inputs}`. scenario_ids и inputs — массивы строк. Один тест может проверять несколько сценариев, один сценарий — несколько тестов. preparation/action/observation описывают воспроизводимые условия, действие и результат. `runner: null` обозначает ручную проверку; для неё допустимы пустые file/selector. Ручное наблюдение записывается через spec-evidence.

Проектный `runners.json` хранит именованные штатные команды. Добавь конфигурацию через `spec-runner-set --id ID --input runner.json --expected HASH`. Формат: `{ "program":"cargo", "args":["test","--test","{target}","{selector}","--","--exact"], "cwd":".", "format":"cargo-test", "timeout_seconds":60 }`. Для JUnit используй format=junit и аргумент `{report}`: инструмент подставляет уникальный путь отчёта. Доступны `{file}` (абсолютный тестовый файл), `{target}` (его имя без расширения), `{selector}`. Все пути входов и cwd относятся к корню проекта; executable — имя из PATH или проектный относительный путь. Shell не добавляется. Команда является исполняемым кодом проекта и требует обычного ревью.

`spec-run --id HG-0001 --check CHECK_ID|all --expected HASH` запускает только явную выборку. Чтение, фильтры и schema ничего не запускают. cargo-test требует единственного точного прошедшего теста; JUnit — единственного testcase с name=selector либо classname::name=selector. Пустая выборка, пропуск, ошибка, тайм-аут и изменение входов не дают passed. Настрой штатный раннер так, чтобы он завершал дочерние процессы; на Windows тайм-аут завершает дерево taskkill, на остальных платформах — прямой процесс.

runs сохраняет команду, cwd, время, результат, исходные хеши вместе с отчётами в files и снимок inputs_after. Не запущенная проверка получает unknown с причиной. Автоматически добавляются тестовый файл, конфигурация раннеров и проектный executable; остальные значимые исходники/конфиги укажи в inputs. Состав входов и подлинность внешнего отчёта проверяются ревью. Все привязанные автоматические проверки должны пройти; один успех не скрывает соседнюю ошибку.

Повторные spec-run/spec-evidence/spec-review разрешены для интегрированной спеки: требования и spec.json сохраняются, results.json пополняется. Новая редакция доказательств обесценивает прежнее ревью/приёмку; история остаётся. Изменение поведения требует нового change. Новый Git SHA сам по себе не требует новой спеки.
