# Проработка задачи

Прочитай AGENTS, проектную инструкцию и только нужные действующие источники. Если область задачи неясна, найди её целевым поиском по проекту и прочитай найденные источники. Если проектная инструкция отсутствует или несовместима, предложи init или clear; не угадывай местные команды. Только для неясной задачи без выбранного режима предложи A — обсудить по шагам и B — проработать автоматически из контекста. Ясное разрешённое поручение не задерживай выбором режима. Запрос только на анализ остаётся только чтением.

Для существенных нерешённых вопросов используй короткие карточки. Независимые вопросы покажи одним раундом; зависимые задай после ответа на предпосылку:

```text
D<N> — <что нужно решить>
Контекст и последствия: <почему это влияет на результат>
Рекомендую: <A/B/C> — <почему>
A) <вариант> — <что получим и чем платим>
B) <вариант> — <что получим и чем платим>
C) <вариант, если действительно нужен> — <последствие>
Свой вариант: <пользователь может описать решение своими словами>
```

Всегда предлагай два или три взаимоисключающих содержательных варианта, когда вопрос действительно является выбором. Если нужен уникальный факт (например, адрес сервера), спроси его прямо и не выдумывай ложные варианты. Не сокращай выбор до голого вопроса; уже принятые решения и разрешения не переспрашивай. Если варианты и последствия понятны в одной строке, не разворачивай шаблон целиком.

Когда вопросов больше нет, покажи короткий результат: цель, границы, наблюдаемое поведение, существенные исключения и проверки. При явно выбранном пошаговом обсуждении дай один раунд дополнений или исправлений. Если исходное поручение уже разрешает работу и не оставляет существенного выбора, передай краткий результат в spec или work без повторного подтверждения. Для изменения устойчивого поведения сам вызови `highgrade-spec`; иначе передай ясную задачу в work или технический план. Не создавай поведенческую спеку для оформления и рефакторинга без изменения поведения.

## Поведение и примеры

Установи участника, действие, нужный результат и существенные правила предметной области. Для сложного процесса достаточно короткой цепочки «что произошло → кто действует → какое ограничение действует → что меняется»; отдельный воркшоп или событийная архитектура не обязательны. Термины бери из проекта. Согласованное правило важнее случайного текущего поведения кода; обнаруженное расхождение назови явно.

Результат task — цель, границы, существенные решения и наблюдаемое поведение. Не переписывай сюда архитектуру или спецификацию; передай ссылку на уже существующий источник. Требование менять поведение идёт в spec; формализация существующего значимого контракта также допустима, если она прямо поручена. Обычная техническая задача без нового контракта может идти в work.
