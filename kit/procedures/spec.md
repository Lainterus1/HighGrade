# Подготовка спецификации

Маршрутизатор highgrade-spec сохраняет историческое упоминание OpenSpec в описании ради совместимости существующего global-update; фактический формат определяет эта процедура и проектная инструкция.

Возьми согласованное описание результата или эквивалентное явное поручение. Прочитай AGENTS, проектную инструкцию и относящиеся к задаче требования. Найди затронутые компоненты целевым поиском. Для нового изменения используй установленный CLI High Grade и нативный JSON; команды и форматы — в [справочнике](../references/cli.md#структурированные-спецификации). Если проект явно сохраняет старый маршрут OpenSpec, следуй ему до согласованного перехода. Наличие старых файлов само по себе не назначает новый маршрут.

Начни с `spec-list`, затем `spec-new` с полученным `store_sha256` и устойчивым ID изменения. Инструмент создаёт одинаковые поля. Получи `change` через `spec-read`, заполни цель, основание, границы, вопросы, задачи и операции add/modify/remove; сохрани через `spec-save` с хешем именно прочитанного снимка. Для modify сначала прочитай действующее требование. Не редактируй store напрямую, не угадывай защищённые поля; при конфликте перечитай изменение и сопоставь чужие правки. Удаление требует причины. Второго backlog нет. Сохраняй ID при редактуре названий.

## Контракт сценария

Требование объясняет нужное поведение, сценарий показывает конкретный пример. Запиши исходные условия, одно значимое действие, наблюдаемый результат и существенные ограничения или запрещённые последствия. Ожидание выводится из согласованного правила до реализации; оно должно отличать правильную реализацию от нарушения. Детали тестового раннера не становятся продуктовым требованием. Проверка наличия файла не доказывает поведение его содержимого.

Примеры формы, не готовые требования подключаемого проекта:

- Обычное приложение: сохранён валидный каталог; пользователь передаёт запись без обязательного названия; операция возвращает ошибку, прежний каталог не меняется. Проверка вызывает настоящую операцию сохранения и наблюдает состояние.
- Событийный процесс: получены факты о запасе и резерве; поступает запрос резервирования; проверяются ответ и новые факты. Повтор запроса проверяется на отсутствие двойного резерва только если идемпотентность входит в контракт.
- Процедура агента: задача и область записи разрешены, рядом есть чужой файл; агент выполняет задачу; результат достигнут, чужой файл сохранён, непроведённая проверка не объявлена успешной. Наблюдаются реальные действия и файлы, а не совпадение текста ответа.

Для каждого нового или изменённого сценария выбери способ доказательства: штатный автоматический тест (в том числе с форматом вне trace) либо конкретное ручное упражнение. При выборе проверки определи, как воспроизводимо подготовить исходное состояние, выполнить действие и наблюдать результат. Укажи команду/тест или наблюдение и проверяемый исход. Поддержка отчёта в trace — свойство инструмента, не критерий допустимости теста. Выбор проверки ещё не доказывает выполнение.

Выполни `spec-validate`: он проверяет наполненность контракта, но не выполнение задач или тестов. Пустой шаблон остаётся черновиком. Проверь смысл: ожидание выводится из согласованного правила, а не из текущей реализации; не подгоняй требование под ошибку. При готовом контракте и имеющемся разрешении переходи в work без нового формального согласования.

Исторические Markdown/OpenSpec доступны по прежним путям. Выборочный перенос требует явного поручения: `spec-import` создаёт черновик, сохраняет исходный текст и сверяет сценарные ID. Агент и независимое ревью проверяют эквивалентность; после проверок `spec-integrate` переводит владение в JSON. Исходный файл сохраняется как история, другие требования в нём остаются действующими. Не поддерживай две редактируемые версии одного требования.
