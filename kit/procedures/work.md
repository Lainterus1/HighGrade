# Выполнение задачи

Установи полномочия, проектную инструкцию, текущее состояние и один основной источник задач: JSON change High Grade (либо явно сохранённый проектом OpenSpec) для изменения поведения, иначе технический план, если нужны зависимые этапы. Малую ясную задачу выполняй напрямую. Если область кода неясна, найди её целевым поиском и чтением проекта. Не заводи второй backlog. Для новых и изменённых сценариев проверь уникальность ID и подходящий способ доказательства. Изменяй только порученное и запускай минимальные штатные проверки затронутого поведения напрямую. Расширяй их при конкретном риске или обязательном проектном барьере. После них используй `trace` только для поддерживаемых доказательств сценариев; одна отметка на тесте не означает выполненную проверку. Для ручного сценария зафиксируй действие, наблюдение, дату, состояние исходника и предел проверки; отсутствующее доказательство оставь пробелом.

Во время обычной работы доводи документы, бюджеты контекста, временные обходы и архив до состояния текущей задачи. Перед завершением сверь каждый затронутый сценарий с фактическим тестом, ручным наблюдением либо явно названным пробелом. Значимое изменение проходит независимое ревью по риску; недоступное ревью остаётся незавершённым. В итоге кратко назови результат, проверки и существенный остаток; подробный отчёт создавай лишь по запросу или для проверяемого решения. Храни одно основное место машинных результатов, промежуточные прогоны не копируй в архив. `highgrade-approve` по явному вызову сверяет готовый результат, создаёт локальный коммит и выполняет назначенную проектом локальную активацию; `highgrade-push` отдельно публикует выбранный диапазон.

## Доказательства и ревью

Для значимой проверки сохраняй команду, область, состояние проверенного кода и важных зависимостей, время, инструмент, результат и ссылку на исходный машинный отчёт. Дополнительные логи и скриншоты нужны по ситуации; не копируй отчёт в архив задачи. Изменение проверенной логики, тестов или конфигурации требует повторной проверки затронутой области. Неизменённый состав может переиспользовать результат между work, approve и push.

Связь сценария с тестом, успешный код команды и фактическое выполнение теста — разные факты. Для ручного упражнения сохраняй также исходные условия и предел наблюдения. Текст инструкции, отметка ID и наличие отчёта не доказывают исполнение. Пропущенное, неизвестное и устаревшее остаётся пробелом; прежнее исключение относится к конкретным условиям.

Независимое ревью обязательно при изменении поведения продукта, доступа или сохранности данных, архитектурных границ, основных правил workflow либо по запросу автора. Для малых редакций без изменения требований достаточно проверки исполнителя. Передай проверяющему требования, фактические изменения и результаты проверок. Существенные замечания исправь и перепроверь; недоступное обязательное ревью оставляет задачу незавершённой. Ревью не заменяет тесты.

## Содержательные проверки

Проверяй настоящую изменённую логику, а не отдельную упрощённую реализацию. Изолируй дорогие или нестабильные границы по необходимости; свойства транзакций, хранилища, очереди или UI требуют проверки соответствующей границы. Значимая исправленная ошибка получает воспроизводимый регрессионный сценарий, когда это обосновано риском. Входы, часы, случайность и внешние ответы контролируй там, где они влияют на воспроизведение; отдельный DSL или симулятор не требуется.

Проверки повтора, отмены, тайм-аута и порядка событий выбирай из контракта, без универсальной квоты. Для нового существенного правила по возможности убедись, что проверка обнаруживает его нарушение. Для агентной процедуры проверяй действия, границы записи и результат; один прогон не доказывает статистическую устойчивость модели.

Штатный автоматический отчёт вне поддержки trace остаётся автоматическим доказательством: сверь реально исполненный тест и его исход средствами проекта, сохрани команду и исходный отчёт, явно назови границу trace. Успешная команда с пропущенным тестом не закрывает его сценарий. До завершения сопоставь каждый критерий с актуальным результатом либо открытым пробелом; неизменённые проверки не повторяй по одному факту смены этапа.

## Передача и продолжение

| Этап | Минимальный результат |
|---|---|
| task | Цель, границы, существенные решения и наблюдаемое поведение |
| spec | Проверенные требования, сценарии и способы доказательства |
| work | Изменения, актуальные проверки, нужное ревью и явные пробелы |
| approve | Точный локальный коммит и результат назначенной проектом активации |
| push | Выбранный диапазон, проверенный удалённый SHA и применимый результат CI |

Храни принятое, выполненное, ссылки на доказательства и один следующий шаг в основном артефакте задачи. Состояние сеанса может ссылаться на него, но не дублирует задачи спецификации. После перерыва сверь записи с реальным diff и актуальностью проверенных входов. Продолжай с первого незавершённого действия; принятое не спрашивай повторно. Изменившийся состав, утраченная проверка или новый существенный выбор пересматривает только зависимую часть. Не объявляй work завершённым при обязательном незакрытом критерии; публикация и приёмка остаются отдельными состояниями.

## Работа с JSON-спецификацией

Продолжай по `spec-read --id`: задачи, вопросы и сохранённые доказательства находятся в change. Читай отдельные требования через `--requirement`; весь store в контекст не загружай. Наполненность контракта проверяет `spec-validate`, полноту выполнения — `spec-check`.

После настоящей проверки подготовь evidence input по `spec-schema`: метод manual или native_report, команду, время, исходный отчёт/наблюдение, сценарный ID, исход и полную область входов (логика, тест, конфигурация, зависимости, влияющие на результат). До и после запуска проверь неизменность этой области; при изменении повтори проверку. `spec-evidence` фиксирует хеши представленных файлов, но не запускает тест и не подтверждает правдивость переданного исхода. Для поддерживаемого native отчёта дополнительно используй trace; skipped/failed/unknown не записывай как passed. Не включай store в inputs: редакция конкретного сценария закрепляется инструментом отдельно.

Заполняй выполненные задачи через spec-save. Передай независимому ревью diff, исходные отчёты, покрытие входов и требования; при импорте также original_text. Зафиксируй фактический вердикт `spec-review --verdict go|no_go`, автора и заключение. Изменение контракта или доказательств требует актуального ревью. После успешного spec-check выполни spec-integrate: текущие требования и архив change обновляются одной записью. Это техническое включение требований; полномочия на commit/push и пользовательская приёмка остаются отдельными.

При дрейфе базы не переписывай baseline или ожидания ради зелёной проверки: перечитай текущий контракт, закрой заменённый черновик через spec-abandon с причиной и создай новое изменение с явно согласованным результатом. При конкурирующей редактуре используй новый снимок и осмысленно объедини изменения. Устаревшие доказательства сохраняются для объяснения, но не закрывают сценарии.


## Передача человеку и фиксация решения

Технически готовые задачи можно выполнять последовательно, не ожидая приёмки каждой. Передай человеку ID/title, точную проверенную редакцию (Git SHA или неизменяемый build ID), краткий итог, 2–4 действия проверки с ожидаемыми исходами из сценариев и ограничения. Сохрани в основном артефакте передачи change_sha256/inputs_sha256 из spec-read и связь с проверенным build; не создавай вторую спецификацию. spec-list даёт JSON со сводкой технической готовности и человеческих решений.

После явного «принимаю» или возврата на доработку запиши spec-decide по [схеме CLI](../references/cli.md#номера-версии-и-приёмка), сохранив именно переданные версии, автора и комментарий. Для явно выбранных нескольких задач допустим один атомарный пакет; неоднозначный ответ требует уточнения только затронутых позиций. Не выводи приёмку из молчания, согласования плана, тестов или технического ревью. Не записывай решение за человека. При дрейфе покажи изменившуюся версию и запроси её проверку; старое решение остаётся историей. Для включённого change исправление идёт новым изменением. Человеческая приёмка не вызывает approve/push сама по себе и не заменяет их отдельные полномочия.

Если checks настроены, запускай явную выборку spec-run с ожидаемым хешем и анализируй runs и исходные отчёты. Не превращай skipped/unknown/timeout в успешное доказательство. Для неподдержанного автоматического формата используй штатный прямой запуск + spec-evidence с проверкой фактического результата; для ручного — воспроизводимое упражнение. Проверяй полноту inputs, конфигурацию runner и подготовку состояния. Повторная проверка интегрированной спеки не переписывает её требования и не создаёт новую задачу; прежняя приёмка остаётся историей, актуальное решение даёт человек.
