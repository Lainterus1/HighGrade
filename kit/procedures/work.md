# Выполнение задачи

Установи полномочия, проектную инструкцию, текущее состояние и один основной источник задач: OpenSpec change для изменения поведения, иначе технический план, если нужны зависимые этапы. Малую ясную задачу выполняй напрямую. Если область кода неясна, найди её целевым поиском и чтением проекта. Не заводи второй backlog. Для новых и изменённых сценариев проверь уникальность ID и подходящий способ доказательства. Изменяй только порученное и запускай минимальные штатные проверки затронутого поведения напрямую. Расширяй их при конкретном риске или обязательном проектном барьере. После них используй `trace` только для поддерживаемых доказательств сценариев; одна отметка на тесте не означает выполненную проверку. Для ручного сценария зафиксируй действие, наблюдение, дату, состояние исходника и предел проверки; отсутствующее доказательство оставь пробелом.

Во время обычной работы доводи документы, бюджеты контекста, временные обходы и архив до состояния текущей задачи. Перед завершением сверь каждый затронутый сценарий с фактическим тестом, ручным наблюдением либо явно названным пробелом. Значимое изменение проходит независимое ревью по риску; недоступное ревью остаётся незавершённым. В итоге кратко назови результат, проверки и существенный остаток; подробный отчёт создавай лишь по запросу или для проверяемого решения. Храни одно основное место машинных результатов, промежуточные прогоны не копируй в архив. `highgrade-approve` по явному вызову сверяет готовый результат, создаёт локальный коммит и выполняет назначенную проектом локальную активацию; `highgrade-push` отдельно публикует выбранный диапазон.

## Доказательства и ревью

Для значимой проверки сохраняй команду, область, состояние проверенного кода и важных зависимостей, время, инструмент, результат и ссылку на исходный машинный отчёт. Дополнительные логи и скриншоты нужны по ситуации; не копируй отчёт в архив задачи. Изменение проверенной логики, тестов или конфигурации требует повторной проверки затронутой области. Неизменённый состав может переиспользовать результат между work, approve и push.

Связь сценария с тестом, успешный код команды и фактическое выполнение теста — разные факты. Для ручного упражнения сохраняй также исходные условия и предел наблюдения. Текст инструкции, отметка ID и наличие отчёта не доказывают исполнение. Пропущенное, неизвестное и устаревшее остаётся пробелом; прежнее исключение относится к конкретным условиям.

Независимое ревью обязательно при изменении поведения продукта, доступа или сохранности данных, архитектурных границ, основных правил workflow либо по запросу автора. Для малых редакций без изменения требований достаточно проверки исполнителя. Передай проверяющему требования, фактические изменения и результаты проверок. Существенные замечания исправь и перепроверь; недоступное обязательное ревью оставляет задачу незавершённой. Ревью не заменяет тесты.

## Содержательные проверки

Проверяй настоящую изменённую логику, а не отдельную упрощённую реализацию. Изолируй дорогие или нестабильные границы по необходимости; свойства транзакций, хранилища, очереди или UI требуют проверки соответствующей границы. Значимая исправленная ошибка получает воспроизводимый регрессионный сценарий, когда это обосновано риском. Входы, часы, случайность и внешние ответы контролируй там, где они влияют на воспроизведение; отдельный DSL или симулятор не требуется.

Проверки повтора, отмены, тайм-аута и порядка событий выбирай из контракта, без универсальной квоты. Для нового существенного правила по возможности убедись, что проверка обнаруживает его нарушение. Для агентной процедуры проверяй действия, границы записи и результат; один прогон не доказывает статистическую устойчивость модели.

Штатный автоматический отчёт вне поддержки trace остаётся автоматическим доказательством: сверь реально исполненный тест и его исход средствами проекта, сохрани команду и исходный отчёт, явно назови границу trace. Успешная команда с пропущенным тестом не закрывает его сценарий. До завершения сопоставь каждый критерий с актуальным результатом либо открытым пробелом; неизменённые проверки не повторяй по одному факту смены этапа.

## Передача и продолжение

| Этап | Минимальный результат |
|---|---|
| task | Цель, границы, существенные решения и наблюдаемое поведение |
| spec | Проверенные требования, сценарии и способы доказательства |
| work | Изменения, актуальные проверки, нужное ревью и явные пробелы |
| approve | Точный локальный коммит и результат назначенной проектом активации |
| push | Выбранный диапазон, проверенный удалённый SHA и применимый результат CI |

Храни принятое, выполненное, ссылки на доказательства и один следующий шаг в основном артефакте задачи. Состояние сеанса может ссылаться на него, но не дублирует задачи OpenSpec. После перерыва сверь записи с реальным diff и актуальностью проверенных входов. Продолжай с первого незавершённого действия; принятое не спрашивай повторно. Изменившийся состав, утраченная проверка или новый существенный выбор пересматривает только зависимую часть. Не объявляй work завершённым при обязательном незакрытом критерии; публикация и приёмка остаются отдельными состояниями.
