# Инициализация проекта

Определи язык авторских документов по явному указанию автора или действующей проектной инструкции и сохрани его в адаптации. Если он не определён, используй язык текущего запроса с обозначенным допущением по rules.md; отдельный вопрос нужен только при существенном противоречии источников.

Начни с read-only `inspect --bootstrap --root <проект>`: он показывает семь обязательных путей, возможные альтернативы, связи и непросмотренные области до создания реестра. Структурный `failed` из-за отсутствующих путей или связей на этом этапе ожидаем: продолжай обследование, используя находки как список работ; недоступный корень или отсутствие пригодного отчёта останавливает зависимую адаптацию. Для существующего проекта получи обзор структуры через read-only `inventory`, прочитай действующие инструкции, основные документы, команды и источники затронутой области по `references/audit.md`. Углубляй проверку там, где требуется перенос или найден риск; перечисли непрочитанное и неизвестное, не называя обзор полным продуктовым аудитом. Для нового проекта выясни назначение, критерии успеха, риски, ограничения и пожелания автора. Задавай только вопросы, на которые ещё нет ответа.

Сопоставь документы с пятью основными ролями и каноническими путями: `README.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/ENGINEERING.md`, `docs/DEVELOPMENT.md`; проектная инструкция и реестр находятся в `.highgrade/project/INSTRUCTIONS.md` и `.highgrade/project/documents.json`. Составь краткую таблицу только по пробелам и спорным совпадениям: **путь или связь → проверенный источник → решение → открытый вопрос**. Для найденного по имени кандидата проверь содержание и явно отклони ложное совпадение с причиной. Если сканер не нашёл документ, ищи его содержание самостоятельно. Эквивалентный документ с другим именем перенеси, смешанный раздели по ответственности, действительно недостающее содержание создай; сохраняй дополнительные профильные источники. После переноса обнови входящие ссылки и реестр. Для местного навыка, пересекающегося с общим, установи повод вызова, вход, выход и владельца действия, покажи конфликт и варианты. Не устанавливай два конкурирующих активных пути молча.

Предложи проектную инструкцию по [критериям адаптации](../references/audit.md#контекст-и-адаптация), ссылки из README к четырём основным документам и из AGENTS к проектной инструкции, маршрут спецификации High Grade и решение о совместимости со старым форматом, проектные команды, бюджеты контекста и один план адаптации. До разрешения изменений init остаётся аудитом и планом. Если адаптация уже разрешена, выполни её без повторного согласования определённых решений. Шаблоны заполняй по проверенным источникам; незаполненные поля не объявляй согласованными. После выполнения проверь `doctor`, обычный `inspect` и применимые штатные проверки; структурный отчёт не заменяет смысловую сверку результата. Техническое подключение и пользовательская приёмка различаются. Общие навыки, CLI и процедуры в проект не копируются. При повторном init используй действующую адаптацию и меняй только выявленные пробелы.

Формат реестра и начальный JSON — в [справочнике CLI](../references/cli.md#начальный-реестр-документов). Адаптируй области по обследованию; не угадывай схему по именам полей.
