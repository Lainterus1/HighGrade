# Местная инструкция Проекта High Grade

Статус: Поставка v0-2-17 [активирована локально](../../docs/releases/v0-2-17.md). Установленную версию проверяет `global-status`. Эта инструкция управляет только Проектом — репозиторием разработки Поставки — и не входит в установленную Поставку. Подключаемые проекты получают собственную адаптацию; термины определены в [README](../../README.md#термины-и-границы).

## Владение знаниями

- Цель и вход: [README](../../README.md).
- Агентские правила: [AGENTS](../../AGENTS.md).
- Фактическое устройство: [ARCHITECTURE](../../docs/ARCHITECTURE.md).

## Работа над задачей и спецификацией

- Язык Проекта — русский, в том числе для сохраняемых спецификаций, задач, планов, состояния, отчётов и передачи человеку. Это явный выбор языка для навыков с английским по умолчанию. Имена полей JSON, ID, команды, пути, машинные статусы и дословные исходные сообщения не переводятся.
- Изменения требований веди через установленный `highgrade-spec` и команды `spec-*`: `specs/changes/<ID>/spec.json` и `results.json`, schema_version 3. Версию активной CLI проверяй через `global-status`. Шаблон создаёт CLI; агент заполняет его и сохраняет через инструмент. Команды и проверки — в [DEVELOPMENT](../../docs/DEVELOPMENT.md), формат — в [справочнике Поставки](../../kit/references/cli.md#структурированные-спецификации). Не создавай новое OpenSpec-изменение или второй список задач.
- Прежние OpenSpec-исходники побайтно сохранены в [архиве](../../docs/archive/legacy-openspec/); старая [карта переноса](../../docs/archive/legacy-openspec/migration.json) и [карта канонизации](../../docs/archive/legacy-native-specs/2026-09-25/mapping.json) относятся только к истории. Действующие требования самостоятельны и названы по нативному HG-счётчику. Наличие требования не подтверждает сценарий и не означает человеческую приёмку. Для будущего выборочного импорта остаётся `spec-transfer`; готовность устанавливай отдельно по доказательствам и `spec-check`.
- Каталог specs принадлежит Проекту и зарегистрирован в [реестре](documents.json). Действующие требования — requirements; изменения и результаты — changes/<ID>. Читай выборочно через spec-list/read, включая краткие зависимости; теги помогают выборке, но не доказывают полноту. Повторные проверки сохраняют историю results; изменение требований или нормативных сценариев требует новой спеки; восстановление реализации по существующему контракту обновляет результаты. Структуру и готовность проверяют spec-validate/check, не Markdown-проверка inspect. Старый store после миграции — история, писать в него старой CLI нельзя.
- Общие навыки High Grade маршрутизируют init, task, spec, work, planner, clear, approve, push и update. Для зависимых задач или спек Проекта принят автоматический Planner с одним Goal на цепочку; явный вызов также запускает Goal в границах запроса. Исходные пакеты SVG и Code Health Audit под `plugins/` — отдельные специалисты и не заменяют общие маршруты.
- Штатные проверки и сценарные ID: [DEVELOPMENT](../../docs/DEVELOPMENT.md), критерии доказательств — [QUALITY](../../docs/workflow/QUALITY.md). Trace охватывает только поддерживаемые Rust nextest/Playwright-сценарии после native запусков; ручные сценарии требуют отдельного наблюдения.
- Независимое ревью значимых изменений этого репозитория выполняет отдельный субагент по правилам [work](../../kit/procedures/work.md#доказательства-и-ревью). Для него разрешён просмотр незакоммиченных изменений в пределах Проекта без повторного согласования; передавай требования, относящийся к задаче diff и результаты проверок. При недоступности обязательного ревью не объявляй задачу проверенной.

## Локальное принятие через `highgrade-approve`

- Область коммита определяется принятой задачей, её спецификацией при наличии и ревью; посторонние изменения остаются вне него. Перед коммитом выполни проверки из [DEVELOPMENT](../../docs/DEVELOPMENT.md), проверь полный staged diff, лицензию и отсутствие закрытых данных. Рабочие документы и архив готовит work; approve устраняет найденный разрыв. Неудача проверки возвращает задачу в work.
- Разовый переход на v0-2-7 завершён; его условия сохранены в [архивной спецификации выпуска](../../docs/archive/legacy-openspec/specs/release-workflow/spec.md), результат — в [записи выпуска](../../docs/releases/v0-2-7.md). К текущим задачам переходная процедура не применяется.
- `highgrade-approve` всегда создаёт точный локальный коммит. В этом Проекте локальная активация назначена, если меняется исполняемая CLI (`src/`, `Cargo.toml`, `Cargo.lock`) или Поставка `kit/`, либо автор явно просит активировать. Для остальных проектных документов и скриптов без такого поручения не собирай кандидат выпуска и не повышай версию; нужные тесты выполняй обычным маршрутом.
- Если активация назначена, **до коммита и сборки кандидата** назначь следующий неиспользованный release ID: повысь patch-версию синхронно в `Cargo.toml`, `Cargo.lock`, `kit/manifest.json` (`release` и `cli_version`) и обнови ожидания версии в тестах. Проверь манифест и тесты. Не собирай для активации новый кандидат с уже установленным ID: выпуск неизменяем.
- При назначенной активации после коммита выполни `python scripts/build-release.py <SHA>`: изолированные исходники удаляются, Cargo использует `target/highgrade/build-cache`, готовый кандидат — `target/highgrade/candidate`. Запусти **CLI кандидата**: `target/highgrade/candidate/highgrade.exe global-update --profile <домашний-каталог> --source target/highgrade/candidate/kit --candidate-exe target/highgrade/candidate/highgrade.exe`. Подробности — в [инструкции сборки](../../docs/BUILD.md). Сначала preview и смысловая сверка, затем apply с тем же `candidate_sha256`. Не собирай из грязного дерева. Проверка — `global-status`; после сбоя проверь фактическое состояние по [процедуре Update](../../kit/procedures/update.md#повтор-и-ошибки). Если активация не прошла, коммит остаётся, статус задачи частичный. Approve не разрешает GitHub push.

## Публикация через `highgrade-push`

- По отдельному поручению отправь выбранный непрерывный диапазон готовых коммитов в `origin/main` репозитория `Lainterus1/HighGrade`. Диапазон может включать несколько задач. До отправки сверь состав, результаты approve, актуальное состояние удалённой ветки и последствия CI; неоднозначный состав покажи автору. Используй обычный push без force и сверь `refs/heads/main` на origin с итоговым SHA. Отправка не доказывает местную активацию каждого коммита; установленная версия определяется только `global-status`. Установленные SVG/CHA и другие проекты не входят в маршрут.

## Полномочия и исключения

- Этот репозиторий поддерживает исходники High Grade. Работа с SNAF, PlantsNotify и другими целевыми проектами выполняется в их каталогах по отдельному поручению.
- Публикация следующих версий, переключение SVG/CHA, деплой и приёмка пилотов требуют соответствующего поручения; прежние выпуски не дают постоянного разрешения на эти действия.
- Для выпуска v0-2-15 автор 2026-09-25 явно принял все 15 действующих спек, остановил дополнительные агентные пилоты и поручил продолжить коммит, локальную активацию и публикацию при известных пробелах проверки. Решение и точный исходный снимок — в [записи](../../docs/evidence/spec-verification/2026-09-25-human-decision.json), технический остаток — в [записи выпуска](../../docs/releases/v0-2-15.md). Исключение действует только для этого выпуска: недостающие наблюдения не отмечать `passed`, машинный статус CLI не подменять. Остальные найденные конфликты показывать автору до зависимого действия.
